## X4 shared の認証と暗号の部品

### X4 の前提

- 対象は M1（shared）の認証の手順と、M3・M4 が渡す `CryptoProvider` の約束。ペアリングの手順、署名、再送防止の判定、指紋の表示形式を書く
- M1 は時計と乱数と暗号の実体に触れない（B1-3）。時刻、乱数、`CryptoProvider` は引数で受ける
- ルートの検査の順と HTTP の扱いは X5、端末側の署名ヘッダの付与は X6。この節は「何を入力にして何を返すか」まで
- 用語は B4 に従う。コードは 6 桁の数字（V1）、K は署名用の鍵（32 バイト）、device_id と pc_id は乱数 16 バイト（UUID の形）

### X4-1 `CryptoProvider` の表

- 置き場：インターフェースの定義は M1。実体は M3（PC 側）と M4（端末側）が渡す。テストでは固定の乱数と既知の値を返す偽の実体を渡す（N5-1）
- 失敗は例外にせず、結果の型で返す（X3-5 の結果の型に合わせる）。暗号の部品の内部の失敗は E の番号を持たず、手順の失敗として扱う
- 点は P-256 の曲線上の点で、符号化は非圧縮形式（65 バイト）とする（RFC 9382 の P-256 の定義による。細部は未確認）
- 点演算の実体は Bouncy Castle の楕円曲線の演算（J16）。SPAKE2 の手順は M1 に置く。Bouncy Castle 1.80 の仕様書に SPAKE2 は載らない（確かめた事実 4b）

| 部品 | 入力 | 出力 | 副作用 |
|---|---|---|---|
| 乱数 | バイト数 n | n バイトの暗号論的な乱数 | OS の乱数源を読む。M1 は直接呼ばない |
| HMAC-SHA256 | 鍵（バイト列）、メッセージ（バイト列） | 32 バイト | なし |
| HMAC-SHA256（鍵の参照版） | 署名鍵の参照、メッセージ（バイト列） | 32 バイト | 実体が鍵の持ち方（K1 の値、Keystore の別名）を吸収する |
| HKDF-SHA256 の抽出と展開 | 入力鍵材料、塩（空可）、情報の文字列、出力の長さ | 指定の長さのバイト列 | なし |
| SHA-256 | バイト列 | 32 バイト | なし |
| 点の定数倍（基点） | スカラー（32 バイト） | 点 | なし |
| 点の定数倍（任意の点） | 点、スカラー | 点 | なし |
| 点の加算 | 点 2 つ | 点 | なし |
| 点の符号反転 | 点 | 点 | なし |
| 点の復号 | 65 バイト | 点、または曲線上にない旨の失敗 | なし |
| 定数時間の比較 | バイト列 2 つ | 真偽 | なし |

- スカラーを群の位数で割った余りに直す処理は、点演算の部品の側の約束とする（M1 では行わない）。任意長の整数が要る箇所は、32 バイトの固定長で受け渡す
- SPAKE2 の定数点 M と N は M1 が持つ定数。値は RFC 9382 の P-256 の定義から写す（実装時に原本と照合する。未確認）
- 端末側の署名は K3 を Keystore に取り込んだ後は取り出せない（B4-3 の 2）。そのため署名の部品は「鍵の参照と本文で HMAC を得る」形にも使えるよう、M4 の実体が鍵の持ち方を吸収する。M1 の署名の手順は、鍵の参照（M3 は K1 から読んだ値、M4 は Keystore の別名）を不透明な値として受ける

| 型 | 項目 | 型 | 必須 | 意味 |
|---|---|---|---|---|
| 署名鍵の参照 | 種別 | 区分（バイト列、Keystore の別名） | 要 | 実体が解釈する |
| 署名鍵の参照 | 値 | バイト列または文字列 | 要 | 種別に応じる。ログに出さない |

- 署名鍵の参照を使う署名の部品として、上の表に「HMAC-SHA256（鍵の参照版）」の行を足した。B1-3 への反映は基本設計の直し 16

### X4-2 ペアリングの手順

#### X4-2-1 状態機械

- 端末側（状態は M4 が持つ。M1 は純粋な関数だけを持つ）
- D0〜D4 は端末の状態。概要設計の決定 D1〜D14 とは別

| 状態 | 入る条件 | 出る条件 | 次の状態 |
|---|---|---|---|
| D0 未開始 | 画面の操作 | コードの入力を受けた | D1 |
| D1 開始の送信待ち | P5 の要求を作った | P5 の応答を受けた | D2 |
| D2 確認の送信待ち | 端末の確認の印 MAC_d を作った | P6 の応答を受けた | D3 |
| D3 検証中 | PC の印 MAC_p を受けた | 印が合えば K を導く | D4、失敗 |
| D4 取り込み中 | K の導出の完了 | K3 と K4 の保存が済んだ | 完了 |
| 失敗 | 各段の失敗 | 画面の操作 | D0 |

- 端末の保存（K3、K4）は、MAC_p の照合を経た P6 の成功で確定する。指紋は画面に表示するだけで、確認の段ではない。指紋が違うと思えば、PC の W3 と端末の S5 の両方で解除する（J27。2026-11-06）

- PC 側（状態は M3（X5 の前提、X5-5）が持つ。コードの生成と試行の判定は M1 の純粋な関数）

| 状態 | 入る条件 | 出る条件 | 次の状態 |
|---|---|---|---|
| H0 閉 | 起動、コードの無効化 | コードの作成（W4 の操作） | H1 |
| H1 開（コード表示中） | コードを作った | P5 を受けた、V3 の経過、使用後 | H2、H0 |
| H2 P5 済 | P5 に応答した | P6 を受けた、V3 の経過 | H3、H0 |
| H3 検証中 | P6 を受けた | 印が合う、合わない | 成功、H1 または H0 |
| 成功 | 印が合い、K1 の保存が済んだ | コードを無効にする | H0 |

- H0 のうち V4 の待ちの間は `pairing_locked`、それ以外は `pairing_closed` を返す（X4-2-2）
- H2 のあいだに別の P5 を受けた場合は、先の P5 の途中状態を破棄して新しい P5 を処理する（同時に進められるのは 1 本。決定（未付番）。LAN の第三者の P5 で正規の端末の P6 を妨げられるが、試行は数えないので妨害の効果は限られる）
- 状態は PC のメモリだけで持つ。再起動で H0 に戻る

#### X4-2-2 P5 の本文（B4-4 の 1、B4-2 の段 1・2）

要求の本文

| 項目 | 型 | 必須 | 意味 |
|---|---|---|---|
| `device_id` | 文字列（UUID の形） | 要 | 端末の識別子 |
| `device_name` | 文字列 | 要 | 機種名まで。人名を含めない（N1-6） |
| `x` | 文字列（base64url） | 要 | SPAKE2 の端末の値 X（65 バイトの点） |

応答の本文（成功時）

| 項目 | 型 | 必須 | 意味 |
|---|---|---|---|
| `pc_id` | 文字列（UUID の形） | 要 | PC の識別子 |
| `y` | 文字列（base64url） | 要 | SPAKE2 の PC の値 Y |

- 失敗の順：(1) コードを表示していなければ 403（E2）。V4 の待ちの間は `detail=pairing_locked`、それ以外は `detail=pairing_closed`。(2) devices（K1 の表）が 1 件でもあれば、device_id によらず 403（E2、`detail=device_exists`。D11、D14。review-11）。P5 の連続は B4-4 の 7 の 429 の対象
- P5 は試行を数えない（B4-2 の 2）。端末を入れ直して device_id が変わっても、登録が残っていれば受け付けない。利用者は PC の W3 で解除してからやり直す

#### X4-2-3 P6 の本文（B4-4 の 1、B4-2 の段 3・4）

要求の本文

| 項目 | 型 | 必須 | 意味 |
|---|---|---|---|
| `device_id` | 文字列 | 要 | P5 と同じ値 |
| `mac_d` | 文字列（base64url） | 要 | 端末の確認の印 |

応答の本文（成功時）

| 項目 | 型 | 必須 | 意味 |
|---|---|---|---|
| `mac_p` | 文字列（base64url） | 要 | PC の確認の印 |

- 失敗：印が合わなければ 401（E2）で、その時点のコードの試行を 1 回数える。数えた結果が V2 に達したら H0 に戻し、以後は P5・P6 とも 403（`pairing_locked`）を V4 の間返し、その後に利用者がコードを作り直す
- P6 の応答の前に、K1 への保存と settings.json の `devices` への追加（X5-4。K1 と同じ時点）を済ませる。保存に失敗したときは、成功の応答を返さず 500 相当の失敗を返し、端末は何も保存しない（B4-2 の 2）。応答の HTTP の番号と E の対応は X5 が確定する（J21）

#### X4-2-4 SPAKE2 の手順（疑似手順）

端末は A、PC は B の役とする。コードは UTF-8 の数字の列。`TT` は RFC 9382 の転写。2026-11-07 に実装を RFC 9382 の付録 B の試験ベクターで検算し、この手順を実装に合わせた。

1. 端末と PC は、コードからパスワードのスカラー w を作る。入力はコード（V1 桁）、情報の文字列は `psfox v1 pake-password`。HKDF で 32 バイトを作り、そのまま w とする（J21。RFC 9382 の MHF とは違う独自の選択）。群の位数で割った余りを取るのは点演算の実体の側で（X4-1）、`TT` には 32 バイトのまま入れる。位数以上になる確率は 2 の −32 乗ほどで、両側が同じ値を使うので整合する
2. 端末は乱数のスカラー x を作り、X = x・基点 + w・M を計算して P5 で送る
3. PC は P5 で X を受け、X が曲線上の点であることを確かめる（復号の失敗は 400）
4. PC は乱数のスカラー y を作り、Y = y・基点 + w・N を計算して P5 の応答で返す。PC は K = y・(X − w・M) を求める
5. 端末は Y を受け、K = x・(Y − w・N) を求める。両側の K は等しくなる。途中の点が無限遠点になっても、実体は例外を投げず、P5 の応答を変えない（P5 の失敗は試行に数えないので、応答が変わるとコードを当てる手がかりになる）
6. 転写 `TT` は、A の識別子、B の識別子、X、Y、K、w の順に、長さ（8 バイトのリトルエンディアン）を前置して連ねる。ここで A の識別子は device_id、B の識別子は pc_id で、どちらも UUID の文字列の UTF-8 とする
7. 付加データ AAD は、device_id、pc_id、PC の SPKI の SHA-256 の全体（32 バイト）を長さ付きで連ねたもの（B4-2 の 2 の段 3。長さ付きにする理由は、境界の曖昧さによる衝突を避けるため）
8. `Ke || Ka = SHA-256(TT)` とし（前半が Ke）、確認の鍵 `KcA || KcB` を `Ka` から HKDF で導く。情報の文字列は `ConfirmationKeys` に AAD を続ける（RFC 9382 の形）
9. 端末は `MAC_d = HMAC(KcA, TT)` を作り、P6 で送る。PC は同じ値を計算して一定時間の比較で照合する
10. 合えば PC は `MAC_p = HMAC(KcB, TT)` を返し、端末が照合する
11. 両方の印が合ったら、`K = HKDF(Ke, 塩なし, "psfox v1 request-signing", 32)` を両側で導く（B4-2 の段 5）

- TLS が提示した SPKI のハッシュは、端末が P5 の接続で見たもの、PC が自分の証明書から計算したものを使う。中間者が別の証明書を提示した場合、AAD が食い違い、印が合わない（B4-3 の 1）
- 端末の画面に出す指紋は X4-4 の形式を使う。表示だけで、保存の確定には関わらない（J27）

#### X4-2-5 試行の数え方とコード

| 項目 | 規則 |
|---|---|
| 数える事象 | P6 の MAC_d の不一致だけ。P5 の失敗、書式の誤りは数えない |
| 数える単位 | 現在のコード 1 つにつき。コードを作り直すと 0 に戻る |
| 上限 | V2。達したらコードを無効にして H0 に戻る（V2 回目の不一致で無効） |
| 上限後の待ち | V4 の間はコードを作れない |
| 有効時間 | V3。H1 に入った時刻から。V3 ちょうどは無効（F5-4。review-11） |
| 使用後 | 成功したら即座に無効 |

コードの生成（疑似手順）

1. `CryptoProvider` の乱数で 4 バイトを得る
2. 符号なしの整数として読み、10 の（V1 の桁数）乗で割った余りを求める。偏りを避けるため、2 の 32 乗を 10 の（V1 の桁数）乗の倍数に切り下げた値以上の乱数は捨てて、1 に戻る（最大 V42 回。超えたらエラー）
3. 先頭を 0 で埋めて V1 桁の文字列にする

- 総当たりの余地：V2 と V4 の組み合わせでは、1 回のコードで当てられる確率は V2 / 10 の V1 乗。コードは作り直しと V3 の経過で無効になるので、攻撃者が続けても 1 回のコードごとに同じ確率になる。確率の見積りは X4-2-5 の「総当たりの余地」にある（B1 も同じ参照。B4-2 に検証の節は無い。X4 の他の節への依頼 4）

### X4-3 署名と再送防止

#### X4-3-1 署名対象の組み立て（B4-4 の 6）

入力

| 項目 | 型 | 必須 | 意味 |
|---|---|---|---|
| メソッド | 文字列 | 要 | 大文字に正規化して使う |
| パスと問い合わせ | 文字列 | 要 | 送った文字列のまま。再エンコードしない |
| タイムスタンプ | 整数（UTC のエポック秒） | 要 | 呼び出し側が時計から渡す |
| nonce | 16 バイト | 要 | 呼び出し側が乱数から渡す |
| device_id | 文字列 | 要 | 署名鍵の索引 |
| 本文 | バイト列 | 要 | 空なら長さ 0 のバイト列 |

手順

1. 本文の SHA-256 を計算し、小文字の 16 進にする（空の本文なら、空の列の SHA-256 の 16 進）
2. 7 行を LF で連ねる。順は B4-4 の 6 の表のとおり（`PSFOX1`、メソッド、パスと問い合わせ、タイムスタンプ、nonce、device_id、本文のハッシュ）
3. nonce は base64url（パディングなし）の文字列で行に入れる
4. 末尾に LF は付けない
5. UTF-8 のバイト列にして HMAC-SHA256 を取り、base64url（パディングなし）にする

- 各行にはもともと LF を含められない値だけが入る。含まれていれば 400 に当たる書式の誤りとして、署名の前に弾く（X5 の検査の順で扱う）
- `Range` は署名しない（B4-4 の 6）

署名ヘッダ（出力）

| 項目 | 型 | 必須 | 意味 |
|---|---|---|---|
| `X-Psfox-Device` | 文字列 | 要 | device_id |
| `X-Psfox-Timestamp` | 文字列（10 進の整数） | 要 | エポック秒 |
| `X-Psfox-Nonce` | 文字列（base64url） | 要 | 乱数 16 バイト |
| `X-Psfox-Signature` | 文字列（base64url） | 要 | 手順 5 の値 |

- ヘッダの名は Q1 で変わりうる（B4-4 の 1）。名前は定数として 1 か所に置く

#### X4-3-2 検証の疑似手順（PC 側。呼び出しは X5）

入力：メソッド、パスと問い合わせ、本文、4 つのヘッダの値、現在時刻、PC の起動時刻、K1 の引き当て、再送の記録。出力：成功、または E2 の `detail` 付きの失敗

1. ヘッダの欠けによる 400（書式の誤り）は、X5-1 の検査 4 で呼び出しの前に済んでいる前提とし、ここでは検査しない
2. タイムスタンプが 10 進の整数でないときの 400 も同じ（X5-1 の検査 4）。ここでは整数として受ける
3. タイムスタンプが PC の起動時刻より前なら、V12 の幅の内でも 401（`detail=clock_skew`）。再起動で nonce の記録が消えても、起動前の通信の再送を通さないため（J29。2026-11-06）
4. 現在時刻との差の絶対値が V12 を超えれば 401（`detail=clock_skew`）
5. device_id で K1 を引く。未登録なら、署名が合わない場合と同じ時間をかけて 401（`detail` は出さない。区別を外に出さない）。時刻の検査（手順 3、4）を引き当ての前に置くので、時刻の誤りの応答は登録の有無によらず同じになる（X5-1 の検査の順もこれに揃える。review-11）
6. X4-3-1 の手順で署名を計算し、一定時間の比較で照合する。合わなければ 401（E2）
7. 署名が合ってから、（device_id、nonce）が再送の記録にあるかを調べる。あれば 401（`detail=replay`）
8. 記録に無ければ追加して成功とする

- 手順 7 を署名の後にする理由：署名の合わない要求で記録を埋められないため
- 失敗の応答は B4-4 の 8 の表に従う。署名の失敗が続く接続元の 429（V43 に達したら V32 の間。X1-4 の A10）は X5 が数える。この節は失敗の種別を返すだけ

#### X4-3-3 nonce の保持

| 項目 | 規則 |
|---|---|
| 保持の期間 | V12 の 2 倍（記録の追加から） |
| 保持の場所 | PC のメモリのみ。再起動で消える（手順 3 の「起動時刻より前」の拒否で補う） |
| 索引 | （device_id、nonce） |
| 掃除 | 追加のたびに、期間を過ぎた記録を先頭から消す |
| 上限 | 件数の上限（V41）を置く。引数で受け、試験では小さい値を渡せる。超えたら古い記録から消す |

- 件数の上限を超えて古い記録を消した場合でも、その記録のタイムスタンプは V12 を超えて古いか、もう近いうちに許容を外れる。許容の幅のうちに再送された場合は通る余地が残る。上限（V41）は 1 台 1 回の同期の要求数に対して十分大きく取る

#### X4-3-4 時刻のずれ

- 端末と PC のどちらの時計が違うかは、PC は区別できない。応答の `detail=clock_skew` に PC の現在時刻（UTC の秒）は添えない（J21）
- 端末は `detail=clock_skew` を受けたら「端末と PC の時計が違う」と案内する（B4-4 の 7。画面は X6 と X7）
- V12 は前後同じ幅。端末の時計の進みと遅れの区別はしない

### X4-4 SPKI のハッシュと指紋の表示形式

| 項目 | 規則 |
|---|---|
| 対象 | 証明書の SubjectPublicKeyInfo の DER のバイト列 |
| ハッシュ | SHA-256（32 バイト）。T4 の `spki_hash` と K4 には全体を持つ |
| 固定の照合 | 32 バイト全体を定数時間で比較する |
| 表示 | 先頭 12 バイトを小文字の 16 進にし、4 桁ずつ空白で区切る（B4-2 の 3）。例：`0a1b 2c3d 4e5f 6071 8293 a4b5` |

- 証明書全体でなく SPKI のハッシュを使う理由は B4-3 の 1 のとおり。期限切れで証明書を作り直しても同じ鍵なら照合は通る
- DER の SPKI の取り出しは、証明書の解析が要る。M1 は証明書の解析を持たず、M3・M4 が SPKI の DER を取り出して M1 へ渡す（X4 の他の節への依頼 2）
- 端末の画面は、P5 の接続で TLS が提示した証明書から計算した値を出す。PC の画面（W4）は自分の証明書から計算した値を出す。両者は M1 の同じ関数で表示を作る（別実装にしない）。テストは関数 1 つの分で足りる（X4-5）

### X4-5 テストの観点

- 試験ベクターは公開されたもの（RFC 9382 の付録、HKDF と HMAC の RFC の例、SHA-256 の標準の例）を使う。値は実装時に原本から写す（未確認。本稿に値は書かない）
- 試験ベクターの置き場は M1 のテストの資源とする（手順は M1 が持つため）。M3・M4 の実体（HMAC、HKDF、SHA-256、点演算）は、同じ既知の入力で既知の値を返すかを、各モジュールのテストで確かめる（review-11）
- w の導出（HKDF の 1 段。X4-2-4 の 1）は RFC の MHF と違う独自の選択で、RFC のベクターでは検算できない。ベクターには w を直接与える範囲まで使い、w の導出の期待値は手で作った試料で確かめる
- 乱数は固定の偽の実体で与える。乱数の呼び出しの順が試験ベクターと一致するように、手順の中で乱数を得る順を固定する（x の次に y。コードの生成は別）

| 観点 | 入力と期待 |
|---|---|
| SPAKE2 の一致 | 固定の x、y、w から、両側が同じ Z、V、TT、K を得る |
| コードの不一致 | w を 1 桁違いにすると、MAC_d が合わず、K に至らない |
| AAD の不一致 | PC の SPKI のハッシュを 1 バイト変えると、印が合わない（中間者の再現） |
| 端末側の MAC_p の不一致 | PC が返す MAC_p を 1 バイト変えると、端末は K に至らず失敗する（偽の PC を拒否する） |
| 点の検査 | 曲線上にない点の X は復号で失敗する。無限遠点は拒否する |
| 途中の無限遠点 | `X = w・M` を送って K の途中が無限遠点になっても、実体は例外を投げず、P5 は別の入力と同じ形で応答する（実体を作る束 4・5 で確かめる） |
| 試行の数え方 | P5 の失敗は数えない。P6 の不一致は 1 回ずつ数え、V2 回目で無効になり、V4 の間は P5・P6 とも `pairing_locked` |
| コードの有効時間 | V3 の 1 秒前は通り、V3 ちょうどと直後は 403（`pairing_closed`）。時刻は引数で与える。H2 で V3 ちょうどに届いた P6 は、MAC_d が合っていても 403（`pairing_closed`）で、端末は登録されない |
| 使用済みのコード | P6 の成功の後（V3 の内）は H0 になり、P5・P6 とも 403（`pairing_closed`）。2 台目は登録されない |
| コードの生成 | 偏りの除外の境界（閾値の直前と直後の乱数）。先頭の 0 の埋め。除外が V42 回を超えたらエラー |
| 署名対象 | 固定の入力から 7 行の文字列が一致する。本文が空の場合の 7 行目。末尾に LF が無い |
| 署名の一致 | HMAC の試験ベクターの形で、既知の鍵と文字列から既知の値になる |
| 時刻の境界 | 差が V12 ちょうどは通り、1 秒超過は `clock_skew`。起動時刻より前は V12 の幅の内でも `clock_skew` で拒否、起動時刻ちょうどは通る |
| 再送 | 同じ（device_id、nonce）の 2 回目は `replay`。署名の失敗では記録に残らない |
| 未登録の端末 | 時刻が許容の内なら、署名の誤りと同じ失敗の応答になる（`detail` の差が無い）。時刻が許容の外なら、登録済みと同じ `clock_skew` になる |
| nonce の掃除 | V12 の 2 倍を過ぎた記録が消える。件数の上限（V41。引数で小さくして試す）で古い順に消える |
| 指紋の表示 | 既知の SPKI から 24 桁の 16 進を 4 桁ずつに区切る。12 バイトを超えて出さない |

- テストは M1 の JVM のテストで実行する（B1-3）。実機は要らない

### X4 の決定（未付番）

- ペアリングの処理は同時に 1 本だけ進める。後の P5 が先の P5 の途中状態を破棄する（X4-2-1）
- 再送の記録の確認は署名の照合の後に行う（X4-3-2 の手順 7）
- 署名鍵は不透明な参照で受け、M3 は K1 から読んだ値、M4 は Keystore の別名を渡す（X4-1）
- 時刻の検査は device_id の引き当ての前に行う（X4-3-2。review-11）

### X4 の置いた値

V41（nonce の記録の件数の上限）、V42（コードの生成の偏り除外の最大の繰り返し）、V43（署名失敗の連続の閾値）に反映済み（X1-4 の A8〜A10。review-11）。
