## B4-1 発見

- サーバーは 1 つの TCP ポート（V16）で HTTPS を受ける。接続方式による違いは、端末が接続先を決める方法だけ（F2-1、D7）
- 端末は接続先の候補を次の順に試す。1 件ごとの待ち時間は、接続の確立が V29、P3 の応答の待ちが V53（J47）。LAN は先に NSD の引き直しの待ち V14 が付くので、1 件は最大 V14＋V29＋V53（J39、J47）。つながった先は、端末が T4 の `last_endpoint`（最後に成功した方式。J30。2026-11-06）に保存し、次回は先頭にする。LAN のサービス名、Tailscale の名前、USB の宛先の 3 列（B3-4 の T4）は、方式ごとの宛先の記録とする

| 順 | 候補 | 方式 | T4 の列 |
|---|---|---|---|
| 1 | 最後に成功した方式（`last_endpoint`）の接続先 | 全方式 | T4 の `last_endpoint` |
| 2 | mDNS で見つけた宛先 | 同一 LAN の Wi-Fi、USB テザリング | LAN のサービス名（成功後に保存） |
| 3 | 利用者が入力した宛先 | Tailscale、ほか全方式 | Tailscale の名前、USB の宛先（成功後に保存） |

- 保存先の列は入力の形で決まる（X7-2-4）。名前は Tailscale の列、IPv4 の手入力は USB の列。USB の列は「IPv4 の手入力の宛先」の意味で、LAN の IP を手入力しても USB の列に入る（`last_endpoint` も `usb`）

### 1 mDNS の広告（F2-2）

- PC は JmDNS（B1 の技術の選定。代替は B1）で、起動している間、広告する。端末は NSD で見つける
- 広告の形（決定（未付番）。人名・PC 名を出さないため、N1-6 の「通信に出す個人情報は曲名まで」に従う）

| 項目 | 値 |
|---|---|
| サービスの型 | `_psfox._tcp` |
| インスタンス名 | `psfox-` と PC の識別子（pc_id）の先頭 8 桁（16 進）。PC のホスト名は使わない |
| ポート | SRV レコードのポート |
| TXT `v` | プロトコルの版（整数。最初は 1）。端末は知らない版の PC に接続しない |
| TXT `pid` | pc_id の先頭 8 桁。端末が保存した pc_id と前方一致で照合し、同じ PC かを選ぶ |
| TXT `pair` | ペアリングのコードを表示中なら 1、そうでなければ 0 |

- 広告は認証の代わりにならない。TXT の値は信用せず、接続後は B4-3 の固定の証明書で確かめる（N1-5）
- 端末はペアリング前、`pair=1` の PC だけを候補に出す
- mDNS は Tailscale の経路を通らない（未確認）。Tailscale では 2 番を使わず、3 番の手入力に頼る
- 広告する範囲は、起動中の IPv4 の全インターフェース（ループバックを除く）。仮想アダプタが混じるときの動作は実機で確かめる（N5-3）

### 2 MagicDNS 名の手入力（F2-3）

- 入力の形は `ホスト名` または `ホスト名:ポート`。ホスト名は MagicDNS 名（例 `pc-name.tailnet.example.invalid`）、または IPv4（例 `192.0.2.10`）。ポートを省くと既定のポート
- 入力できる文字は英数字、`.`、`-`、`:`。パスと `https://` は受け付けない（決定（未付番）。接続先を 1 つの host:port に揃えるため）
- 端末から MagicDNS 名が引けることは確認済み（2026-11-05 先生）。PC は W4（B4b）で自分の MagicDNS 名を表示し、手入力を省けるようにする（F2-3）
- 入力した宛先は、ペアリング後に端末が保存する。以後の同期では入力しない

### 3 USB テザリング時の到達（F2-4、Q2）

- 端末が DHCP で PC に IP を配る。端末から見た PC の IP は、端末のアプリが自分では確実に知れない（ARP 表を読む手段が無い。未確認）
- 決め方は mDNS と手入力の 2 段。上から試す（J12。決定（未付番）。実機で確かめる、N5-3）
  - mDNS：テザリングのリンクで広告が届けば、B4-1 の 2 番で見つかる（届くかは未確認）
  - 手入力：W4 が PC の IPv4 の一覧を出す。利用者が 1 回入力すれば、以後は 1 番で足りる。IP が変わったら、再び mDNS か手入力へ
- 端末の自動の走査（テザリングの `/24` の探索）は最初の版に持たない。実機の確認 C-5 で mDNS がテザリングのリンクを通らないと分かったときに足す（J12）
- テザリングのインターフェース名と、リンク上での mDNS の可否は端末で異なる見込み（未確認）。名前を決め打ちせず、端末が持つ接続のうち「従量制でない」「Wi-Fi でない」ものの IPv4 を使う

## B4-2 ペアリング

- 目的：コードを送らずに、両側が同じ鍵 K（B4-3 の K1、K3）を得る。LAN で PC を名乗る別の機器にコードを渡さない（review-01 の指摘 5、F2-5）
- 識別子（B3 の依頼に応える）

| 識別子 | 形 | 作る側と時期 | 用途 |
|---|---|---|---|
| device_id | 乱数 16 バイト（UUID の形で表す） | 端末。アプリの初回起動 | 署名の要求の宛先の鍵の索引。D11 の端末の識別子。入れ直すと変わる（D14） |
| pc_id | 乱数 16 バイト（UUID の形で表す） | PC。初回起動。保存は B4-6（B4b） | mDNS の `pid`、端末の保存の索引 |

### 1 方式の候補

| | A SPAKE2 | B CPace | C コードを HKDF で伸ばす |
|---|---|---|---|
| 種類 | PAKE（RFC 9382） | PAKE（CFRG の仕様。確定の状態は未確認） | 共有の秘密をコードから直接導く簡易案 |
| 受動の盗聴からの総当たり | できない | できない | 通信の 1 回分から全 100 万通りを総当たりできる |
| 能動の中間者 | 1 回の試行で 1 通りしか試せない | 同じ | 通信を 1 回分得れば、コードを割って成り済ませる |
| 部品 | Bouncy Castle の楕円曲線の演算。SPAKE2 の手順は M1（review-05 の基本設計の直し 3） | 同じ（群の選び方で変わる。未確認） | 標準の HMAC と HKDF だけ |
| 実装量 | 中 | 中 | 小 |

- 参考に挙げた SRP は、部品が JVM にあるか未確認のため候補に入れない。J-PAKE は Bouncy Castle にあるが（facts-jvm 4c）、往復が増えるため候補に入れない（J16 の b）
- 確定：A（J16 の a、review-05。Q5）。理由は、コードが 6 桁と短く、C は盗聴 1 回で割れるため。B は A と性質が同じで、仕様の状態が未確認のため A を先にする
- 部品の実体：Bouncy Castle の仕様書に SPAKE2・CPace は載らない（facts-jvm 4b）。このため点演算（P-256）だけを Bouncy Castle の実体とし、SPAKE2 の手順の組み立ては M1 に置く。RFC 9382 は Informational（facts-jvm 4a）で、試験ベクターで検算する（review-05 の基本設計の直し 3）
- 手順の実装が成り立たなければ、B を試す。どちらも使えない場合は C にせず、再判断する（J11。決定済み）
- 実装の確かめ：RFC の試験ベクターを shared のテストに入れる（N5-1）

### 2 A の手順（決定（未付番）。RFC の細部は実装時に再確認する）

- 暗号の部品の置き場（B1 が確定。手順は M1、実体は `CryptoProvider` で M3・M4 が渡す）：手順の組み立て、署名対象の文字列、鍵の導出の呼び出しは shared に置く。乱数、HMAC、HKDF、SHA-256、点演算の実体は `CryptoProvider` の形で desktop と android が渡す。テストでは固定の乱数の偽の実体を渡す（N5-1）
- 登場する値：コード（6 桁の数字）が PAKE のパスワード。識別子は device_id と pc_id。SPKI のハッシュは B4-3 の 2

| 段 | 向き | 内容 |
|---|---|---|
| 1 | 端末 → PC（P5） | device_id、端末の表示名（機種名まで）、SPAKE2 の値 X |
| 2 | PC → 端末（P5 の応答） | pc_id、SPAKE2 の値 Y。PC がコードを表示していなければ 403（`pairing_closed`）で拒否する。試行は数えない |
| 3 | 端末 → PC（P6） | 端末の確認の印 MAC_d。PAKE の鍵の確認に、双方の識別子、PC の SPKI のハッシュを付加データとして含める |
| 4 | PC → 端末（P6 の応答） | MAC_d が合えば PC の確認の印 MAC_p |
| 5 | 双方 | 両方の印が合えば成功。PAKE の共有の秘密から、HKDF で署名用の鍵 K を導く（用途の文字列は `psfox v1 request-signing`） |

- PC は P6 の印が合わなかったときに、そのコードに対する試行を 1 回数える。P5 は数えない（LAN の第三者が P5 を繰り返してコードを無効にする妨害を防ぐ。review-03 の指摘 20）。P5 の連続は B4-4 の 7 の 429 の対象にする。試行の上限は V2。V2 に達したらコードを無効にして作り直す（N1-3。review-11）
- コードの扱い：暗号論的な乱数から 6 桁を作る。使用後と V3 に達したときに無効にする（F5-4）。ペアリングのたびに作り直す
- 上限に達した後の待ち時間は V4
- 端末の入力が誤りのとき、E2 を表示する（B3 に依頼）
- 端末を入れ直すと device_id が変わる（D14）。PC は `devices` が 1 件でもあれば P5 を 403（`device_exists`）で断る（device_id の一致は条件にしない。D11、D14。review-11）。入れ直した後は PC の W3 で解除してからペアリングする。端末の S2 にも同じ案内を出す（B3 に依頼）
- 成功時：PC は device_id をキーに K を K1 へ保存し、settings.json の `devices` にも書く（P6 の成功で確定）。端末は K を K3 へ取り込み、PC の SPKI のハッシュと pc_id を K4 へ保存する
- 保存できたことを確かめるまで、成功を端末の画面に出さない。PC 側の保存に失敗したときは、P6 の応答の前に失敗を返し、端末は何も保存しない
- 端末 1 台の制約（D11）：PC に既存のペアリングがあるときの扱いは、B4b の W3 に任せる。PC は既存を残したまま新規を受け付けない（Q8 は D11 で決定済み。置き換えの操作は W3 の「解除」の後）

### 3 確認コードの見比べ（Q5）

- 用語：固定する対象は公開鍵（SPKI）のハッシュ。画面と説明書では「確認コード」と呼ぶ（旧称「指紋」。D18。利用者が入力する 6 桁は「ペアリングコード」と呼び分ける。B3 の T4 の列名は `spki_hash`、コード中の識別子は `fingerprint` のまま）
- PC の SPKI の SHA-256 のうち先頭 12 バイトを 16 進で 4 桁ずつ区切って示す（決定（未付番）。96 ビットで見比べには十分）
- PC は W4（B4b）に、端末は ペアリングの画面（B3 の S）に出す。端末の画面には、P5 の応答の時点で TLS が提示した証明書から計算した値を出す
- PAKE の付加データに SPKI のハッシュの全体を含めるため、見比べなくても中間者は成り立たない。見比べは利用者の確認の手段で、必須にしない
- 確認コードは表示だけとする。端末の保存（K3、K4）は P6 の成功で確定し、確認コードの確認の段は状態機械に置かない。違うと思えば、利用者が PC の W3 と端末の S5 の両方で解除する（案内は端末の S2 に出す）（J27。2026-11-06）

### 4 解除（F2-7）

- PC からの解除：K1 の該当の項目を消す。端末の次の要求は E2 になる
- 端末からの解除：K3 と K4 を消す。PC への通知は行わない（J15）。PC の W3 に端末が残るため、PC 側でも解除する
- どちらの解除の後も、同じ端末に戻すときは再ペアリングになる。PC だけ解除しても端末の T4 は残り、端末は S1 から S2 へ入れないので、PC の W3 と端末の S5 の両方で解除してから再ペアリングする

## B4-3 TLS と鍵 K1〜K4

### 1 TLS（N1-1、Q5）

- 全方式で同じ形。ポートは HTTPS だけ。平文の HTTP は開かない
- 証明書は自己署名。鍵の種類は ECDSA P-256（決定（未付番）。小さく、JVM の標準で扱える）。有効期間は V30
- 端末は、ホスト名の照合をしない。固定した SPKI のハッシュとの一致だけで信頼する。IP が変わる（DHCP、テザリング）ため、SAN に宛先を頼らない
- 固定する対象は、証明書全体でなく公開鍵（SPKI）のハッシュ（決定（未付番））。期限が切れたら、同じ鍵で証明書を作り直せば、再ペアリングは要らない。残りが V44 以下になったときも、同じ鍵で作り直す（X5-2）
- 鍵そのものを作り直した場合、全端末は固定の照合に失敗し、E2 になる（自動は再ペアリングまで止まる）。端末は「証明書が変わった」と表示し、再ペアリングへ誘導する。案内は「PC の W3 と端末の S5 の両方で解除してから」とする（B3 に依頼）（J28。2026-11-06）
- ペアリング前の P5 の接続では、端末は証明書を検証せず、提示された SPKI のハッシュを PAKE の付加データに入れる。他の P は固定の照合に失敗すれば切断し、E2 とする
- ただし到達確認（B4-1 の候補を順に試す段）では、固定が合わない接続先は「応えない」と同じに扱い、次の候補を試す。全候補がだめで、そのうち 1 つでも不一致があれば E2、不一致が無ければ E1（J36）。IP が別の機器に移った場合に、自動が止まらないため

### 2 鍵の一覧

| K | 中身 | 持つ側 | 保管場所 | 備考 |
|---|---|---|---|---|
| K1 | 端末ごとの署名用の共有の鍵 K（32 バイト）。device_id が索引 | PC | DPAPI で暗号化したファイル `secrets.bin`（`%APPDATA%\playlist-sync-fox\`）。利用者ごとの保護 | D11 の将来の複数台に備え、端末ごとに 1 項目（D11、review-05 の基本設計の直し 2） |
| K2 | PC の証明書の秘密鍵（PKCS#8）と証明書 | PC | 秘密鍵は K1 と同じ `secrets.bin`。証明書は `%APPDATA%\playlist-sync-fox\tls-cert.pem`（B4-6、B4b） | 証明書は公開してよい |
| K3 | 署名用の共有の鍵 K | 端末 | Android Keystore。HMAC-SHA256 の鍵として取り込む。以後は取り出さず、署名を Keystore に依頼する | 取り込める形は 32 バイトの HMAC-SHA256 の鍵（B3 の依頼に応える） |
| K4 | 固定する PC の SPKI のハッシュと pc_id | 端末 | アプリの内部領域（Room か設定。B3） | 秘密ではない。改ざんされると接続先が変わるため、内部領域に限る |

- K1 と K2 は、現在の Windows のユーザーだけが復号できる（DPAPI は OS が利用者ごとに保護する）。別ユーザーのログオンからは復号できない
- DPAPI は JNA の `Crypt32Util` に束縛がある（review-05 の J17。根拠は facts-jvm 5a：資格情報マネージャーの束縛は見当たらない）。呼ぶ部品の追加は B1 に依頼する。`secrets.bin` の中身の形は詳細設計に任せる
- 平文のファイルに鍵を置かない（N1-4）。ログにも出さない（N1-6、B4-6）
- 自動バックアップの対象から K3 と K4 を外す（B3 に依頼。Keystore の鍵は復元されないため、復元後は再ペアリングが要る）
- Q5 は「PC は DPAPI」としていた。資格情報マネージャーに寄せる案（第 2 稿）は、JNA に束縛が見当たらないため取り下げ、Q5 の原案の DPAPI に戻す（J17 の a。review-05 の基本設計の直し 2）

## B4-4 API P1〜P8

### 1 ルートの一覧

- 共通：HTTPS、パスの先頭に版 `/v1`。本文は JSON（P2 の曲の本文を除く）。要求の本文の長さの上限は V31
- 名前の `X-Psfox-*`、`_psfox._tcp`、`PSFOX1` は Q1（正式名）で変わる。Q1 の決定で名前を揃える

| P | 名前 | メソッドとパス | 署名 | 用途 |
|---|---|---|---|---|
| P1 | マニフェストの取得 | `POST /v1/manifest` | 要 | F3-1。本文は端末が選んだプレイリストの ID の配列（下の 2）。B2 のマニフェストを返す。2026-11-07 から GET ではなく POST（D15） |
| P2 | 曲の取得 | `GET /v1/tracks/{persistent_id}` | 要 | F3-4。Range 対応 |
| P3 | 到達確認 | `POST /v1/digest` | 要 | 要求の本文は P1 と同じ ID の配列。応答の本文は `content_digest` だけ。PC は要求のたびに、実在の確認を含めてマニフェストを組み（X2-4 の 7・8 と実在の確認の順）、その `content_digest` を返す。自動起動の到達確認（D13）と、差分なしの判定（N2-5） |
| P4 | 結果の報告 | `POST /v1/reports` | 要 | B2-8 の報告の項目を PC に渡す。W3 の表示に使う |
| P5 | ペアリングの開始 | `POST /v1/pairing/start` | 不要 | B4-2 の段 1・2 |
| P6 | ペアリングの確認 | `POST /v1/pairing/confirm` | 不要 | B4-2 の段 3・4 |
| P7 | プレイリストの一覧 | `GET /v1/playlists` | 要 | F3-11。端末が選ぶためのプレイリストの木を返す（下の 8）。2026-11-07（D15） |
| P8 | 進み具合の知らせ | `POST /v1/progress` | 要 | F5-3。端末が同期の進み具合を PC へ知らせる（下の 5b）。2026-11-07（D22） |

- P5・P6 を P1〜P4 の続きに採番した。署名の鍵ができる前の経路のため、署名を要さない。コードを表示していない間は、403（E2、`pairing_closed`）で拒否する

### 2 P1 マニフェスト（B2 の依頼）

- 要求の本文：`{"playlist_ids":["<大文字 16 桁の 16 進>", …]}`（D15）。署名の対象（本文の SHA-256 が署名の 7 行目。6）。PC は境界で検査する：本文の大きさは V31（413）、JSON の形と各 ID の書式（大文字の 16 桁の 16 進）、個数は V54 まで（違えば 400）。重複は 1 つにまとめる。空の配列は有効で、空のマニフェストを返す。ID が XML に無ければ `unresolved_playlists` に入る（B2-4）
- 応答の本文は B2 のマニフェストの形。`content_digest` を含める。圧縮は要る（決定（未付番）。数千曲で 1 回に数 MB になりうる）。端末が `Accept-Encoding: gzip` を付けたときだけ圧縮する
- XML が読めない間は 503（E4）。端末は前回のマニフェストで差分を作らず、同期を止めて E4 を示す
- 選んだ ID が 0 件の要求には、空のマニフェストを返す（PC は選択を持たない。端末は選択が空なら要求しない。F3-11）
- P2 の曲の表（J31）は、この要求の選択で作ったものに置き換える。選んでいない曲は P2 で配らない（端末は 1 台の前提。D11）

### 3 P2 曲の取得（B3 の依頼）

- 指定は `persistent_id`（16 桁の 16 進）だけ。パスやファイル名を受け取らない（N1-7）。書式が違えば 400。マニフェストに無い ID は 404（E5）
- 端末は、問い合わせの `size`、`modified_at` を新規も再開も付ける。新規と置き換えはマニフェストの値、再開は T5 に保存した値を付ける
- PC は次を順に確かめる。1 つでも違えば 409（E8）で、本文を送らない
  - 問い合わせの値が、PC の最後に作ったマニフェストの曲の表（M3 が持つ）の値と一致する（J31）
  - 実ファイルの大きさがマニフェストの `size` と一致する（B2 に依頼。実ファイルの更新日時を使うかは B2）
- ファイルが無ければ 404（E5）
- `Range: bytes=N-` を受ける。再開のたびに新しい署名で要求し直す。範囲が大きさを超えれば 416。端末は 416 を受けたら最初から取り直す（N2-2）
- 応答のヘッダ：`Content-Length`、`Accept-Ranges: bytes`、206 のとき `Content-Range`。加えて次の 2 つを付ける（B3 の依頼）

| ヘッダ | 意味 |
|---|---|
| `X-Psfox-Size` | ファイル全体の大きさ（バイト） |
| `X-Psfox-Modified-At` | マニフェストの `modified_at`（形は B2） |

- 端末は応答の `X-Psfox-Size` と `X-Psfox-Modified-At` を検査する。新規と置き換えはマニフェストの値と、再開は T5 の値と比べる。違えば E8 と同じ扱い

### 4 P3 到達確認（D13）

- 要求の本文は P1 と同じ（選んだ ID の配列。検査も同じ。digest が選択に依存するため）。応答の本文は `content_digest` だけ。曲名やプレイリスト名を含めない。PC は digest を出すために、要求のたびに XML の読み直しと実在の確認（X2-4 の 7・8 と実在の確認の順）を含めてマニフェストを組む。最後の P1 の値を返さない（返すと端末が記録した値と常に同じになり、変化を見落とす）。P2 の曲の表（J31）は P3 では置き換えない
- 前回の同期（`content_digest` を持つ最新の同期。X3-2）が `success` のとき、端末がその値と同じなら、自動は P1 を省いて終える（N2-5）。手動は P1 を取り、前回の同期（同じ定義）が `success` で差分が空なら m3u8 の書き出しと消す処理を省いて T3 だけ記録する（B3-3。J37）
- 端末は P3 の応答を V53 まで待つ。接続の確立の待ち V29 とは別に数える（J47）
- 自動起動では、P3 が成功すれば到達したとみなす。P3 が失敗を返したときは、その接続先で止め、次の接続先を試さずに E2・E4 を T3 に残す（B2-7 の例外。手動も同じ。J45）。P3 の 500 も E なしで同じく T3 に残す（J45）。接続先に届かないときは何もせず終わる（D13）

### 4b P7 プレイリストの一覧（F3-11、D15）

- 応答：`{"playlists":[ノード, …]}`。ノードは `persistent_id`、`name`、葉なら `track_count`（曲数）、フォルダなら `children`（ノードの配列）。フォルダは端末でも開閉できる木の形で返す。葉が選べるもの。組み込みの一覧（`Master`、`Distinguished Kind`）は出さない（B2-1）。曲のパスと曲名は含めない（N1-6）
- 要求の時に XML の更新日時を確かめて読み直し（B2-3）、読めなければ 503（E4）。曲の表は置き換えない。本文は無い（GET）。圧縮は P1 だけ
- 一覧の大きさは、プレイリストの数に比例して数百 KB に収まる見込み。端末は受信側に上限を置かない

### 5 P4 結果の報告

- 本文は B2-8 の報告の項目（件数と日時の要約）だけ。曲名とパスは含めない（N1-6）
- PC は W3 に最後の同期（日時、結果）として表示する（F5-3）。応答は 204
- 報告の失敗は同期の結果に影響しない。端末は、1 回の同期で 1 度、P3 が通った後に再送する。未報告の行は `started_at` の昇順で送り、PC は保存済みより古い報告で最後の同期を上書きしない（X5-1）。成功するまで次の同期で試す（X6-3）

### 5b P8 進み具合の知らせ（D22）

- PC は端末が取りに来る曲を先に知らない（差分は端末が決める）。全体の割合を PC に出すため、端末が知らせる
- 要求の本文：`{"stage":"transfer","done_tracks":9,"total_tracks":17,"done_bytes":159697715,"total_bytes":298948198}`。`stage` は SyncProgress の `stage`（X6-3）の値のうち `finished` を除く 6 つ。数はすべて 0 以上の整数。`done_bytes` は転送中の曲の受け取った分を含む。曲名、ID、パスは含めない（N1-6）
- PC は境界で検査する：JSON の形、`stage` の値、数が 0 以上（違えば 400）。`done` が `total` を超えても拒まない（表示で 100% に切る）。応答は 204
- 端末は、P3 が通った後（X6-3 の 2）から P4 の前（X6-3 の 11）まで、SyncProgress を更新したときに送る。間隔は V28 以上。`stage` が変わったときは間隔を待たない。送っている途中の要求があれば、その回は送らない（待たない、溜めない）
- 失敗しても同期は止めない。再送しない。T3 に残さない。応答の待ちは V29
- PC はメモリにだけ持つ（保存しない）。P4 を受けたとき、または最後の P8 から V56 の間更新が無いときに消す
- 署名の失敗の連続（7 の 429）は失敗だけを数えるので、成功する P8 を定期的に送っても数に入らない

### 6 署名（N1-2）

- 鍵：B4-3 の K。device_id で PC が鍵を引く
- 署名：HMAC-SHA256。出力は base64url
- 署名対象の文字列（決定（未付番）。行の区切りは LF）

| 行 | 内容 |
|---|---|
| 1 | 固定の `PSFOX1` |
| 2 | メソッド（大文字） |
| 3 | パスと問い合わせ（送った文字列のまま） |
| 4 | タイムスタンプ（秒） |
| 5 | 一回限りの値（nonce） |
| 6 | device_id |
| 7 | 本文の SHA-256（16 進。本文が空なら空の列の値） |

- 要求のヘッダ

| ヘッダ | 内容 |
|---|---|
| `X-Psfox-Device` | device_id |
| `X-Psfox-Timestamp` | UTC のエポック秒 |
| `X-Psfox-Nonce` | 乱数 16 バイトの base64url |
| `X-Psfox-Signature` | 上の署名 |

- `Range` は署名しない。TLS で守られており、再開のたびに新しい nonce で署名し直すため

### 7 再送防止

- PC は、タイムスタンプが現在から V12 を超えて離れる要求を拒否する（401、E2、`detail=clock_skew`。端末は「端末と PC の時計が違う」と案内する）
- 同じ device_id と nonce の組を、許容の 2 倍の時間だけメモリに保持し、重なれば拒否する（401、E2、`detail=replay`）
- PC の起動より前のタイムスタンプは、V12 の幅の内でも拒否する（401、E2、`detail=clock_skew`）。再起動で nonce の記録が消えても、前の通信の再送を通さないため（review-05 の基本設計の直し 14、J29。2026-11-06）
- 署名の比較は一定時間で行う。未登録の device_id は、署名が合わない場合と同じ応答にする（401、E2）。区別を外に出さない
- 署名の失敗と P5 の連続は、接続元ごとに数える。V43 の回数に達した接続元は、V32 の間、429 を返す（review-05 の基本設計の直し 15）

### 8 応答の印と E の対応

- 失敗の応答は本文に `{"error":"E<番号>","detail":"…"}` を持つ。端末は E の番号で表示を決める（F6-2）

| HTTP | E | 場面 |
|---|---|---|
| 200、206 | なし | 成功 |
| 204 | なし | P4、P8 の成功 |
| 400 | なし | 書式の誤り（ID、ヘッダ、P1・P3 の本文の JSON・`playlist_ids` の形と個数（V54）、P8 の本文）。端末の不具合として扱う。P8 の 400 は同期を止めない（5b） |
| 401 | E2 | 署名が合わない、未登録の端末、時刻のずれ（起動前のタイムスタンプを含む。`clock_skew`）、再送、ペアリングの試行の誤り |
| 403 | E2 | コードを表示していない（`pairing_closed`）、試行の上限（`pairing_locked`）、`devices` が 1 件でもある（device_id の一致は問わない。`device_exists`） |
| 404 | E5 | マニフェストに無い ID、ファイルが無い |
| 404 | なし | ルート不明（既知でないパス。`{persistent_id}` は `/` を含まない 1 要素のため、`/` を含む値もここに入る） |
| 405 | なし | GET・HEAD 以外のメソッドで P2 を呼んだ（`PartialContent` が受けない。facts-jvm 7a） |
| 409 | E8 | `size`・`modified_at` の不一致 |
| 413 | なし | 要求の本文が V31 を超える |
| 416 | なし | Range の誤り。端末は最初から取り直す |
| 429 | E2 | 署名の失敗の連続 |
| 500 | なし | 想定外の失敗。端末の不具合ではなく PC の不具合として扱い、同期を止めて結果に残す |
| 503 | E4 | XML が読めず、マニフェストを作れない（P1、P3。J45）。P2 で、PC の再起動などで曲の表が空のとき（J31） |

- E1、E3、E6、E7、E9 は端末の側で判定し、PC は返さない。E1 は接続の失敗（候補の全滅）。証明書の固定の不一致は E2（J28）。ただし到達確認で候補を順に試す間は、不一致も「応えない」と同じに扱う（B4-3 の 1。J36）
- 自動の抑止（B2-7）の「前回が E2 なら再ペアリングまで止める」の対象は、`detail` なしの 401 と証明書の固定の不一致（鍵の不一致）に限る。`clock_skew`・`replay`・429 では止めない（J35）
