## B2 ライブラリの読み取りと同期

### B2 の書く項目

- B2-1 XML の読み取り：plist の構造、取る項目の表、スマートプレイリストの扱い、除外するプレイリスト
- B2-2 ファイルが無いトラックの除外：`file://` の復号、実在の確認、除外の理由、結果への一覧（F1-10）
- B2-3 XML の監視と読み直し：変更の検知、書き込み途中の扱い、古さの警告
- B2-4 マニフェストの形：項目の表、曲の同一性と変更の検知（Q10）
- B2-5 差分の計算：集合の規則、4 種の判定、消す規則
- B2-6 転送の手順：1 曲ずつ、再開、失敗の種類 E1〜、同期状態を更新するタイミング
- B2-7 自動起動：WorkManager の制約、PC への到達確認、手動との優先
- B2-8 同期の結果の形：件数、容量、除外の一覧、再生できない形式の一覧

### B2-1 XML の読み取り

F1-1、F1-2、F1-4、F1-5、F1-9、N3-1。

前提：

- 入口は `iTunes Music Library.xml` だけ。COM は使わない（D1）
- XML の既定の場所（`%USERPROFILE%\Music\iTunes\`）は Apple の文書で確かめられていない（facts-jvm 1i）。実物（iTunes 12.13.7.1）はこの場所だった（2026-11-06 の実物の確認）。設定画面での指定を優先し、既定の場所は候補にとどめる（B4）。XML の書き出しは iTunes の設定「iTunes ライブラリ XML を他のアプリケーションと共有」（Edit > Preferences > Advanced）で切り替わる。既定の状態は Apple の文書に無い（1j）。案内文は B4-5
- plist は Apple の XML の書式で、最上位は辞書。キー名と型は公式に網羅した文書が見つからない。下の表はキー名の通例による案で、実物で確かめる項目に「（iTunes 12.x の実物で確かめる）」と添える。2026-11-06 に実物で確かめ、結果は末尾の「実物の確認」に置いた
- 数万トラックを読むので、全体を木にせず、先頭から順に読む方式にする（N2-3。技術は詳細設計）

plist の構造：

| 位置 | 型 | 中身 |
|---|---|---|
| 最上位の辞書 | dict | ライブラリ全体 |
| `Library Persistent ID` | string | ライブラリの識別子。16 桁の大文字の 16 進（2026-11-06 の実物の確認） |
| `Date` | date | XML を書き出した時刻。診断のログにだけ使う |
| `Application Version` | string | 診断のログにだけ使う |
| `Music Folder` | string | 使わない。トラックの場所は各トラックの `Location` で決める |
| `Tracks` | dict | キーは Track ID の文字列、値はトラックの辞書 |
| `Playlists` | array | プレイリストの辞書の並び |

トラックから取る項目（F1-4、F1-9。再生回数と評価は読まない）：

| キー | 型 | 用途 | 備考 |
|---|---|---|---|
| `Track ID` | integer | 読み取りの中で `Playlist Items` と突き合わせる | 書き出しのたびに変わりうる。外へ出さない。マニフェストにも書かない |
| `Persistent ID` | string | 曲の同一性（F3-2）。大文字の 16 桁の 16 進に揃える | 変わらない前提。実物では終了と再起動をまたいで全件不変だった（2026-11-06 の実物の確認）。無いトラックは除外（B2-2） |
| `Track Type` | string | `File` 以外（配信、URL）は除外 | 実物では全件 `File`。ほかの値は未確認（2026-11-06 の実物の確認） |
| `Location` | string | 曲のファイルの場所。`file://localhost/` で始まる URL で、percent-encoding を含む | 復号は B2-2 |
| `Size` | integer | 読み捨てる | 同期の判定には実ファイルの値を使う（B2-4 の「曲の同一性と変更の検知」）（review-05 の基本設計の直し 9） |
| `Date Modified` | date | 読み捨てる | 同期の判定には使わない。実物では、コメントの変更で値が変わり、元に戻しても元の値には戻らなかった（Q10。2026-11-06 の実物の確認）（review-05 の基本設計の直し 9） |
| `Total Time` | integer | 長さ（ミリ秒）。m3u8 の `#EXTINF` に使う | 無ければ空 |
| `Name` | string | 曲名 | 無ければ空 |
| `Artist` | string | アーティスト | 無いことが多い。無ければ空 |
| `Album` | string | アルバム | 無ければ空 |
| `Album Artist` | string | アルバムのアーティスト | 無ければ空。Artist での補いは B3 の保存先の規則 |
| `Track Number` | integer | トラック番号 | 無ければ空 |
| `Disc Number` | integer | ディスク番号 | 無ければ空 |
| `Kind` | string | 形式の名（例：保護された AAC の名） | 再生できない形式の判定に使う（B2-8） |
| `Protected` | boolean | 保護（DRM）の有無 | 無ければ偽 |

- 欠けた項目は空で持ち、補う処理は M2 に置かない。保存先の規則での補いは B3 が決める
- 上の表にないキーは読み捨てる。キーが増えても壊れない

プレイリストから取る項目（F1-5）：

| キー | 型 | 用途 | 備考 |
|---|---|---|---|
| `Playlist Persistent ID` | string | プレイリストの同一性。PC の選択の保存（B4）と m3u8 の対応（B3）の鍵 | 大文字の 16 桁の 16 進 |
| `Name` | string | 表示と m3u8 のファイル名の元 | 同名がありうるので鍵にしない |
| `Playlist Items` | array | 順序付きの `Track ID` の並び | 空のプレイリストでは無い場合がある。同じ曲が 2 回あってもそのまま残す |
| `Master` | boolean | ライブラリ全体を表す一覧の印 | 除外 |
| `Distinguished Kind` | integer | ミュージック、映画、ポッドキャストなど、iTunes が持つ特別な一覧の印 | 付いているものは除外。値を固定の表で持たず、キーの有無で判定する（起動中だけ出る Genius の値 26 があり、組み込みの数が変わるため。2026-11-06 の実物の確認） |
| `Folder` | boolean | プレイリストをまとめるフォルダ | 除外。中の一覧は `Parent Persistent ID` を持ち、個別に選べる |
| `Parent Persistent ID` | string | 親のフォルダの `Playlist Persistent ID` | 入れ子の表示（W）に使う。B4 へ渡す |
| `Smart Info`、`Smart Criteria` | data | スマートプレイリストの条件 | 読まない（F1-5） |

- スマートプレイリストは、`Playlist Items` に入っている展開済みの並びをそのまま使う。条件は解釈しない。XML を書き出した時点の結果で、書き出し後の変化は次の書き出しまで反映されない
- 除外の規則：`Master` が真、`Distinguished Kind` を持つ、`Folder` が真のどれかに当たるプレイリストは、選択の一覧に出さない。決定（未付番）。根拠：F1-5 は利用者が作った一覧の同期を想定し、ライブラリ全体や特別な一覧は曲数が多く、同期の対象にすると容量を使い切るため。選べるようにするかは J15（B2 の旧 J2。a。選べない）
- `Playlist Items` の `Track ID` は、読み取りの中で `Tracks` の `Persistent ID` に置き換える。`Tracks` に無い Track ID は落とし、件数を診断のログに残す
- 読み取りの結果は「トラックの一覧」と「プレイリストの一覧（Persistent ID の並び）」の 2 つ。M2 の出力はこの形で、ファイルの実在の確認の前の状態

### B2-2 ファイルが無いトラックの除外

F1-6、F1-10、N1-7、N3-5。

`file://` の復号（M2。純粋な関数）：

| 手順 | 規則 |
|---|---|
| 1 | 先頭が `file://` でなければ、場所が無いものとして扱う |
| 2 | `file://` の後ろから、最初の `/` までを権限部とする。権限部が `localhost` か空なら、ローカルのパスとする |
| 3 | 権限部が別のホスト名のとき、`\\ホスト名\共有名\…` の形に直す。iTunes がこの形を書くかは未確認（iTunes 12.x の実物で確かめる）。直せないときは「復号不能」にする |
| 4 | 権限部の後ろのパスを、UTF-8 として percent-decoding する。`+` は空白にしない（そのまま `+`）。復号した結果が UTF-8 として不正なら「復号不能」にする |
| 5 | 手順 2 でローカルのパスとしたときだけ、復号後のパスが `/X:/…`（X はドライブ文字）の形なら、先頭の `/` を外す。ドライブ文字が無い（Mac のパスなど）ときは「復号不能」にする。手順 3 で `\ホスト名\共有名\…` に直したものには当てない（review-05 の基本設計の直し 8） |
| 6 | 区切りの `/` は、PC のファイルの API に渡す前に `\` へ直す |

- XML の文字参照（`&amp;` や `&#38;`）は plist の読み取りの段で戻る。復号の入力は戻した後の文字列
- 日本語名と記号（`#`、`%`、`&`、空白）を含むパスは、手順 4 で戻る。テストの入力に入れる（N5-1）

実在の確認（M3。純粋でない）：

- 確認の対象は、選んだプレイリストに入るトラックだけ。ライブラリ全体は確認しない（数万件の確認を避けるため。N2-3）
- 確認の時点はマニフェストを作るとき（B2-4）。結果を長く持ち越さない
- 確認の内容：通常のファイルとして存在する、読み取れる。その場でサイズと最終更新日時を取る。取った値がマニフェストの値になる（B2-4）

除外の理由（結果の一覧に出す。F1-10、F6-2）：

| 理由 | 検出の位置 | 扱い |
|---|---|---|
| 場所なし | `Location` が無い、または `Track Type` が `File` でない（iCloud の未ダウンロード、配信の曲） | 除外。E5 の細目 |
| 復号不能 | 上の手順 1、3、4、5 の失敗 | 除外。E5 の細目 |
| 実在しない | 復号したパスにファイルが無い | 除外。E5 の細目 |
| 読めない | ファイルはあるが読み取れない（権限、他のプロセスの占有） | 除外。E5 の細目 |
| ID 無し | `Persistent ID` が無い | 除外。E5 の細目ではなく、XML の不備として、`persistent_id` を空のまま除外の一覧に載せる（T6 は ID 無しを許す。J23。2026-11-06） |
| 保護 | `Protected` が真、または `Kind` が保護された形式 | 転送しない印を付ける（J8）。除外の一覧には載せない。再生できない形式の一覧（B2-8）にだけ出す（review-05 の基本設計の直し 10） |

- 保護の曲は除外ではない。`tracks` に残し、`protected` を真にして印を付ける。端末はこの印の曲を転送しない（B2-8 の規則 1）。除外の一覧と再生できない形式の一覧に二重に載せない
- 除外したトラック（保護を除く）は、マニフェストの「除外の一覧」に載せる（曲名、アーティスト、理由。パスは載せない。N1-6）。PC のログにはパスを出してよい（N1-6）
- 除外したトラックは、プレイリストの並びからも外す。m3u8 に載せない曲を作らないため
- 除外の一覧は、端末の同期の結果に写して利用者に見せる（B2-8）
- 同期の最中にファイルが消えた場合は、取得の段で E5 として検出する（B2-6）

### B2-3 XML の監視と読み直し

F1-7、F1-8、N2-3、F5-6。

監視（M3）：

| 項目 | 規則 |
|---|---|
| 対象 | XML のあるフォルダ。ファイル単独ではなくフォルダを監視し、ファイル名で絞る |
| イベント | 作成と変更の両方を受ける。iTunes 12.x は一時ファイルへ書いて、改名で置き換える（2026-11-06 の実物の確認）。XML の名前は改名で現れ、置き換えの数ミリ秒は XML が無い。直接書き換える書き方にも備えて、作成と変更の両方を受けるのは変えない。Java の WatchService で改名がどう見えるか（削除と作成か）は未計測 |
| 安定の待ち | 最後のイベントから V18（XML 安定待ち）の間、サイズと更新日時が変わらなければ、書き込みが終わったとみなして読む |
| 起動時 | 起動したときに 1 回読む |
| 要求の時 | 端末からマニフェストの要求を受けたとき、XML の更新日時が読み込み済みの値と違えば、読み直してから応える。監視の取りこぼし（ネットワーク上のフォルダなど。未確認）に備える |

読み直し：

- 読めなかった（XML の構文が壊れている、ファイルが開けない、置き換えの途中でファイルが無い）ときは、V6（XML 読み直しの回数・間隔）の間隔で待って読み直す。回数を超えたら読み取りを諦める
- 諦めたときは、最後に読めた結果（あれば）を残し、画面に警告を出す（B4 の W）。端末への応答では E4（XML 不可）を返す。最後に読めた結果で応えるかは、F3-3 の消す規則への影響が大きいので、応えない（決定（未付番）。根拠：古い結果で「消す」差分を作ると、後から直った XML と食い違う）
- 読み取りの途中でさらにイベントが来たら、読み終えた後にもう 1 回読む

古さの警告（F1-8、F5-6）：

- XML の更新日時が V5（古さの基準）より前のとき、PC の画面に警告を出す
- iTunes 12.x は、ライブラリが変わったときと終了のときに XML を更新する（2026-11-06 の実物の確認。操作から更新までの秒数は未計測）。XML の作成日時は置き換えで前のファイルの値を引き継ぐので、新旧の判定には更新日時を使う。更新日時が古いだけでは誤りとは限らない。警告の文は「XML の更新が古い」とし、原因を断定しない
- マニフェストに XML の更新日時を入れる（B2-4）。端末は結果の画面に出してよい（B3）

### B2-4 マニフェストの形

F3-1、F3-2、F4（B3 への材料）、N1-7。Q10。

マニフェストは、PC が最後に読んだ XML と、選んだプレイリストから作る 1 つの文書。型は M1 に置き、kotlinx.serialization の形式で運ぶ（B1）。

最上位の項目：

| 項目 | 型 | 意味 |
|---|---|---|
| `format_version` | integer | マニフェストの版。互換のない変更で増やす。端末が知らない版なら、E8 ではなく更新を促す表示にする（B3） |
| `generated_at` | UTC の日時 | 作成の時刻 |
| `library_id` | string | ライブラリの識別子。XML の `Library Persistent ID`。無いときは PC が最初に作って保存した乱数（保存は B4）。暫定 |
| `xml_modified_at` | UTC の日時 | 読み込んだ XML の更新日時。古さの表示に使う |
| `content_digest` | string | 下の 3 つの一覧の内容の指紋。内容が同じなら同じ値。到達確認の応答に載せる（B2-7） |
| `tracks` | array | 選んだプレイリストに入るトラックの集合（重複なし）。下の表 |
| `playlists` | array | 選んだプレイリストの定義。下の表 |
| `unresolved_playlists` | array | 選んだが XML に無いプレイリストの Persistent ID と最後に知っていた名前 |
| `excluded` | array | 除外したトラック（B2-2）。曲名、アーティスト、理由 |

トラックの項目（`tracks` の要素）：

| 項目 | 型 | 意味 |
|---|---|---|
| `persistent_id` | string | 曲の同一性の鍵。大文字の 16 桁の 16 進 |
| `size` | integer | 実ファイルのバイト数（B2-2 の実在の確認で取った値） |
| `modified_at` | integer | 実ファイルの最終更新日時（UTC、ミリ秒） |
| `file_name` | string | 元のファイル名（拡張子を含む。ディレクトリは含まない）。用途は診断（review-05 の基本設計の直し 13） |
| `extension` | string | 拡張子（小文字） |
| `name`、`artist`、`album`、`album_artist` | string | メタデータ。空を許す |
| `track_number`、`disc_number` | integer | 空を許す |
| `duration_ms` | integer | 長さ。空を許す |
| `kind` | string | `Kind` の値 |
| `protected` | boolean | `Protected` の値 |

- 要件の文言の「相対パスの候補」は、PC が決めず、上の材料（`album_artist`、`artist`、`album`、`name`、`extension`、`persistent_id`）だけを渡す。`disc_number`、`track_number`、`file_name` は保存先の計算に使わず、表示と診断のために持つ（B3-1）。端末が M1 の関数で相対パスを計算し、マニフェスト内の衝突も端末が解く（J7、a。B3-1）。規則が 1 か所になり、PC に端末の衝突が見えない問題も無いため
- 絶対パスと `Track ID` は載せない（N1-6、N1-7）

プレイリストの項目（`playlists` の要素）：

| 項目 | 型 | 意味 |
|---|---|---|
| `persistent_id` | string | `Playlist Persistent ID` |
| `name` | string | 名前 |
| `track_ids` | array | 順序付きの `persistent_id` の並び。同じ曲の重複を許す。除外したトラックは入れない |

選択の情報：

- 選んだプレイリストは、`playlists` に入っているものそのもの。別の選択の欄は持たない（二重の持ち方による食い違いを避ける）
- 選んだが XML に無いもの（iTunes で消した）は `unresolved_playlists` に入れる。端末は、その一覧の m3u8 を消さない。曲は、未解決が 1 件でもあれば「消す」を確認が要る扱いにする（B2-5。J24。2026-11-06）。差分の入力に曲とプレイリストの対応が無く、未解決の一覧の曲だけを消さない形にはできないため。選択を外すのは利用者の操作（B4 の W）
- 選択の保存は PC が持つ（F6-3、B4）。端末へは結果だけを渡す

曲の同一性と変更の検知（Q10）：

| 判定 | 規則 |
|---|---|
| 同一 | `persistent_id` が同じなら同じ曲 |
| 変更あり | 同じ曲で、`size` か `modified_at` が、端末が記録した値と違う |
| 値の出どころ | どちらも PC の実ファイルから取る。XML の `Size` と `Date Modified` は使わない。XML の値は iTunes の記録で、実ファイルとずれうる |
| 見逃す場合 | 内容が変わったが、サイズも更新日時も同じ（更新日時を戻す操作）。認める |
| 誤って検知する場合 | 内容は同じで更新日時だけ変わる（コピーし直し）。置き換えが 1 回増えるだけで、害は転送量に限る |
| ハッシュ | 最初の版では持たない。トラックの項目に `content_hash`（空を許す）を足せる形にし、足したときは端末が記録に持つ。`format_version` を増やさず、空の項目の追加で済ませる |

- 結論は節末の「B2 の Q の結論」

規模の見積もり（概算）：1 トラックを 400 バイト前後とすると、数千曲で数百 KB から数 MB。圧縮は gzip。端末が `Accept-Encoding: gzip` を付けたときだけ（B4-4）

### B2-5 差分の計算

F3-3、F3-5、N2-4、N2-5、D9、D14。

差分は端末が、マニフェストと自分の同期状態（B3 の表 T）から M1 の関数で計算する。入力は 3 つ。

| 入力 | 中身 |
|---|---|
| マニフェストの `tracks` | 選んだプレイリスト全体の曲の集合（重複なし） |
| 同期状態の曲の記録 | 自分が置いた曲：`persistent_id`、`size`、`modified_at`、置いた場所（B3） |
| 端末のファイルの有無 | 同期状態にある曲のファイルが、置いた場所に今あるか（B3 が調べて渡す。M1 は調べない） |

4 種の判定（足す、置き換える、消す、変更なし）：

| 種 | 条件 | 動作 |
|---|---|---|
| 足す | マニフェストにあり、同期状態に無い。または、同期状態にあるがファイルが無い | 取得して置く。ファイルが無い場合の補充を「足す」に含める |
| 置き換える | マニフェストと同期状態の両方にあり、`size` か `modified_at` が違う | 取得して、置いた場所のファイルを替える。置き場所は動かさない |
| 消す | 同期状態にあり、マニフェストの `tracks` に無い | 端末のファイルを消し、同期状態の記録も消す |
| 変更なし | 両方にあり、`size` と `modified_at` が同じで、ファイルがある | 何もしない |

- 保護付き（`protected` が真、または `m4p`）の曲は 4 種のどれにも数えず、転送しない曲として別に出す（B2-8 の規則 1。X3-2 の `unplayable`）
- 集合の取り方（F3-3）：プレイリストごとではなく、選んだプレイリスト全体の集合で比べる。1 曲が複数のプレイリストに入っていても、1 件として数える。消すのは、選んだどのプレイリストにも入らなくなった曲だけ
- 消す対象は、同期状態にある曲に限る（D9、F3-5）。端末にあっても同期状態に無い曲は、判定に入れない。入れ直しの後は同期状態が空なので、以前に置いた曲は「消す」にならず、「足す」の側で衝突として B3 が扱う（D14）。消すときの同意の画面は B3
- 置き場所の移動は判定しない。メタデータが変わり、保存先の規則を当てた結果が変わっても、置いた場所は動かさない。m3u8 は置いた場所を参照する（B3）
- プレイリストの差分：端末は m3u8 をすべて作り直す（F4-4。変わったときに作り直すと読む。差分が空で `content_digest` が前回の完了と同じときは作り直しを省く。下の「差分が空のとき」。J37）ので、プレイリストの差分は計算しない。同期状態にあって、マニフェストの `playlists` にも `unresolved_playlists` にも無いプレイリストの m3u8 は消す（自分が書いたものに限る。B3）
- 別のライブラリへの付け替え：同期状態に記録した `library_id`（B3 の表 T3）がマニフェストの値と違うとき、「消す」の一覧は計算して返し、確認が要る扱いにする。別の PC か別のライブラリに付け替えると、全部の曲を消す差分になるため。手動は一覧の件数を見せて承認を受け、承認したときだけ実行し、記録の `library_id` を新しい値に更新する。自動は「消す」を飛ばす（J25。2026-11-06）。「消す」が 0 件のときは承認の機会が無いため、確認なしで記録の `library_id` を新しい値にする。Q9（複数の PC は未決）に関係する
- 消す件数の確認（全消しの防止）：「消す」が V20（消す件数の確認の閾値）を超えるとき、同期状態の曲の全部に当たるとき、`library_id` が違うとき、未解決のプレイリストが 1 件でもあるときは、確認が要る扱いにする（J9、a。J24）。要否は M1 が判定する（X3-2）。手動は、実行の前に画面で利用者へ確認する。XML は正しいがプレイリストを空にした場合（選択が 0 件の場合を含む）でも、全部を消すのは意図かどうかを聞くため。手動の確認を取り消したときは、「消す」だけ飛ばして同期を続ける（J26。2026-11-06）。自動は画面を出せないので、確認が要る扱いのときだけ「消す」を飛ばし、通知で S4 へ誘導する。確認が要らない（許可の）ときは、自動でも「消す」を実行する
- 順序：足す、置き換える → m3u8 の書き出し → 消す。消すは最後にする。途中で止まっても、曲を失わないため
- 容量の判定（N2-4）：同期の前に、「足す」と「置き換える」の `size` の合計と端末の空き容量を比べる。置き換えは新しい `size` を数える（一時ファイルを置く間、古いファイルと両方ある）。消す分は差し引かない（安全側）。足りないとき、同期を始めずに E3 と不足分を表示する
- 差分が空のとき（N2-5）：`content_digest` が前回の完了と同じなら、マニフェストの取得の後、m3u8 の書き出しと「消す」の処理を省き、T3 だけ記録して終わる（手動も同じ。自動で B2-7 の抑止に当たるものは T3 に残さない。B3-3。J37）。`content_digest` が違えば、差分が空でも m3u8 は作り直す（プレイリストの定義が変わりうるため）
- 同期の途中の選択の変更：P2 は最後の P1 の曲の表で引く（B2-6 の手順 2。J31）ので、変更前の選択の曲は同期の最後まで取れる。変更は次の P1（E8 の取り直しを含む）から反映する

### B2-6 転送の手順

F3-4、F3-8、N2-2、N2-6、F6-2、N1-7。

1 曲ずつの手順（1 曲の中は直列。曲の間も直列。同時に複数曲を取らない。N2-2）：

| 手順 | 内容 |
|---|---|
| 1 | 端末が、取得の要求を送る。曲は `persistent_id` だけで指定する（N1-7）。要求に、`size` と `modified_at` を、新規も再開も添える（新規と置き換えはマニフェストの値、再開は T5 に保存した値）。検査の基準も同じ |
| 2 | PC は `persistent_id` から、最後に作ったマニフェストの曲の表（J31）でパスと値を引く。マニフェストの集合に無い ID は断る。実ファイルの大きさが違うときは、E8 を返す |
| 3 | 端末は、一時ファイル（B3 が名前を決める）へ書く。受け取った量を保つ |
| 4 | 全部受け取ったら、受け取った量が `size` に等しいことを確かめる。等しければ、本来の場所へ移し、MediaStore へ登録する（B3） |
| 5 | 登録まで終えたら、その曲の同期状態を更新する（B3 の表 T）。この 1 曲が完了 |

再開（F3-4、N2-2）：

1. 途中で切れたとき、一時ファイルの大きさを続きの位置にする。T5 の `received_bytes` と違えば、ファイルの大きさを正とする（T5 の更新の前に止まっても、中身がずれないため）
2. 同じ要求に、続きの位置からの Range を付けて送る
3. PC は、`size` と `modified_at` が一致している間だけ Range に応える。一致しなければ E8 を返す。端末は一時ファイルを捨て、マニフェストを取り直して最初からやり直す
4. 再開の回数と再試行の前の待ちは V10（転送の再試行の回数・間隔）。超えたら E6 として同期を止める
5. 転送済みの部分は取り直さない。Range の対象は、先頭からの途中までに限る（最後の区間の指定は使わない）
6. アプリが終了した後にも一時ファイルが残っていれば、次の同期で続きから再開する（残す期間は B3）

失敗の種類 E：

| E | 名 | 検出 | 範囲 | 扱い | 利用者に見せる文 |
|---|---|---|---|---|---|
| E1 | 接続不可 | 到達確認で接続を確立できない（名前の解決の失敗、接続の拒否、時間切れ）。E1 は到達確認で接続先の全部がだめなときだけ。P1 の受信中の切断と、同期の開始後（P1 の後）の確立の失敗は E6 | 同期全体 | 手動なら、保存した接続先を順に試した後に失敗にする。自動なら、何も表示せず終わる（B2-7）。取得済みの曲はそのまま | PC に届かない |
| E2 | 鍵不一致 | 署名が合わない、証明書の固定に合わない、ペアリングが解除されている | 同期全体 | 再試行しない。同期を止める。自動は、鍵の不一致（`detail` なしの 401、証明書の固定の不一致）のときだけ、利用者が直すまで再開しない（B2-7。J35） | ペアリングし直す必要がある |
| E3 | 容量不足 | 事前の判定（B2-5）、または書き込み中の容量不足 | 同期全体 | 事前なら始めない。途中なら、その曲の一時ファイルと T5 の行を消して止める。完了した曲は残す | 不足分の大きさ |
| E4 | XML 不可 | PC が XML を読めない（無い、解析できない。B2-3 の回数を超えた） | 同期全体 | 端末は再試行しない。PC の画面にも警告が出る | PC の XML が読めない |
| E5 | ファイル無し | PC で曲のファイルが無い、読めない（B2-2 の細目） | 曲単位 | その曲を飛ばして続ける。同期は止めない。失敗の一覧（T6 の `failed`。S4 の失敗）に載せる。マニフェストの時点で除外した曲は除外の一覧（B2-2） | 一覧に出す |
| E6 | 途中切断 | 転送中の切断、P1 の受信中の切断（曲の指定が無いので `persistent_id` なし）、または同期の開始後（P1 の後）の接続の確立の失敗。再試行の回数を超えた | 同期全体 | 再開（上の「再開」）を試し、P1 の受信中の切断は V10 の回数でマニフェストの取得を再試行し、超えたら止める。完了した曲は残す。一時ファイルと T5 の行は残す（次の同期で再開するため） | 途中で切れた |
| E7 | 時間上限 | 前面サービスの上限に当たった（N2-6。OS が止めるのを知らせる呼び出し） | 同期全体 | その曲を保存せずに止める。一時ファイルは残す。次回に続きを行う（結果に「続きあり」を付ける） | 時間の上限。続きは次回 |
| E8 | マニフェストが古い | 曲の要求の `size`、`modified_at` が実ファイルと違う（同期の最中に曲か XML が変わった） | 曲単位 | その曲を飛ばし、同期の終わりにマニフェストを取り直して 1 回だけやり直す。やり直しでも E8 なら、E5 と同じく結果に載せる | 曲が変わった |
| E9 | 端末の書き込み失敗 | 端末が一時ファイルの書き込み、移動、MediaStore への登録に失敗した（容量不足を除く） | 曲単位 | その曲を飛ばして続ける。詳細は B3 | 保存に失敗した |

- F6-2 の五つ（接続できない、鍵が合わない、容量不足、XML が読めない、ファイルが無い）は E1〜E5。E6〜E9 は転送の途中で起きるものとして足す
- 同期全体の失敗（E1、E2、E3、E4、E6、E7）の後で、「消す」は実行しない（B2-5 の順序）。曲単位の失敗（E5、E8、E9）だけなら、ほかの曲は続け、「消す」も実行する。ただし E8 の曲に対応する消すは無い
- 結果の区分は、全部成功：完了、曲単位の失敗あり：一部、同期全体の失敗か E7、または利用者の中断：中断（取得済みの数を併記）、同期を始められなかった：失敗（端末の記録では、容量不足の事前の判定は `not_started`、他は `failed`。B3-4）

同期状態を更新するタイミング（F3-8）：

- 1 曲の更新は、その曲のファイルが本来の場所に置かれ、MediaStore への登録を終えた時点。取得の途中の曲は記録しない
- 失敗や中断で止まっても、完了した曲の記録は残る。次回の差分は、残りだけになる
- 置き換えは、新しいファイルを置き終えるまで古いファイルを残し、置き終えた時点で同期状態を新しい値に更新する。失敗したときは古いファイルと古い値のまま残す（B3 に依頼）
- m3u8 は、同期の終わりに、同期状態にある曲だけで書く。取得できなかった曲は載せない。中断で終わるときも、T3 の更新は必須とし、m3u8 は時間があれば書く。書けずに止まったときは次の同期で書き直す（次回に完全な内容になる。B3 に依頼）
- 初回の同期は、E7 で数回に分かれうる（F3-8）。続きの同期は、前回の完了分を飛ばして差分を取り直すだけで進む。特別な再開の記録は持たない

### B2-7 自動起動

F3-6、D13、N2-6。

WorkManager の制約：

| 項目 | 規則 |
|---|---|
| ネットワーク | 従量制でない（UNMETERED）を要求する。SSID は見ない（D13。WorkManager に SSID の制約が無い。review-01 の確認した事実） |
| 起動の形 | 周期の仕事（間隔は V15（自動起動の周期））。WorkManager には「つながった瞬間に起動する」制約が無いので（facts-android 1-3。下の確かめた事実）、条件を満たす間に周期で起動する形に近似する。J15（B2 の旧 J4。a） |
| 一意性 | 仕事の名を 1 つにして、同時に 2 つ走らせない |
| 実行の場所 | 仕事は到達確認までを行い、届けば前面サービス（B3）へ引き継ぐ。`setForeground` は到達確認（P3）が通り、`content_digest` の比較で抑止されないと分かった後（T3 に行を足す手順の直前）に呼ぶ（届かない自動と、抑止で終わる自動は前面の通知を出さない。review-12）。転送そのものを仕事の中で長く行わない |

- 従量制でない回線で起動するので、モバイル回線の Tailscale では自動起動しない。モバイル回線の外出先の同期は手動で行う（結果の画面で案内。B3）
- 従量制でない回線は、利用者の自宅の Wi-Fi とは限らない（外の Wi-Fi もある）。到達確認が届かないときは終わるので、害は到達確認の 1 回の通信だけ

PC への到達確認：

1. 端末は保存した接続先（方式ごとの最後の宛先 3 つ。LAN、Tailscale、USB テザリング。T4）を、最後に応えた方式（T4 の `last_endpoint`）から順に試す
2. LAN は、保存したサービス名を NSD で引き直す（保存した IP を使うと、アドレスが変わったときに外れるため）。引き直しの待ちは V14（NSD の引き直しの待ち）。Tailscale は保存した MagicDNS 名を名前解決する。USB テザリングは保存した接続先へつなぐ
3. 試す要求は、P3（署名付きの要求 1 本。本文は返さず、`content_digest` と鍵の確認だけを返す）。PC は要求の時の読み直しと実在の確認を含めてマニフェストを組んだうえで `content_digest` だけを返す（X2-4 の 7・8。P2 の曲の表（J31）は P3 では置き換えない）。認証なしでは何も返さない（N1-5）。各接続先への接続と P3 の応答の待ちは V29（LAN の 1 件は最大 V14＋V29。J39）。証明書の固定が合わない接続先は「応えない」と同じに扱い、次の接続先を試す（J36）
4. 1 件でも応えたら、その接続先で同期を始める。応えた方式を `last_endpoint` に保存し直す（J30。2026-11-06）
5. どれも応えなければ、何もせず終わる。通知を出さず、結果の記録にも残さない（F3-6）。診断のログに 1 行だけ書く（B3）。ただし、どれも応えず、そのうち 1 つでも証明書の固定の不一致があれば E2 とする（J36。T3 に残す。下の「自動起動の抑止」の例外）

自動起動の抑止：

- 抑止の判定は 2 段に分ける。到達確認（P3）の前に、T3 と T4 だけを読んで、E2・E3 の後の抑止と V19 の抑止を判定する（E2 は「`ended_at` が `paired_at` 以後の行に E2（鍵の不一致）がある」、E3 は「最新の E3 の行より後に手動の `success` か `partial` の行が無い」で、T3 の最新の行ではなく行の種類で引く。review-12）（通信を重ねないため）。到達確認の後に、`content_digest` の比較を行う（review-11）
- `content_digest` が前回の完了した同期と同じで、前回が「完了」なら、マニフェストを取らずに終わる（N2-5）
- 前回が E2 だったときは、利用者がペアリングし直すまで自動を再開しない（鍵が合わないまま周期で通信を重ねないため）。対象は、`detail` なしの 401 と証明書の固定の不一致（鍵の不一致）に限る。`clock_skew`・`replay`・429 では止めない（J35）。E3 のときは、手動の同期が成功するまで自動を再開しない（容量不足のまま転送を繰り返さないため）。J15（B2 の旧 J5。a）
- 抑止で終わった自動は、T3 に残さない。診断のログに 1 行だけ書く（B3-4）。例外として、P3 が E2 を返した自動と、到達確認の全部がだめで不一致が 1 つでもあった自動（J36）は E2 で T3 に残す（鍵の不一致のものだけが後の抑止の印になる。J35）
- 前面サービスの時間の上限（Android 15 以降は dataSync で 24 時間に合計 6 時間。review-01 の確認した事実）は、自動も手動も同じ枠を使う。上限に近いときの扱いは B3

手動との優先：

| 状況 | 規則 |
|---|---|
| 手動の開始時に自動が進行中 | 二重に始めない。画面は P1 の前に実行中の自動を確かめ、動いていれば確認を出さずに S3（進行）に入る。自動は自動のまま続け、抑止も「消す」の飛ばしもそのまま。終わった後に必要なら、利用者がもう一度押す（J34） |
| 自動の開始時に手動が進行中 | 自動は何もせず終わる |
| 手動の完了の直後 | V19（手動の後の自動の抑止時間）の間、自動は何もせず終わる（到達確認の前に判定する） |
| 手動の開始 | 到達確認で届かないときは、E1 を利用者に見せる（自動と違い、何もせず終わらない） |

### B2-8 同期の結果の形

F3-7、F6-2、F5-3、F1-10、N3-5。

### B2 の確かめた事実

この稿（第 5 稿）では新たに文書を取得していない。第 2 稿までは概要設計のレビューで取得した 3 件。第 3 稿で facts-jvm（2026-11-05。notes。この repo には無い）の 1a〜1j、2 を写した（review-05 の基本設計の直し）。第 5 稿で facts-android の 1-1、1-3 を写した（review-13。B3 に写してあるものと同じ）。取得日はすべて 2026-11-05。

- WorkManager の `Constraints.Builder` が持つ制約は、ネットワークの種別、充電中、電池残量、端末のアイドル、空き容量、content URI の変化だけ。SSID は指定できない。出典：Android の `androidx.work.Constraints.Builder` のリファレンス（2026-11-05 取得。review-01 の確認した事実）
- Android 15 を対象にしたアプリの `dataSync` 前面サービスは、24 時間のうち合計 6 時間で `Service.onTimeout` が呼ばれ、数秒以内に止めないと例外になる。利用者がアプリを前面に出すと計時が戻る。出典：Android 15 の動作の変更（2026-11-05 取得。review-01 の確認した事実）
- WorkManager の周期の仕事の最小の間隔は 15 分。`Constraints` に「ネットワークにつながった瞬間に起動する」制約は無い。出典：Android の WorkManager の文書（facts-android 1-1、1-3。2026-11-05 取得。B3 の確かめた事実に写してある）
- MediaStore 経由でアプリが作ったメディアファイルは、アプリを入れ直すと別のアプリの扱いになり、変更や削除には利用者の同意が要る。出典：共有ストレージのメディアの文書（2026-11-05 取得。review-01 の確認した事実。B2-5 の入れ直しの扱いの根拠）

WatchService（2）。出典：Java SE 21 API「WatchService」（2026-11-05 取得。一部）：

- JDK 文書に Windows 固有の記述は無い。実装依存として、1 回の変更が 1 件にも複数件にもなる。取りこぼしがあれば OVERFLOW を返し、状態の再確認の契機にする（B2-3 の「安定の待ち」と「要求の時」の読み直しで受ける）
- ローカル以外の記憶域では変更を検知できるかは実装依存で、遠隔での変更の検知は必須ではない。ネイティブの機構が無いときは定期確認で代替する

実物の確認（2026-11-06。iTunes 12.13.7.1、Apple のサイトの版、Windows 11。トラック 12827、プレイリスト 35 のライブラリ。集計はスクリプトで行い、曲名・パス・ID の値は記録していない）：

- XML の場所は `%USERPROFILE%\Music\iTunes\iTunes Music Library.xml`（1i）。書式は UTF-8、BOM なし、`DOCTYPE` あり、改行は CRLF。文字参照は `&#38;`、`&#60;`、`&#62;` で、`&amp;` は出ない。date は全件 `YYYY-MM-DDThh:mm:ssZ`
- 最上位：`Major Version`、`Minor Version`（1、1）、`Application Version`、`Date`（書き出しの時刻と秒まで一致）、`Features`、`Show Content Ratings`、`Library Persistent ID`（16 桁の大文字の 16 進。1a）、`Tracks`、`Playlists`、`Music Folder`（`Location` と同じ形で末尾は `/`）
- トラック：B2-1 の表のキーは `Protected` を除いて型も一致。`Persistent ID` は全件 16 桁の大文字の 16 進で重複なし。`Track ID` は dict のキーと全件一致。`Track Type` は全件 `File`（1c）。`Kind` は MPEG、Apple Lossless、AAC、購入した AAC、WAV。拡張子は mp3、m4a、wav で m4p なし。`Location` が無いトラックが 1 件
- `Protected`：全件キーなし。購入した AAC（保護なし）にも出ない。保護された曲が無く、真の出方は未確認。保護の判定は `Protected` と `m4p` の両方を見る今の規則（B2-8 の規則 1）を保つ
- `Location`（1d）：全件 `file://localhost/X:/` の形（`file:///`、`file://<ホスト>/`、`X%3A` は 0 件）。エンコードされる記号は空白 `%20`、`#` `%23`、`%` `%25`、`[` `%5B`、`]` `%5D`、`` ` `` `%60`、`}` `%7D`、`^` `%5E`。そのままの記号は `&` `+` `'` `(` `)` `!` `@` `_` `-` `.` `,` `~` `=` `$`。日本語は全件 percent-encoding で、16 進は大文字のみ、UTF-8 として不正なものは 0 件。正規化は NFC、ASCII のみ、NFD（1 件）が混ざる（B3-1 の「正規化しない」で通る）。ネットワーク上の曲は無かった
- B2-2 の手順で復号し、1 つのドライブの全件が実在まで通った。ほかのドライブの曲は親フォルダーごと無く（古い場所の記録の見込み）、実在しない曲が多数ある実物でも B2-2 の除外で扱える
- プレイリスト：`Master` は「ライブラリ」1 件だけに付く（1g）。`Distinguished Kind` は組み込みの 8 件（ミュージック 4、ムービー 2、テレビ番組 3、ポッドキャスト 10、オーディオブック 5、ダウンロード済み 65・66・67）に付き、起動中だけ Genius（26）が増える。`Smart Info` は組み込みにだけ付き、常に `Smart Criteria` と対。`Visible`（偽）は組み込みの 1 件。`Folder`、`Parent Persistent ID` は 0 件。`Playlist Items` が無いものは組み込みと空の普通の一覧。`Playlist Items` の要素は `Track ID` だけで、`Tracks` に無い参照は 0 件。`Playlist Persistent ID` は全件 16 桁の大文字の 16 進で重複なし。除外の規則（B2-1）の後に残るのは利用者が作った一覧だけ
- 書き出し：`.itl` を先に置き換え、次に `Temp File.tmp` を作って書き、改名を 3 回して XML と入れ替え、一時ファイルを消す。XML に作成のイベントは出ず、名前は改名で現れる。入れ替えの数ミリ秒は XML が無い。XML の作成日時は前のファイルの値を引き継ぐ。プレイリストの変更、タグの変更、終了のそれぞれで書き出された
- `Date Modified`（Q10）：コメントの変更で変わり、元に戻しても元の値には戻らない
- `Persistent ID` は終了と再起動をまたいで全件不変。`Track ID` も 4 回の比較で変化 0 件。ただし再起動 1 回分なので、「書き出しのたびに変わりうる」前提（B2-1）は外さない
