## X6 android の保存と同期

### X6 の書く項目

- X6-1 Room の定義 T1〜T7
- X6-2 MediaStore の書き込み
- X6-3 同期の実行（ワーカーの手順）
- X6-4 WorkManager の登録
- X6-5 HTTP クライアント
- X6-6 鍵の保管 K3・K4
- X6-7 テストの観点

### X6 の読み方

- M4 の中の置き場は X1-3 のパッケージの構成に従う。この節は M4 の「保存と同期」の部分（データベース、ストレージ、ワーカー、通信、鍵）だけを書く
- 判断（差分、パスの計算、m3u8 の生成、署名対象の組み立て）は M1。この節は M1 の関数を呼ぶ順と、OS の API を呼ぶ手順だけを書く（B1-3）。M1 の関数の名前は X3、X4 に従う
- 読み替え：B2-6 の「一時ファイル」は、端末では MediaStore の `IS_PENDING`＝1 の行を指す（B3-2）。「本来の場所へ移す」は `IS_PENDING`＝0 への更新を指す
- 値は V の番号で参照する。この節で新しく要る値は「X6 の置いた値」に置く

### X6-1 Room の定義 T1〜T9

#### 全体の約束

| 項目 | 決め方 |
|---|---|
| データベース | 1 つ。M4 の内部領域。ファイル名と版は実装で決める（版の初期値は 1。2026-11-07 に 2 へ上げた。T8、T9 を足す手書きの `MIGRATION_1_2`。X-34） |
| 型の対応 | text は文字列、integer は 64 ビット整数、真偽は使わない（text か integer で持つ）。日時は UTC のエポックのミリ秒（B3-4） |
| NULL | 表の「必須」が「いいえ」の列だけ NULL を許す。それ以外は NOT NULL |
| 列挙の text | `state`、`result`、`trigger`、`kind` は B3-4 の語を文字列のまま持つ。未知の語を読んだら、その行を「不明」として扱い、書き換えない（新しい版で足した語を古い版が壊さないため） |
| 外部キー | T6 の `run_id` から T3 へ。T3 の行を消すとき T6 も消える（V26 の件数を超えた分の削除で、同じ取引の中で消す）。T1、T2 は T4 へ張らない（ペアリングの解除後も残す。B3-4） |
| 取引 | 1 曲の完了（T1 の追加と T5 の削除）は 1 つの取引にする。T2 の更新も同じ |
| スキーマの書き出し | Room のスキーマの JSON を repo に置く（移行の試験の入力にする） |

#### 移行の方針

1. 版を上げるときは、手書きの移行（`Migration`）を必ず書く。破壊的な再作成（表を消して作り直す）の指定は使わない。根拠：T1 が消えると「自分が置いた」の記録が失われ、D14 と同じ状態になる
2. 足すものは列の追加を第一にする。既存の列の型の変更と削除は、新しい表を作って写す手順にする
3. 移行の試験は M4 の薄い統合（B1-3）。旧版のスキーマの JSON から新版へ移し、T1 と T5 の行が残ることを確かめる。版 1 → 2 は T8、T9 の追加だけ（既存の表の列は変えない）。版 1 の端末は選択が空で始まり、利用者が S6 で選ぶ（PC の選択は引き継がない。D15）
4. `allowBackup` は無効（B3-2）。データベースはアプリと一緒に消える前提で、バックアップからの復元の移行は考えない。Android 12 以降を対象にしたアプリでは `allowBackup` の無効だけでは機器間の移行が止まらない、と理解している（実装時に公式文書で確かめる）。移行先で T1 が戻ると持ち主でないファイルを自分のものとみなす（D14 の前提が崩れる）ので、`dataExtractionRules` で Room のデータベースを移行の対象から外す

### X6-2 MediaStore の書き込み

- 保存先のボリューム（D16。2026-11-07）：`MediaStoreFiles` の実体はボリューム名を受け取って作る。挿入と問い合わせは `MediaStore.Audio.Media.getContentUri(<ボリューム名>)`、`MediaStore.Files.getContentUri(<ボリューム名>)` を使う。ボリューム名は T7 の `storage_volume`（無ければ `external_primary`）。選んだボリュームが `MediaStore.getExternalVolumeNames` に無いとき、`MediaStoreFiles` を作る側が「保存先が無い」を同期の入口（X6-3 の手順 0）に伝える。削除は URI を直接指すので、別のボリュームの URI も削除できる
- 切り替え前のファイルの削除（`deleteRelocated`）：T9 の URI を順に削除し、成功か「既に無い」なら T9 の行を消す。`SecurityException`（持ち主が違うなど）の行は残す。消した件数を返す。呼ぶのは S5 の「以前の場所の曲を消す」（確認の後。同期が動いている間は呼ばない）だけで、同期の手順からは呼ばない（2026-11-07）。保存先を切り替えたとき T9 に行が残っていれば、S5 は切り替えの案内に「前の場所に曲が残っています。次の同期の前に、「前の保存先の曲を削除する」で、先に前の場所の曲を消してください」を足す（切り替え自体は止めない。X7-1-6）。残したまま本体と SD の間を戻すと、前の場所の曲との衝突で全曲が接尾辞つきで重複して置かれるため（review-15）

呼び出しは `ContentResolver` 経由。操作は 1 つのクラス（名前は `MediaWriter`）に集める。`MediaWriter` は手順と T1・T2・T5 の更新を持つ具象クラスで、OS に触る部分（挿入、開く、読み戻し、削除、問い合わせ）だけを interface `MediaStoreFiles` に分ける。実体は `ContentResolver` を呼び、試験では `MediaStoreFiles` を差し替える（X6-7）。入口は次の表。

| 操作 | 入力 | 出力 | 副作用 |
|---|---|---|---|
| 曲を新規に書く | 相対パス（M1 の結果）、MIME、`size`、`modified_at`、取得元の入力 | 読み戻した値（`DISPLAY_NAME`、`RELATIVE_PATH`、`SIZE`、`DATE_MODIFIED`、URI）またはエラー（E3、E9） | pending 行の作成、T5 の更新、完了で T1 の更新 |
| 曲を置き換える | T1 の行、取得元の入力 | 同上 | T1 の `state` を `replacing`、同じ URI を `"wt"` で書き直す |
| 曲を消す | T1 の行 | 成功、または「既に無い」 | `ContentResolver.delete`。T1 の行を消す |
| m3u8 を書く | 名前、本文（M1 の結果） | URI | `MediaStore.Files` に insert（下の「m3u8」）、または既存の URI を `"wt"`。名前が変わったときは古い m3u8 を消す |
| 以前の曲を一覧する | `Music/<アプリ名>/` の下を問い合わせる。持ち主（自分のパッケージ）では絞らない | T1 に無い曲と、T2 に無い m3u8（`MediaStore.Files`）の一覧（URI、相対パス、サイズ） | なし。読み取りの権限が要る（B3-2、J15、J32）。入れ直しで持ち主が外れた曲も出すため、持ち主では絞らない（review-15）。持ち主で絞るのは、書き込み時の衝突判定（下の「曲を新規に書く手順」の 1）だけ |

#### 曲を新規に書く手順

1. 保存先の相対パスは、X3-3 の関数（M1）が返した値を使う。T1 と `MediaStore.Audio.Media` の問い合わせの両方で、同じ相対パスの別 ID を確かめ、衝突があれば関数に「使用中のパスの集合」を渡して接尾辞を足させる（B3-1 の 4）。衝突の問い合わせは持ち主が自分の行に絞る（絞り方は実機で確かめる。整理のために読み取りの権限を許した後も、旧の曲と他のアプリの曲で集合が変わらないようにする）。接尾辞を足した全文のパスでも使用中のときは、関数は「解けない」を返さずそのパスを返し、MediaStore の別名付け（手順 9 の読み戻し）に任せる（X3-3 の手順 6。J42）
2. 空き容量は、同期の前に一括で確かめ済み（X6-3 の 5）。ここでは書き込み中の容量不足（`IOException` のうち空きの不足）を E3 として扱い、pending の行を削除し T5 を消して止める（B2-6）
3. `MediaStore.Audio.Media` に insert する。`DISPLAY_NAME`、`MIME_TYPE`（拡張子の表から決める。表は X3-3 が持つ）、`RELATIVE_PATH`（`Music/<V22>/<アーティスト>/<アルバム>/`）、`IS_PENDING`＝1。行が作れなければ E9
4. 返った URI と、`expected_size`、`source_modified`、`started_at`、`received_bytes`＝0 を T5 に保存する
5. 出力ストリームを開く。再開のときは追記の書き込みモード（`"wa"`）で開き、開けなければ「取り直し」にする。取り直しは、pending の行を削除し、T5 を消して、新規に書き直す（手順 3 から。同じ行を `"wt"` で開き直さないので、URI が変わりうる）。`"wa"` が使えるかは、公式文書に記載が無く、コード上は拒否する箇所を見つけていない。実機で確かめる（未確認。C-12）
6. 入力を、V27 の長さの区切りで読んで書く。1 区切りごとにフラッシュし、`received_bytes` を T5 に更新する。区切りの間に、取り消しの要求（下の X6-3 の「中断と時間の上限」）と容量不足を確かめる
7. 書き終えたら、書いた量を `expected_size` と比べる。足りないときは E6 とし、pending の行と T5 を残して再開に回す（B2-6）。足りない場合には、取得元の切断のほか、取得元が正常に閉じた短い本文も含める（review-15）。ただし、取り直しても増えなかったときは、E9 とし、pending の行を削除して T5 を消し、次の曲へ進む。増えなかったとは、続きから受ける取得（再開）では 1 バイトも受けなかったとき（再開の取得が 0 バイトで閉じ、pending のファイルの大きさが再開の前と同じ）、毎回最初から書き直す取得（置き換え、新規）では、正常に閉じた短い本文で受けた量が前の取得の受け取り量以下のとき（その曲の最初の取得は比べない）。PC が常に短く返すと、再開を V10 の回数まで繰り返して同期全体が止まるため。多すぎるなどそれ以外の不一致は E9 とし、行を削除して T5 を消す
8. `IS_PENDING`＝0 に更新し、`DISPLAY_NAME`、`RELATIVE_PATH`、`SIZE`、`DATE_MODIFIED` を読み戻す
9. 読み戻した値で T1 を書き、T5 を消す（1 取引。「曲の完了の記録」）。T1 の `relative_path` は、読み戻した `RELATIVE_PATH` から `Music/<V22>/` を除いた後に `DISPLAY_NAME` を足した値

- 読み戻した `RELATIVE_PATH` が `Music/<V22>/` で始まらない（MediaStore が場所を変えた）ときは、その曲を E9 として扱い、行を削除する。根拠：`RELATIVE_PATH` はヒントにすぎない（B3-2）。m3u8 の基準が崩れるため

#### 再開と回収

1. 同期の始めの整理（X6-3 の 1）で、T5 の期限切れ（V25）の行を回収する。pending の行を削除し、T5 を消す
2. T5 に行があり、`source_modified` と `expected_size` が今のマニフェストの値と同じなら、その URI を開き直して続ける（手順 5 から）。どちらかが違えば、pending の行を削除して T5 を消し、新規に書く。同じ場合の再開の位置は pending のファイルの大きさを正とする（フラッシュと T5 の更新の間に落ちると T5 の `received_bytes` が遅れる。`received_bytes` が大きさと違えば大きさに合わせて T5 を直す）。pending のファイルの大きさが `expected_size` と同じ（`IS_PENDING`＝0 の後、T1 を書く前に落ちた）ときは、取得せずに手順 8（読み戻し）、9（T1 の記録）へ進む
3. T5 に行があるが、その URI が MediaStore に無い（利用者が消した、OS が掃除した）ときは、T5 を消して新規に書く
4. 置き換えの途中（T1 の `state`＝`replacing`）は、続きから再開せず、最初から書き直す。根拠：`"wt"` で切り詰めており、途中の位置が使えない。T5 には置き換えの行を作らない

#### 削除と整理

- 自分が作った行の削除に同意の画面が要らないことは、文書に明記が無い。他のアプリが所有するファイルの削除で `RecoverableSecurityException` を捕まえる必要がある、という書き方からの読み取りである（確かめた事実の 4）。実機で確かめる
- 消す対象は T1 の曲だけ。`ContentResolver.delete` を呼び、成功か、行が無い（既に消えている）ときに T1 の行を消す。権限の例外（`SecurityException`）は、その曲だけ E9 にして T1 を残す
- 空のフォルダの後始末はしない（B3-2）
- 入れ直し後の整理は、「以前の曲を一覧する」の結果（T1 に無い曲と、T2 に無い m3u8。入れ直し後の古い m3u8 を含む。J32）を X7 が表示し、選ばれたものを Activity が `createDeleteRequest` で消す。ワーカーからは呼ばない（B3-2）。ワーカーは整理の対象を作らない。一覧は持ち主で絞らない（上の表。review-15）
- 入れ直し後の初回の同期で、MediaStore が名前を変えた（`(1)` など）場合も、読み戻した値を T1 に保存する（手順 8）ので整合する

#### m3u8

1. 本文は X3-4 の関数が返す。入力は、プレイリストの順の `persistent_id` と、T1 から引いた `relative_path`（T1 に無い曲は除く）。UTF-8（BOM なし）のバイト列で書く
2. m3u8 は `MediaStore.Files` に書く（J18）。`MediaStore.Audio.Media` は playlist の MIME を insert できず `IllegalArgumentException` になるため使わない。`Files` では MIME が playlist 種別のとき `Music/` が許可される
3. 新規は `MediaStore.Files` に insert する。値は次のとおり。行が作れなければ、そのプレイリストを E9 にして続ける
   - `DISPLAY_NAME`＝`<名前>.m3u8`（拡張子は m3u8 のまま）
   - `MIME_TYPE`＝`audio/x-mpegurl`
   - `RELATIVE_PATH`＝`Music/<V22>/`
   - `IS_PENDING`＝1 で書き、書き終えて 0 に更新する
4. 既存の確認：T2 に同じ `playlist_id` の行があり、その `relative_path` の名前が X3-4 の `buildPlaylistFileName` の結果と同じなら、T2 の URI を開いて `"wt"` で書く。同名の insert は上書きにならず `名前 (1).m3u8` の形の別名になる（確かめた事実の 3-5）。そのため新規の insert の前に T2 で既存を確かめ、あれば既存を書き直す。読み戻した `DISPLAY_NAME` と `RELATIVE_PATH` を T2 に保存する
   - 読み戻した名前が期待した名前（`buildPlaylistFileName` の結果）に「 (n)」を足しただけのときは、改名とみなさない（入れ直し後の初回の別名が、同期のたびに消して作り直されるのを避ける）。T2 の URI を開いて `"wt"` で書く
   - 名前が違う（上の場合を除く。プレイリストの改名）なら、T2 の URI の古い m3u8 を削除してから、新しい名前で新規に insert する（手順 3）。古い m3u8 の削除に失敗しても、新しい書き込みは続ける（残った古い m3u8 は「以前の曲を一覧する」の対象になる）
5. 書き終えたら索引の更新を促す（`IS_PENDING` の切り替え、または `MediaScannerConnection.scanFile`。どちらで足りるかは未確認。C-2 の「`Files` への insert と索引の実機確認」で確かめる）
6. T2 の `track_count`、`written_at` を更新する
7. `playlists` と `unresolved_playlists` のどちらにも無い T2 の行は、m3u8 を削除して T2 の行を消す。未解決のプレイリストの T2 の行と m3u8 は消さない（J24）

### X6-3 同期の実行

#### 手順

0. 始められるかの確認（手動・自動とも。D15、D16。2026-11-07）。次のどれかなら、同期を始めず、診断のログに 1 行書いて何もせず終える（T3 に残さない）：(a) T8 が空（選択が空）。(b) 選んだ保存先のボリュームが `MediaStore.getExternalVolumeNames` に無い（SD が見つからない）。本体へ勝手に切り替えない。手動は、同期ボタンの時点で画面側（X7-1-2）が同じ判定を先に行い、S6 または S5 へ案内する。ワーカーのこの判定は、画面を通らない起動（自動、走り直し）への備え。通知は出さない
1. 始めの整理（手動・自動とも。端末内の処理だけを、次の抑止より前に行う）。自動の開始時に `manual-sync` が実行中か待機中なら、この整理も行わず何もせず終える。手動の開始時に `auto-sync` が実行中なら、ワーカーを作らない（X6-4 の排他）。したがって次の整理は、自分以外の同期が動いていないときだけ行う：
   1. T5 の期限切れ（V25）の行を回収する（X6-2 の「再開と回収」）
   2. `ended_at` が NULL の T3 の行（自分の行を作る前なので、すべて強制終了の跡）を `interrupted` で閉じる（`error_kind` は空）。`ended_at` は `started_at` と同じ値にする（閉じた時刻は分からない。手順 2 の 1 の (a) の V19 の起点は手動の `success`・`partial` の行だけなので、跡の行は起点にならない。J48）。`result_json` は空のまま（S4 は件数を出さない。X7-1-5）。強制終了の跡なので `reported`＝1 にして再送しない
   3. T2 に無い、自分の pending（`IS_PENDING`＝1）の m3u8 の行を消す（m3u8 の新規の insert の途中で落ちた残り。`MediaStore.Files` の `Music/<V22>/` の下を問い合わせる）
2. 到達確認と自動の抑止：
   1. 自動のとき、次のどれかなら終える。診断のログに 1 行書き、T3 に残さない（B2-7、B3-4、J10）。(a) 手動の `success`・`partial` の最新の行（J37 の省略で閉じた行を含む）の `ended_at` から V19 以内（失敗した手動、中断、`not_started` の行は起点にしない。失敗した手動の後は自動を抑えない。J48）、(b) `ended_at` が T4 の `paired_at` 以後の T3 の行に、鍵の不一致の E2 がある（`result_json` の `key_mismatch` が真の行。`detail` なしの 401 と、証明書の固定の不一致。`clock_skew`・`replay`・429 の E2 は数えない。J35）、(c) 最新の E3 の行より後に、手動の `success` か `partial` の行が無い（E3 の行が無ければ当たらない）。行の種類で引くので、間に手動の E1 や中断の行が入っても外れない
   - 1b. 接続先を試す前に、T4 の `key_alias` の別名が Keystore にあるか確かめる。無ければ（X6-6）P3 を送らず、手動・自動とも T3 に行を追加して E2（`failed`、`key_mismatch` は真）で閉じて終える（書き方は手順 2 の 4 と同じ。J35）
   2. 保存した接続先を P3 で試す（本文は T8 の選択の ID の配列。B2-7、V14、V29、V53）。順は `last_endpoint` を先頭にし、残りは LAN、Tailscale、USB。LAN は T4 の `pc_id` の先頭 8 桁（`pid`）で NSD から引き直してから試し、見つかった名前が保存したサービス名と違えば `endpoint_lan` を書き直す。引き直しの待ちは V14。1 件の接続の確立の待ちは V29、P3 の応答の待ちは V53。LAN の 1 件は最大で V14＋V29＋V53（J39、J47）。接続の確立の待ち（V29）と P3 の応答の待ち（V53）のどちらが切れても「応えない」と同じに扱い、証明書の固定が合わない接続先も同じに扱って、次の接続先を試す（J36、J47）。応えた方式を `last_endpoint` に保存する（J30）。診断のログに、接続先ごとの失敗の理由（応えない、証明書の不一致、引き直しで見つからない）を 1 行ずつ書く。手動の入力データの `reach_failed` が真なら、この接続の試行を省いて手順 2 の 3 へ進む（画面側が同じ試行を済ませているため）
   3. 全部の接続先が応えず、証明書の不一致が 1 つも無いとき（届かない）、手動は T3 に行を追加して E1（`failed`）で閉じて終える。書く列は `result_json` に分かる範囲（予定の件数など。無ければ空の件数）で、`reported`＝0 のまま次回の再送の対象にする。閉じた後に `stage`＝`finished`（`outcome`＝`failed`）を立て、手順 12 の終了の通知を出す（手動の S3 は `finished` で S4 へ進む。X7-3-2 の 7）。自動は診断のログに 1 行書いて終える（T3 に残さない。通知も出さない）
   4. P3 が E2 を返したとき、または全部の接続先が応えず、そのうち 1 つでも証明書の不一致があったとき（J36）は、手動・自動とも T3 に行を追加して E2（`failed`）で閉じて終える。`result_json` に空の件数、`key_mismatch`、`error_detail` を書く（手順 2 の 3 と同じ書き方。手順 10 を通らないため）。閉じた後に `stage`＝`finished`（`outcome`＝`failed`、`error_detail` に E2 の `detail`）を立て、手順 12 の終了の通知を出す（自動は静かな通知。X7-3-2 の 7）。鍵の不一致（`key_mismatch` が真）の自動の E2 の行は (b) の抑止の印なので、「抑止で終えた自動は残さない」規則とは別の扱いとする（`reported`＝0。再送の対象）
   - 4b. P3 が E2 以外の失敗（503＝E4、500）を返したときは、その接続先で止め、次の接続先を試さない。PC には届いているので「届かない」にも抑止にも当たらず、手動・自動とも T3 に行を追加して E4（500 は `error_kind` なし）の `failed` で閉じて終える（書き方は手順 2 の 4 と同じ。`reported`＝0。J45）。閉じた後は `stage`＝`finished` を立て、手順 12 の終了の通知を出す（自動は静かな通知）
   5. P3 が通った後に、`reported`＝0 の T3 の行を `started_at` の昇順で全部、P4 で再送する。1 行の再送は 1 回の同期で 1 度。成功するまで次の同期で試す（B4-4 の 5）。PC は保存済みより古い `startedAt` の報告で `last_sync` を上書きしない（X5-1 への依頼）。失敗しても結果に影響しない
   6. 自動のとき、P3 の `content_digest` が T3 の最新の完了した行（`content_digest` が NULL でない最新の行）と同じで、その行が `success` なら終える（T3 に残さない）。ただし、保存先の切り替えが要る（T7 の `placed_volume` が選んだボリュームと違う）か、前の切り替えが完了していない（`relocating` が `true`）ときは終えない（手順 3b、手順 4 の 1 と同じ。B3-1）。手動は、この比較ではなく手順 4 の 1 で扱う
   7. 自動の抑止で終えないと決まったら、自動は `setForeground` を呼ぶ。抑止で終える自動、届かない自動は前面の通知を出さない（B2-7）。手動は開始直後に呼び済み（入口の表。J46）
3. T3 に行を追加する（`ended_at` は NULL）。上の抑止で終える自動は追加しない。手順 2 の 3（手動）と 4（手動・自動）で終えるときは、そこで追加している（J10）
3b. 保存先の切り替え（D16）：T7 の `placed_volume` が `storage_volume`（既定は本体）と違えば、T1 と T2 の行を T9 へ移し、T5 を破棄し（pending の行を削除）、`placed_volume` を新しい値、`relocating` を `true` にする（X6-1 の「保存先の切り替えの記録」。T3 の行を作った後、差分の前）。`relocating` が `true` のままなら（前の切り替えが完了せずに終わった）、切り替えの途中として手順 4 の 1 の省略と手順 9b の対象にする。ここで T1 が空になるので、差分は選択の全曲の「足す」になる
4. P1 でマニフェストを取り（本文は T8 の選択の ID の配列）、M1 の差分を計算する（足す、置き換える、消す）。入力は T1 の全行、`presentIds`（T1 の曲のうち MediaStore に行が今もある曲の `persistent_id`。自分の pending の行も含めて調べる。無い曲は X3-2 の判定で「足す」になる）、記録の `library_id`（X6-1 の T3）、V20、`isPlayable`（手順 4 の 2）。差分の入力に T1 の `state` は渡さない（X3-2。置き換えの途中で落ちた曲は T1 の `size`・`modified_at` が古いままなので、判定で「置き換える」になる）

| 制約 | 従量制でないネットワーク（`UNMETERED`）。SSID は見ない（D13） | なし（接続の可否は P3 の結果で決める。従量制でも手動は通す） |
| 登録の契機 | S5 で自動起動を有効にしたとき。無効にしたとき解除 | S1 の同期ボタン |
| 重複の規則 | 同じ名前は 1 つだけ。既にあれば残す（`KEEP` 相当） | 同じ名前が進行中なら新しく始めない |
| 再起動後 | WorkManager が登録を保つ（アプリ側の受信は要らない。未確認） | 該当しない |

- 周期の間隔の最小は WorkManager の下限（15 分。確認済み）より V15 が長いので、下限は問題にならない
- 最初の版の土台は targetSdk 36、compileSdk 37、minSdk 30（2026-11-06、#3）。下の条件はすべて当たる
- 前面サービスの種別：targetSdk 34 以上では、長い処理の Worker に前面サービスの種別が要る。`SystemForegroundService` の上書き（`dataSync`）は X7-4-1 に書く。`dataSync` を書く例は文書に無い（確かめた事実の 1-5）
- Android 16 以降の注：長い処理の Worker（前面サービス）がジョブの割り当て時間を使い切ることがある（確かめた事実の 1-6）。C-10 の表で確かめ、必要なら前面サービスの直接起動へ替える（基本設計の直し 18）。C-10 は今後対応。実装（前面サービスの直接起動へ替える余地）は最初の版に入れる（B4-8）
- Android 15 以降（targetSdk 35 以上）の `dataSync` は、24 時間に合計 6 時間で止められる。アプリを前面に出すと計時が戻る（B3-5。review-01 の確認した事実）。C-6 は今後対応（B4-8）
- 手動と自動の排他（B2-7）：
  1. 手動の開始時に `auto-sync` が実行中なら、新しい仕事を作らず、確認を出さずに実行中のものを S3 に出す。自動は自動のままで、「消す」の抑止も飛ばしもそのまま。終わった後に必要なら利用者がもう一度押す（J34）。確認の画面で承認した後の起動のときに自動が動いていた場合も、新しい仕事は作らず、承認は使われない。S3 に「承認は使われなかった。終わった後にもう一度押す」を出す（X7-1-2）
  2. 自動の開始時に `manual-sync` が実行中か待機中なら、何もせず終える（X6-3 の手順 1 の始めに確かめる）
  3. 手動の完了（`success`・`partial`。J37 の省略を含む）から V19 の間は、自動は何もせず終える。判定は T3 の手動の `success`・`partial` の最新の行の `ended_at` による。失敗した手動の後は自動を抑えない（X6-3 の 2 の 1。J48）
- 実行中かどうかは、WorkManager の状態の問い合わせ（名前で引く）と、同じプロセス内の排他（1 つの実行だけが `SyncWorker` の本体に入る）の両方で守る
- 自動の失敗は再試行しない（ワーカーは常に `Result.success` を返す）。次の周期（V15）に任せる。OS が止めた仕事の走り直しは別（X6-3 の入口の「走り直し」）
- S5 の切り替えは T7 の `auto_sync_enabled` の更新と登録・解除を 1 組で行い、順は「T7 を更新 → 登録または解除」。登録に失敗したら T7 を戻す

### X6-5 HTTP クライアント

| 項目 | 決め方 |
|---|---|
| ライブラリ | Ktor のクライアント（B1-4）。エンジンは OkHttp を第一案とする（Android で枯れている。選定は実装で確かめる。未確認） |
| 接続先 | T4 の接続先 3 つ。ポートは各接続先に含める（V16 は既定） |
| 信頼の判定 | 標準の証明書の検証を使わず、OkHttp エンジンの `TrustManager` と `HostnameVerifier` の差し込みで自前の判定にする（Ktor クライアントの Android での固定は公式文書で確かめられていない。未確認。C-11）。提示された葉の証明書の SPKI の SHA-256 を計算し、T4 の `spki_hash` と比べ、一致したときだけ信頼する。ホスト名は照合しない（B4-3 の 1） |
| P5・P6 の接続 | 証明書を検証せず、提示された SPKI のハッシュを記録して X4 の手順へ渡す（B4-3 の 1）。この接続は固定前の専用のクライアントを使い、他の P と共用しない |
| 待ち時間 | 接続先 1 件の接続の確立は V29。P3 の応答の待ちは V53（J47）。LAN の NSD の引き直しの待ちは V14。LAN の 1 件は最大で V14＋V29＋V53（J39、J47） |
| P1・P3・P7 | P1・P3 は `POST`。本文は `{"playlist_ids":[…]}`（T8 の ID。X3-1b の `writePlaylistIds`）で、署名の本文の SHA-256 に含める（X4-3）。P7 は `GET` で、応答の本文を `readPlaylistTree` で読む（X7-1-7）。P7 の失敗は P1 と同じ表（401、403、429、503 など）で E に写す。S6 へ返す取得の結果（`CatalogResult`）は、`Loaded`、`Unreachable`（届かない）、`KeyMismatch`（`detail` なしの 401、証明書の固定の不一致）、`Rejected`（E2 の `detail` つき。401 の `clock_skew`・`replay` と 429）、`XmlUnavailable`（503）、`Other` とする（X7-1-7。review-15） |
| 圧縮 | P1 だけ `Accept-Encoding: gzip` を付ける。P2 では付けない（曲は圧縮済みで、`Range` と `Content-Length` を保つ） |
| 本文の上限 | 受信側では P1 の大きさに上限を置かない（数 MB。V31 は要求の本文の上限で、受信には当たらない） |

#### 署名ヘッダの付与

1. 要求ごとに、M1 の関数に、メソッド、パスと問い合わせ、本文の SHA-256、時刻、nonce（`CryptoProvider` の乱数）、`device_id` を渡す（X4-3）
2. M1 が署名対象の文字列を組み立て、署名を `CryptoProvider` の HMAC-SHA256 に依頼する。M4 の実体は Keystore に依頼する（X6-6）
3. M4 が `X-Psfox-Device`、`X-Psfox-Timestamp`、`X-Psfox-Nonce`、`X-Psfox-Signature` をヘッダに付ける
4. 再開のたびに、新しい nonce と時刻で署名し直す（B4-4 の 6）。`Range` は署名に含めない

#### Range と応答

| 場面 | 動作 |
|---|---|
| 新規 | `Range` なし。200 |
| 再開 | `Range: bytes=<pending のファイルの大きさ>-`（先頭からの途中までに限る。最後の区間の指定を使わない。B2-6） |
| 206 | `Content-Range` の開始が、送った位置（pending のファイルの大きさ）と同じことを確かめる。違えば取り直し |
| 200（Range を付けたのに全体が来た） | `"wt"` で最初から書き直す |
| 本文が短く正常に閉じた（`expected_size` に足りない） | E6 として取り直しに回す。取り直しても増えなければ（再開は 0 バイト、最初から書き直す取得は前の取得の受け取り量以下）E9（曲単位）。X6-2 の手順 7 |
| 200（P1 の本文の `format_version` が版違い） | E なし。同期を止め（`stoppedWithoutE`＝真）、T3 の `result_json` に `manifest_version_mismatch`＝真を残す。壊れた本文も E なしで止めるが、印は付けない（X6-3 の手順 4 の 3） |
| 416 | 最初から取り直す（B4-4 の 3） |
| 409 | E8 |
| 404 | E5 |
| 401（`detail=clock_skew`） | E2 とし、画面に「端末と PC の時計が違う」を出す（`key_mismatch` は偽。自動の抑止の印にしない。J35） |
| 401（`detail=replay`） | E2（`key_mismatch` は偽。J35） |
| 401（`detail` なし）、署名の失敗 | E2（`key_mismatch` は真。自動は再ペアリングまで止まる。J35） |
| 403 | E2。P5 の `pairing_closed`、`pairing_locked`、`device_exists`（X4、X7-1-3 が扱う）。同期（P1〜P4）では起きない（B4-4 の 8） |
| 429 | E2（署名の失敗の連続。V32 の間。`key_mismatch` は偽。J35） |
| 400 | E なし。端末の不具合として扱う（B4-4 の 8）。同期を止め、`error_kind` は空にして結果に残す。T3 の `result` は M1 の区分から写す（転送の前は `failed`、転送の後は `interrupted`）。M1 の区分には `stoppedWithoutE`＝真で渡す（X3-5） |
| 404（ルート不明）、405、413 | E なし。400 と同じに扱う（B4-4 の 8。`stoppedWithoutE`＝真） |
| 500 | E なし。PC の不具合として扱い、同期を止めて結果に残す（T3 の `result` は M1 の区分から写す。転送の前は `failed`、転送の後は `interrupted`。`error_kind` は空。B4-4 の 8。`stoppedWithoutE`＝真）。P3 の 500 も同じ（X6-3 の 2 の 4b。J45） |
| 503 | E4（P1 のとき。P2 でも、PC の曲の表が空のときは同期全体の失敗の E4）。P3 の 503（XML が読めない）も E4 で、その接続先で止めて T3 に残す（X6-3 の 2 の 4b。J45） |
| 切断、時間切れ | E6（V10 の再試行の対象）。到達確認（手順 2 の 2）の接続の確立の待ち（V29）と P3 の応答の待ち（V53）の時間切れは「応えない」で、ここには含めない（E6 は P3 が通った後の通信に限る）。P1 の受信中の切断も E6（曲の指定が無いので `persistentId` は無し。V10 の回数までマニフェストの取得を再試行し、超えたら同期全体を止める）。P3 が通った後の接続の確立の失敗も E6 に数え、P1 の接続の確立の失敗も同じく V10 の回数まで再試行する。再試行は同じ接続先だけに向ける（Wi-Fi が切れて別の回線に移っても、接続先は移らない。次の同期で到達確認からやり直す）。E1 は到達確認で全部の接続先が応えないときだけ |
| 証明書の不一致 | 到達確認の段では「応えない」と同じに扱い、次の接続先を試す。全部だめで 1 つでも不一致があれば E2（J36）。同期の途中の不一致は E2。どちらも `key_mismatch` は真で、自動は再ペアリングまで止まる（J28、J35）。ただし鍵そのものが変わった場合の「証明書が変わった」の案内（B4-3 の 1）は X7 が表示する |

### X6-6 鍵の保管 K3・K4

#### K3（署名用の共有の鍵）

| 項目 | 内容 |
|---|---|
| 取り込み | P6 の成功で確定する（J27）。失敗や離脱では T4 と Keystore に書かない。X4 の手順が返した 32 バイトの鍵を Android Keystore に取り込む。鍵の種類は HMAC-SHA256、用途は署名のみ。Keystore への HMAC の取り込みが使えることは（未確認。実機で確かめる。C-12） |
| 別名 | `psfox-k3-<device_id>`。T4 の `key_alias` に保存。別名の接頭辞は識別子で、製品名 KudagiTune（Q1）には連動せず、変えない |
| 取り出し | しない。署名は Keystore に依頼する（B4-3） |
| 取り込み後 | メモリ上の 32 バイトを上書きして捨てる（ガベージコレクタの都合で完全な保証はない） |
| 解除 | T4 の行を消す前に Keystore の別名を消す。順は「別名を削除 → T4 の行を削除」。途中で落ちたら、T4 の行が残る側に倒れる（再度の解除で完了する） |
| 再ペアリング | 端末は T4 が残る間 S2 へ入れないので（S1 の同期ボタンは S3 へ進む）、再ペアリングは S5 の解除（別名と T4 の行の削除）の後に行う。PC の W3 の解除も要る（X7-1-3 の案内）。別名は `device_id` で決まるので変わらない。解除の後の別名へ取り込み、成功したら T4 を作り直す。`paired_at` は新しい値にする（手順 2 の 1 の (b) の抑止はこれで解ける）。失敗したら T4 は作らず、PC の W3 で端末を解除してから再ペアリングをやり直す（P6 の後の Keystore・T4 の失敗と、X4-2-1 の D4 で落ちた場合も同じ。PC に登録が残るため、そのままでは P5 が `device_exists` になる。J27） |

- 別名が T4 にあるのに Keystore に無い（端末の変更、OS の鍵の破棄）ときは、E2 とし、再ペアリングへ誘導する。同期の始めは、到達確認の前に別名の有無を確かめ、無ければ P3 を送らず `key_mismatch`＝真の E2 で T3 に残す（X6-3 の 2 の 1b）。署名の失敗の例外から判断する

#### K4（SPKI のハッシュと PC の識別子）

- T4 の `spki_hash`、`pc_id` に持つ。内部領域に限る。バックアップの対象外（`allowBackup` を無効。B3-2）
- 更新は P6 の成功で確定するペアリング完了時だけ。失敗や離脱では T4 に書かない（J27）。同期の途中で書き換えない（接続先が変わるのを避ける）

#### CryptoProvider の端末側の実体

| 部品 | 実体の置き場 | 備考 |
|---|---|---|
| HMAC-SHA256（署名） | Keystore の K3 | X4-1 の入出力に従う |
| 乱数 | 標準の安全な乱数 | M1 は直接呼ばず、引数で受ける |
| SHA-256、HKDF、点演算 | ペアリングのときだけ使う。実体は X4-1 の表に従い、M4 が渡す | 同期の実行では使わない |

### X6-7 テストの観点

| 対象 | 種類 | 観点 |
|---|---|---|
| Room の移行 | 薄い統合（端末の実行環境。CI の対象外にしてよい。B1-3） | 旧版のスキーマから新版へ。T1、T5 の行が残る。破壊的再作成を使っていない。版 1 → 2 で T8、T9 が空で作られる |
| Room の取引 | 同上 | T1 の追加と T5 の削除が 1 取引。T3 の超過分の削除で T6 も消える。T3 の `result_json` の往復と `library_id`・`content_digest` の列、T6 の連番の主キー（同じ曲の別の `reason`、ID 無しの除外）、T4 の `last_endpoint` の更新と、解除で T7 の `device_id` が残ること |
| 曲の書き込みの手順 | 試験用の差し替えを使う単体 | OS の境界 `MediaStoreFiles`（interface）を試験で差し替え、`MediaWriter` の実物で、成功のときの結果の状態（T1 に読み戻した値の行、T5 の行が無い、pending でない）と、失敗の各点（行の作成、サイズ違い、読み戻した相対パスのずれ）の後の状態を確かめる。使用中のパス（T1 と MediaStore の既存パスを `resolveTrackPaths` に渡す結線）は接尾辞つきのパスで書くことを、`MediaStoreFiles` の挿入の入力（`RELATIVE_PATH`、`DISPLAY_NAME`）で確かめる |
| 曲を消す | 同上 | 成功と MediaStore に行が既に無いときは T1 の行を消す。`SecurityException` はその曲だけ E9、T1 の行は残る |
| 再開 | 同上 | 再開の判定表：`source_modified` が違う、T5 に URI が無い、URI が MediaStore に無い（T5 を消して新規）、`expected_size` が違うときは最初から。pending のファイルの大きさが `expected_size` と同じなら取得せず次へ。置き換えは常に最初から。再開の位置は pending のファイルの大きさ（T5 とずれる場合）。取得元が正常に閉じた短い本文は E6 で取り直しに回り、増えなければ E9 で次の曲へ進む（再開は 1 バイトも増えない場合、置き換えなど毎回最初から書き直す曲は前の取得の受け取り量から増えない場合。pending の行と T5 が消える。review-15） |
| ワーカーの手順 | 単体（HTTP と `MediaStoreFiles` を差し替え。`MediaWriter` と M1 は実物） | E1〜E9 の各動作（E6 は行と T5 を残す、E3 の途中は削除。曲単位の E5・E8・E9 は次の曲へ進み、失敗の一覧（T6 の `failed`）に残す）。始めの整理。「消す」の扱い（自動の `Allowed`、確認なし、確認の取り消し、同期全体の失敗の後、`library_id` の違いと承認後の記録の更新）。自動の抑止（V19 は手動の `success`・`partial` の後だけで、失敗した手動の後は抑止しない、鍵の不一致の E2 だけ。`clock_skew`・`replay`・429 は抑止しない、E3、同じ `content_digest`）と、抑止で終えたとき T3 に残らないこと、前面の通知を出さないこと。手動の前面への昇格は開始直後で、自動は抑止の判定の後。手順 2 の 1b、3、4、4b で閉じた行（手動の E1・E2、自動の E2、P3 の 503（E4）・500）は T3 に残り、`finished` と終了の通知が出ること（自動は静かな通知）。差分が空で、前回の完了した同期（`content_digest` が NULL でない最新の行）が `success` かつ同じ `content_digest` なら m3u8 を書かず T3 だけ記録する。`setForeground` が例外のとき（手動・自動とも）`Result.success` で終え T3 に残さない。停止の理由から E7 と利用者の中断を決める関数。E7 と利用者の中断の後の T3（`interrupted`。`error_kind` は E7 か空。T5 を残す。T3 の更新は必須で、m3u8 は時間があれば書く。E7 の通知は「続きは次の同期で」）。M1 の区分と `result` の対応（E なしの停止は `stoppedWithoutE` で「失敗」、転送の後は「中断」、`mayRemove` は偽。区分から T3 の `result` への写しは M4 の手順）と、`not_started` の P4 への畳み（M4。初回の報告と再送）。E8 の終わりのやり直し（取り直しの後に成功か、再び E8 で結果に載る。「消す」の判定と T3 の `content_digest`・`library_id` は取り直した側で決める。取り直した差分の容量の確認、取り直しの P1 の失敗は同期全体の失敗で `content_digest` が NULL） |
