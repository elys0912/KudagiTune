# playlist-sync-fox テスト計画 desktop

担当の束は束 4（desktop。API の P1〜P6 と区別する。X5 のサーバー・鍵・設定・ログ・mDNS・状態と、X2-4 の監視と読み直し）。

## 1. 方針

- 束の中ではコンパイル（typecheck）だけを回す。テストは束 4 の最後に、`:desktop` のテストだけを 1 回回す。全件は CI（GitHub Actions、ubuntu。`./gradlew build :android:assembleDebug` と依存の向きの検査）に任せ、実装と全件テストの繰り返しはしない
- desktop は薄く保つ（B4-8）。署名の検証・差分・鍵の導出は shared のテストの担当で、ここでは書かない。サーバーのルートは shared の検証を呼ぶ結線だけを少数で確かめる。画面は「PC の状態」から表示を作る部分だけを試し、Compose の見た目のテストは持たない
- 層は 2 つ。単体（JVM のみ）と薄い統合（JVM。一時フォルダ、記憶の中の `SecretStore`、テスト用のサーバー。実ネットワークと実の資格情報マネージャーは使わない）
- テストは振る舞いだけを確かめる。起こり得ない入力の検証、モックの戻り値の確認、実装の写経は書かない。1 つのテストは 1 つの観点。名前は日本語で「何を・どうすると・どうなる」
- 試料はすべて合成。実在の曲名・パス・ID・IP・ドメインを使わない（IP は 192.0.2.0/24、名前は example.invalid）
- 時刻と乱数は引数で固定する（固定の時計、固定乱数 X4-5）。読み直しのテストは実際の待ちを使わず、時刻と待ちを差し替える
- Windows の実環境が要るもの（C-13：DPAPI、Run キー、Windows の WatchService、仮想アダプタと JmDNS。ほかに jpackage の zip）は CI の対象外とし、4 に代わりと手順を書く
- 実機確認は Android 14 の端末（C-6・C-10 は今後対応）。C-13（PC の実環境）は 4 の手順で手元の Windows で 1 回行う

## 2. テストケースの一覧

試験の部品：記憶の中の `SecretStore`、固定の時計、一時フォルダ、固定乱数、時刻と待ちの差し替え。V の値は設計の置いた値の名前で書き、実装時に定数を参照する。

### C-13 の手順（手元の Windows で 1 回）

- 時期：束 4 の実装の後、1 回まとめて行う。試料は合成のライブラリ。実在の曲は使わない
- 記録：B4-8 の別ファイルの表に、状態（確認済み、不可（理由））、日付、OS の版、アプリの版（sha）。曲名・パス・IP は書かず、成否と件数だけ
- 順序：1）DPAPI（上の表の手順）2）Run キー 3）WatchService（TD-43〜45 を実行し、通知の数と種別を記録。実物の iTunes での再読も 1 回）4）仮想アダプタと JmDNS（広告するインターフェースの数と、端末から見つかるか）
- 合格：各行の手順の条件を満たす。記録する値は、成否、通知の数と種別、広告したインターフェースの数
- jpackage の zip と二重起動・終了の順は C-13 の外だが、同じ機会に確かめる
