## 論点

### Q1 正式名

- 論点：仮名 playlist-sync-fox は屋号のような名で、正式名ではない。正式名を何にするか
- 条件：商標に当たる語（iTunes、Apple、Android、Tailscale など）を含めない。機能の説明に使うときは名前の外で書く
- 推奨（暫定）：未決。先に機能を固める
- 決める時期：基本設計の最後
- 基本設計・詳細設計の結論（2026-11-05）：変更なし。未決のまま。先に機能を固めた結果、正式名は決めていない。

### Q2 USB の方式

- 論点：USB 接続を、端末が `localhost:port` でつなぐ形にするか、IP 経由にするか
- 案：
  - a：adb を PC アプリに同梱し、`adb reverse tcp:port tcp:port` で端末の localhost を PC のサーバーへ向ける。端末は USB デバッグの有効化が要る
  - b：USB テザリング（端末が PC に IP を配る）で、LAN と同じサーバーへつなぐ。adb は不要。端末側の設定が 1 段増える
  - c：a と b の両方を持つ。実装と説明が増える
- 比較：

| | a | b | c |
|---|---|---|---|
| 端末側の準備 | USB デバッグ | テザリングの有効化 | どちらか |
| 同梱物 | adb（platform-tools） | なし | adb |
| 実装 | 起動と監視 | 追加なし（LAN と同じ） | a と b の合計 |
| 端末の露出 | USB デバッグが常時有効で、つないだ PC から端末を操作できる | テザリングの間だけ IP で見える | a と同じ |

- 確認事項：platform-tools のライセンスは不要になった（adb を同梱しない）
- 推奨：b。USB テザリングを USB の正にする。adb は後で足せる
- 決める時期：決定済み（2026-11-05 先生、review-01 の J3）

### Q3 形式の変換

- 論点：ALAC などロスレスや、端末が再生できない形式を、送る前に変換するか
- 案：
  - しない：ファイルをそのまま送る。実装が最小
  - PC 側で ffmpeg：全曲を指定の形式に変換する。容量は減るが、変換の時間とキャッシュが要る
  - 端末が再生できない形式だけ変換：端末の対応形式を端末が申告する
- 論点の補足：
  - Android の標準で ALAC を再生できるかは端末とプレイヤーに依存する（未確認）
  - ffmpeg の同梱はライセンスの確認が要る（未確認）。ビルドの構成で GPL 扱いになる場合がある
- 推奨（暫定）：しない。変換を PC 側に置く余地だけ残す（たたき台の 4）
- 決める時期：基本設計の前半
- 基本設計・詳細設計の結論（2026-11-05）：変換はしない（D10）。

### Q4 MediaStore への反映の仕方

- 論点：端末のプレイヤーに、プレイリストを見せる方法
- 案：
  - m3u8 を置いてメディアスキャンに任せる：相対パス・UTF-8 の m3u8 を書く。Android 11 以降のスキャンが m3u を索引する見込み（未確認）
  - `MediaStore.Audio.Playlists` に直接書く：API 31 で非推奨。将来の互換が読めない
  - 両方：確実だが、二重登録と削除の整合を持つ
- 確認事項：端末と主なプレイヤーで、置いた m3u8 が MediaStore のプレイリストになるか（実物の確認 2）。ならなければ、案を見直す
- 推奨（暫定）：m3u8 を置いてスキャンに任せる。直接書き込みは使わない。D3 はこの形に書き換えた（review-01 の J6）
- 決める時期：実物の確認の後
- 基本設計・詳細設計の結論（2026-11-05）：m3u8 を `MediaStore.Files` に置き、索引に任せる。`MediaStore.Audio.Playlists` への直接書き込みは使わない。根拠は B3-3、X6-2（`Audio.Media` は playlist の MIME を拒否する。facts-android 3-1）。実機での索引と表示の確認は C-2 に残る。
- 状態（2026-11-06）：暫定。C-2・C-3 の実機の確認の結果で見直す（review-13 の J41）。

### Q5 TLS と鍵の保管

- 論点：通信の保護の形と、鍵をどこに置くか
- 案：
  - 自己署名の証明書を端末で固定：ペアリング時に端末が証明書を保存し、以後それだけを信頼する（trust on first use）
  - 平文 TCP と署名だけ：実装は軽いが、内容が LAN で見える
  - Tailscale のときは TLS を省く：Tailscale が経路を暗号化するので二重になる。ただし接続方式ごとの分岐が増える
- 鍵の保管：端末は Android Keystore、PC は Windows の DPAPI。保管の細部は基本設計
- 比較：

| | 固定 | 平文＋署名 | Tailscale だけ省く |
|---|---|---|---|
| LAN での盗聴 | 防げる | 防げない | LAN は防げる |
| 実装 | 中 | 小 | 分岐が増える |
| 方式ごとの分岐 | なし | なし | あり |

- ペアリングコードの扱い：コードは平文で送らない。両側がコードから導いた鍵で互いを確かめる（PAKE などの方式は基本設計）。PC の証明書の確認コードを両方の画面に出して見比べられるようにする
- 推奨（暫定）：自己署名＋固定。全方式で同じ形にする（たたき台の 3）。ペアリングコードの扱いも含む
- 決める時期：基本設計の前半
- 基本設計・詳細設計の結論（2026-11-05）：自己署名の TLS を使い、証明書の公開鍵情報（SPKI）を固定する。ペアリングは SPAKE2 で行い、点演算に Bouncy Castle を使う。PC の鍵は DPAPI で保護した `secrets.bin` に置き、端末の鍵は Android Keystore に置く。根拠は B4-2、B4-3、X4、X5-2（J11、J16、J17）。

### Q6 同期の自動起動の条件

- 論点：同期を、いつ始めるか
- 案：
  - a：従量制でないネットワークにつながったとき（WorkManager の制約）に起動し、ペアリング済みの PC に届かなければ何もせず終わる
  - b：SSID を見る（Android 10 以降は正確な位置情報の権限と常駐の監視が要る）
  - c：手動だけ
  - d：PC から端末へ知らせる（pull の方針と合わない）
- 確認した事実：WorkManager の制約に SSID は無い（review-01 の確認した事実）
- 補足：Android 15 以降、dataSync の前面サービスは 24 時間に合計 6 時間で止められる（review-01 の確認した事実）。長い同期は数回に分かれる
- 推奨：a
- 決める時期：決定済み（2026-11-05 先生、review-01 の J2）
- 2026-11-06 に D13 を周期の形に直した（J40）。案 a の「つながったとき」は、決定前の案の記述として残す

### Q7 端末側の保存先

- 論点：取得した曲をどこに書くか
- 案：
  - `Music/<アプリ名>/…` を MediaStore 経由で書く：権限が少なく、プレイヤーから見える。端末は自分が置いた曲だけを消す
  - SAF でユーザーが選ぶ：場所は自由だが、選択の画面と権限の保持が要る
  - SD カード：容量は大きいが、端末による差が大きい（未確認）。SAF の経由になる見込み
- 補足：MediaStore 経由で置いたファイルは、アプリを入れ直すと所有が切れ、変更と削除に利用者の同意の画面（createDeleteRequest など）が要る（review-01 の確認した事実）。入れ直しの後は以前の曲を「自分が置いた」と扱わず、消すときだけ同意の画面を出す（D14、2026-11-05 先生）
- 推奨（暫定）：`Music/<アプリ名>/…` を MediaStore 経由で書く。SD カードは SAF の案に含めて後で判断する
- 決める時期：基本設計の前半
- 基本設計・詳細設計の結論（2026-11-05）：保存先は `Music/<アプリ名>/<アーティスト>/<アルバム>/` とし、ファイル名の規則を設ける。根拠は B3-1、B3-3。
- 決定（2026-11-06 先生。review-13 の J41）：結論のとおり。

### Q8 複数の端末

- 論点：1 台の PC に複数の端末をペアリングし、端末ごとに同期するプレイリストを選べるか
- 案：
  - 1 台だけ：ペアリングを 1 件にする。最小
  - 複数ペアリング・同期するプレイリストは全端末で共通
  - 複数ペアリング・端末ごとにプレイリストを選ぶ：PC 側に端末ごとの設定を持つ。画面が増える
- 論点の補足：pull 型なので、同期状態は端末ごとに端末の DB（Room）が持つ。選択は端末が持つ（D15。2026-11-07 に PC から端末へ移した）。PC は端末ごとの選択を持たない
- 推奨：a：最初の版は 1 台だけ。同期状態と PC 側の設定に端末の識別子の列を持たせ、後で増やせる形にする
- 決める時期：決定済み（2026-11-05 先生、review-01 の J1）

### Q9 複数の PC

- 論点：最初の版では 1 台の PC だけを対象にする。端末が複数の PC とペアリングできるようにするか。端末の同期状態を PC ごとに分けるか
- 案：
  - 1 台の PC だけ：ペアリングを 1 件にする。同期状態は分けない
  - 複数の PC を許し、同期状態を PC ごとに分ける：別の PC の曲を消さない。管理の画面が増える
  - 複数の PC を許し、同期状態を共通にする：PC 間で曲の ID が一致しないので、誤って消す
- 推奨：未決。最初の版は 1 台だけとし、将来は PC ごとに分ける案を採る前提で、状態の表に PC の識別子の列を持たせるかを基本設計で決める
- 決める時期：基本設計の前半
- 基本設計・詳細設計の結論（2026-11-05）：未決のまま。端末側の library_id を確認する仕組みで、複数の PC に備える（B2-5、X3-2）。

### Q10 変更の検知

- 論点：曲のファイルが変わったことを、何で見つけるか
- 案：
  - サイズ＋更新日時：ファイルの属性だけで足りる。高速
  - ハッシュ：内容で確実に判定できる。全曲の読み込みが要り、初回が遅い
  - iTunes の Date Modified：XML から取れる。ファイルを触らない。タグだけの変更にも反応する（コメントの変更で変わり、元に戻しても元の値に戻らない。2026-11-06 の実物の確認）
- 比較：

| | サイズ＋更新日時 | ハッシュ | Date Modified |
|---|---|---|---|
| コスト | 小 | 大 | 小 |
| 見逃し | 同じサイズで日時が戻る場合 | なし | ファイル差し替えで変わらない場合（未確認） |
| 誤検知 | 日時だけ変わる操作 | なし | タグ編集でも変わる |

- 推奨（暫定）：サイズ＋更新日時。必要ならハッシュを足す（たたき台の 4）
- 決める時期：基本設計の前半
- 基本設計・詳細設計の結論（2026-11-05）：サイズと更新日時で判定する。値は実ファイルのものを使う。ハッシュは使わない。
- 決定（2026-11-06 先生。review-13 の J41）：結論のとおり。

### Q11 Apple Music アプリのライブラリの読み方

- 論点：Windows の Apple Music アプリには、ライブラリを XML に書き出す機能が無い見込み（実物の確認 1）。D1「両方に対応、入口は XML」の Apple Music 側をどう満たすか
- 案：
  - a：最初の版は iTunes 12.x だけを対象にする。Apple Music アプリの対応は、方法が見つかるまで保留。D1 を「iTunes 12.x。Apple Music アプリは保留（Q11）」に直す
  - b：Apple Music アプリの `Library.musicdb`（文書化されていないバイナリ）を解析して読む。版が変わると壊れる。公式の保証が無い
  - c：Mac で書き出した XML を Windows に持ち込む運用（パスの書き換えが要る）。Mac を持つ人だけの手段
  - d：Apple Music アプリの「プレイリストの書き出し」（あれば）を使う。実物で確かめていない
- 決定：a（2026-11-05 先生）。D1 を書き換えた。d は先生の手元で有無を確かめ、あれば案に足す
- 決める時期：決定済み（Apple Music の対応を再開するときに b〜d を見直す）
- 基本設計・詳細設計の結論（2026-11-05）：Q11 は保留のまま。

### Q12 配布の形

- 論点：PC と Android の配布方法、署名、更新の知らせ方
- 案（PC）：
  - JVM 同梱のインストーラ：利用者が JVM を入れなくてよい。サイズが大きい
  - zip：展開して使う。JVM の用意が要る
- 案（Android）：
  - APK の直接配布：審査はないが、提供元不明のアプリの許可が要る
  - Play ストア：審査と登録費用が要る。自動更新が使える。審査の内容は未確認
- 論点の補足：
  - 署名：PC は署名なしだと警告が出る。署名の有無と費用は未確認
  - 更新の知らせ方：アプリ内で版を確認するか、配布ページの案内に任せる
- 推奨：最初は GitHub で公開する。repo は最初 private、公開の前に public。配布物は Releases に置く。アプリ内の更新の確認はしない。Play ストアは将来の対応（D12）
- 決める時期：形（インストーラか zip か）と署名は基本設計の前半
- 基本設計・詳細設計の結論（2026-11-05）：PC は jpackage で作った zip、Android は署名つき APK とし、どちらも Releases に置く。公開は手動で行う。根拠は B4-7、J13（review-03）。
