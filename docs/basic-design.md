### B1-1 文書の読み方

構成と置き場：

- 節は B1〜B4、節の中の項は B2-1 のように書く。固定の 4 節で、増やさない。末尾の「Q の割り付け」と「要件の割り付け」の 2 表は節に数えない
- B1 は節末の見出し（下の「節末の見出し」）を持たない。要判断と他の節への依頼は B1-9 の後ろに置く
- 実 IP、実ドメイン、認証情報、個人名は書かない。例は `192.0.2.0/24`、`example.invalid` の形にする

冒頭の行：

- B1（このファイル）は起票、状態、前提、置き場の 4 行を置く。状態の行に節ごとのファイルの場所を書く（B1-2）
- B2〜B4 は索引、稿、参照の 3 行を置く。索引は B1 へのリンク、稿はその節の稿と日付、参照は他の節のファイルへのリンク

番号と参照：

| 接頭辞 | 指すもの | 採番する節 |

| F、N | 概要設計の要件 | [requirements.md](requirements.md) |
| D | 概要設計の決定 | [README.md の決定事項](design-overview.md#決定事項) |
| Q | 論点 | [open-questions.md](open-questions.md) |
| M | モジュール | B1-3 |
| V | 値の表の行 | B1-7 |
| T | 同期状態の表（Room） | B3 |
| S | 画面（Android） | B3 |
| P | サーバーの API のルート | B4 |
| W | 画面（PC） | B4 |
| K | 鍵と保管場所 | B4 |
| E | エラーの種類 | B2 |

- 項は Bn-1、Bn-2 …。項の中の小見出しは「」で指す（例：B2-3 の「再開」の 2）
- 概要設計への参照は F1-7、N3-2、Q4、D9 の形で書く
- 節をまたぐ参照は項の番号だけで書く（「B4-2」）。ファイルは各節の冒頭の参照の行と B1-2 で引く
- 番号は勝手に増やさない。足したいときは「Bn の他の節への依頼」に書き、採番する節が付ける

値の表 V の使い方：

- 値（上限、秒数、回数、サイズ）は本文に直書きせず、B1-7 の V に一本化する
- 各節は「V の表の n」の形で参照する（例：「V3」）。同じ値を別の項の表に写すときは「（V3）」と添える
- 各節は自分の節で使う値を、節末の「B1 への依頼」に列挙する（項目、使う場所、希望する形）。B1 の執筆者が集めて V に足す
- 仮の値は「暫定」と書く。確かめた事実（OS の制約など）は V に入れず、B1-7 の表の後ろの「固定の事実」に置く
- 値を決めるのは基本設計のレビューの後。決めた値は requirements.md へ戻すかを別途諮る

決定と暫定の書き方：

- 概要設計の決定は変えない。再掲するときは「決定：（内容）（D6）」と書く。「決定：」は D 番号のあるものだけに使う
- 基本設計で新しく決めたものは「決定（未付番）：（内容）」と書き、根拠を添えて B1-9 の一覧に載せる。先生が承認したら README の決定事項へ D 番号を付けて移す
- 推奨にとどまるものは「暫定、Qn」と書く。Q 番号が無い値は V の番号を書く
- 新しい論点は作らず、各節の「Bn の要判断」に J 候補として書く

節末の見出し（B2〜B4。順も同じ）：

- 「Bn の Q の結論」「Bn の要判断」「Bn の他の節への依頼」「Bn の B1 への依頼」「Bn の確かめた事実」
- 該当が無い見出しは「なし」の 1 行だけを書く
- 公式文書で確かめていないことは本文に「（未確認）」と添える。確かめたものは「確かめた事実」に出典の名と取得日を書く

語：

- 用語は [README.md の用語](design-overview.md#用語) に従い、造語しない
- 「端末」は Android の機器、「PC」は Windows の機器。「サーバー」は PC 側、「クライアント」は端末側（D6）

### B1-3 モジュールの構成

1 つの repo を Gradle のマルチプロジェクトで構成する（N5-4、D4）。モジュールは 4 つで、増やさない。

| M | 名前 | 種類 | 依存 |
|---|---|---|---|
| M1 | shared | KMP（JVM と Android を対象） | なし（OS の API に触れない） |
| M2 | itunes | JVM | M1 |
| M3 | desktop | JVM（Compose Multiplatform の PC 向け） | M1、M2 |
| M4 | android | Android（Jetpack Compose） | M1 |

依存の向き：

```
desktop ──▶ itunes ──▶ shared ◀── android
   └────────────────────▲
```

- 矢印は「依存する」向き。shared は誰にも依存しない。itunes と android は互いを知らない。desktop は android を知らない（逆も同じ）
- 循環と、M3 から M4 への依存を禁止する。Gradle の依存の宣言で保ち、CI で確かめる（B1-6）

責務（持つもの、持たないもの）：

| M | 持つもの | 持たないもの |
|---|---|---|
| M1 | マニフェストと API の型、差分の計算（足す、置き換える、消す）、m3u8 の生成、保存先のパスの組み立てと使えない文字の置き換え、ペアリングと署名の手順（暗号の実体は `CryptoProvider` として引数で受ける）、エラーの種類 E の型 | ファイルと通信の入出力、時計と乱数の直接の利用（引数で受ける）、暗号の部品の実体、画面、OS の API |
| M2 | plist XML の読み取り、`file://` の復号、Persistent ID と Track ID の対応、プレイリストの展開、XML の更新の検知に要る値の取り出し | HTTP、画面、同期の判断（除外の規則は M1 の型で返す。M2 は判定の材料を返し、除外の理由の確定は M3。review-05 の基本設計の直し 16） |
| M3 | HTTP サーバー、mDNS の広告、TLS の証明書の読み書き、鍵の保管（DPAPI で暗号化したファイル `secrets.bin`。review-05 の基本設計の直し 2）、トレイの常駐と画面、設定とログの書き込みと読み取り、XML の監視の起動、`CryptoProvider` の実体（PC 側） | 差分の判断、m3u8 の生成、plist の解釈 |
| M4 | HTTP クライアント、NSD、Room、MediaStore への書き込み、前面サービスと WorkManager、通知、画面、権限、Keystore、`CryptoProvider` の実体（端末側） | 差分の判断、m3u8 の生成、署名の手順の中身 |

- 判断（差分、m3u8、署名の手順、除外の規則）は M1 と M2 に置き、M3 と M4 は薄く保つ（N5-2）
- 暗号は、手順を M1 が持ち、実体を `CryptoProvider`（鍵の導出、署名、鍵の参照版の HMAC、乱数、点演算の部品。review-05 の基本設計の直し 16）として M3 と M4 が渡す（決定（未付番）、B1-9 の 11。B4-2）
- M1 の入出力は純粋な関数にそろえる（N5-1）。時刻は引数で受ける

テストの置き場：

| M | テスト | 種類 |
|---|---|---|
| M1 | 差分、m3u8、パスの組み立て、署名と再送防止、型の直列化 | 単体（JVM で実行。実機なし）。テストの中心 |
| M2 | 日本語名と記号を含む `file://` の復号、XML の欠損、スマートプレイリスト、数万トラックの時間（V7） | 単体。試料の XML は匿名の合成データ |
| M3 | 設定の読み書き、サーバーの経路（鍵なしの拒否、パスを受けない）、ログの上限 | 薄い統合（JVM。実ネットワークは使わない） |
| M4 | Room の移行、保存先の書き込みの境界 | 薄い統合（端末の実行環境が要るものは CI の対象外とし、実機確認の表へ） |
| 実機 | mDNS、MediaStore への反映、各プレイヤーでの m3u8、Tailscale の名前解決、テザリング | 確認の表 C-1〜C-12（N5-3。置き場は B4-8） |

### B1-4 技術の選定

版は書かない（版は repo の定義に置く）。名前、選んだ理由、代案の順に 1 行ずつ。

| 用途 | 名前 | 選んだ理由 | 代案 |
|---|---|---|---|
| 共有の言語 | Kotlin Multiplatform（KMP） | PC と端末で差分と署名を 1 つのコードにできる（D4） | 各側で別に書く。型のずれが出る |
| 型の直列化 | kotlinx.serialization | KMP で動き、マニフェストと API の型を M1 に置ける | Gson、Moshi。JVM 専用で M1 に置けない |
| HTTP のサーバー | Ktor（サーバー） | Kotlin で書け、Range と TLS を扱える（Range の細部は未確認） | JDK の HttpServer。Range と TLS を自前で足す |
| HTTP のクライアント | Ktor（クライアント） | 型を M1 と共有でき、中断の再開を書ける | OkHttp。Android では定番だが、型の共有に別の層が要る |
| 同期状態の DB | Room | Android 標準の流れで、移行の仕組みを持つ（D11 の識別子の列を T で持つ） | SQLDelight（KMP で使えるが、この用途では M4 だけで足りる） |
| 自動の起動 | WorkManager | 条件（従量制でない、など）を付けて起動できる（D13）。SSID の制約は無い | AlarmManager、JobScheduler 直接。条件の扱いを自前で書く |
| PC の画面 | Compose Multiplatform | M4 の画面と同じ書き方で、トレイ常駐の小さな画面を作れる（D4） | Swing、JavaFX。M4 と別の書き方になる |
| 端末の画面 | Jetpack Compose | 標準で、Compose Multiplatform と書き方がそろう | View による画面。書き方がそろわない |
| mDNS（PC） | JmDNS（Java で mDNS を扱える） | JVM で追加の常駐物なしに広告できる（動作は B4-1 で確かめる。未確認） | 自前の mDNS の実装、Windows の Bonjour。導入と保守が増える |
| mDNS（端末） | NSD（Android 標準） | 追加の部品が要らない | JmDNS を端末で動かす。電力と権限の扱いが増える |
| plist の読み取り | JDK の XML の読み手（StAX か DOM。暫定） | 追加の依存が無く、plist の形が単純 | plist の専用ライブラリ。依存が増える（B2-1 で決める） |
| ビルド | Gradle（Kotlin DSL）、版は version catalog に一本化 | KMP と Android の標準 | Maven。KMP と Android の対応が弱い |
| テスト | kotlin.test と JUnit | M1 を JVM と Android の両方で書ける | Kotest。依存が増える |
| CI | GitHub Actions | repo が GitHub（D12）で、Releases への添付まで同じ場所で行える | 手元のビルドだけ。再現できない |
| PC の配布物 | jpackage のアプリイメージの zip、コード署名なし（Q12。B4-7） | 追加の導入が要らず、Windows の実行環境で CI が作れる | インストーラ。WiX などの前提が増える（未確認） |
| 点演算の部品（SPAKE2 用） | Bouncy Castle の楕円曲線の演算。SPAKE2 の手順は M1（J16。review-05 の基本設計の直し 3） | ペアリングの方式（J11）が楕円曲線の点演算を要する。手順の組み立てだけが自前（RFC 9382 の試験ベクターで検算） | 自前の点演算（誤りの余地が大きく避ける）、BC の J-PAKE（3 往復になる）、第三者の SPAKE2 ライブラリ（保守は未確認） |
| 資格情報の保管（PC） | DPAPI で暗号化したファイル（`secrets.bin`）。呼び出しは JNA の `Crypt32Util`（J17。B4-3。review-05 の基本設計の直し 2） | 鍵を平文のファイルに置かない（N1-4）。JNA の platform に資格情報マネージャーの束縛が見当たらず、1 項目の上限は 2560 バイト（確かめた事実） | 資格情報マネージャーを自前の束縛で呼ぶ（構造体の束縛を持つ） |
| ライセンス一覧の生成 | Gradle のプラグイン（名前は B4-7 で選ぶ。未確認） | 使う OSS のライセンスの集計をビルドに入れる（N4-4） | 手で一覧を保つ。更新を忘れる |

- ペアリングの方式は SPAKE2（J11）。点演算の実体は Bouncy Castle、手順は M1、`CryptoProvider` の実体は M3・M4（B1-3、B4-2。review-05 の基本設計の直し 3）
- Room は M4 だけに置く。M1 に永続化を持たせない（B3 への依頼 1）

### B1-6 ビルドと CI

Gradle のマルチプロジェクト（N5-4）：

- ルートに設定を置き、サブプロジェクトは `shared`、`itunes`、`desktop`、`android` の 4 つ（B1-3）
- 版は version catalog に 1 か所で持つ。Kotlin、Ktor、Compose の版を合わせる責任は repo にあり、文書には書かない
- Gradle の wrapper を repo に含め、JDK と Android の SDK の版は定義ファイルで固定する
- M1 の対象は JVM と Android。iOS など他の対象は足さない（決定（未付番）、B1-9 の 2）

GitHub Actions（暫定。細部は B4-7 と B4-8）：

| 契機 | 内容 |
|---|---|
| プルリクエストと main への push | 型の検査（全モジュールのコンパイル）、M1 と M2 と M3 のテスト、依存の向きの検査（B1-3）、M4 のデバッグビルド |
| タグ（版の印）の push | M4 のリリースビルド（署名つき APK）、M3 の配布物（jpackage のアプリイメージの zip。Windows の実行環境で作る）、下書きの Release の作成と配布物の添付 |

- APK の署名の鍵と資格情報は GitHub の Secrets に置き、環境変数で渡し、ログに出さない（保管の細部は B4-7）
- Releases への添付は、タグの push を契機に実行し、下書きの Release を作るところまでを CI が行う。公開は手動（B4-7）
- repo は最初 private、公開の前に public にする（D12）。private の間も同じ流れが動く
- アプリ内の更新の確認はしない。新しい版は Releases の案内に任せる（F6-4、D12）
- 使う OSS のライセンスを集めてアプリ内に表示する工程を、ビルドの一部に入れる（N4-4。Gradle のプラグイン。細部は B4-7）
- PC の配布物は、jpackage のアプリイメージを zip にしたもの。コード署名はしない（Q12、J13）
- 実機でしか確かめられないものは CI の対象外とし、確認の表に残す（N5-3）

固定の事実（V に入れない。外部の制約。review-01 の確認した事実）：

- Android 15 以降、dataSync の前面サービスは 24 時間に合計 6 時間で止められる。V17 と B3-5 はこれを前提にする
- WorkManager の制約に SSID は無い。D13 は SSID を見ない
- 自動の起動が失敗したときの再試行の間隔は WorkManager の既定に任せる（V に入れない）

V の扱い：

- V の番号は固定。各節は V の番号で参照し、名前では参照しない。追加は B1 の執筆者だけが行う
- V1 と V7 は要件の文言にある値。要件の文言との差が出たら要件を直す候補にする
- V2〜V4 の組み合わせ（総当たりの余地）は B4-2 が検証する
- 走査の同時接続数と待ち時間の値は、走査を持たない（J12）ので置かない
- 値の単位（秒、分、MB、世代）は表のとおり。節は単位を変えずに参照する

## B1 の確かめた事実

- 概要設計（README、requirements、open-questions、review-01）と、たたき台の 5（モジュールの分け方）を読んだ（2026-11-05）。KMP の対象、Ktor、Room、JmDNS の動作は公式文書で確かめていない（未確認）

  - 4a：RFC 9382 は Informational。IRTF の CFRG の成果で、標準化過程の文書ではない（出典：RFC Editor「RFC 9382」）
  - 4b：Bouncy Castle 1.80 の仕様書に SPAKE2・CPace・OPAQUE・J-PAKE のいずれも載らず、BC 側の SPAKE2 の実装は見つからなかった。パッケージの一覧とソースの直接確認は未実施（出典：Bouncy Castle 1.80 specifications.html）。このため点演算だけを BC に求め、SPAKE2 の手順は M1 に置く（J16）
  - 5a：JNA 5.14.0 の Advapi32 の Javadoc に CredRead・CredWrite・CredDelete は無い。別のクラスにある可能性は未確認（出典：JNA 5.14.0 Javadoc）。このため DPAPI の `Crypt32Util` を使う（J17）
  - 5b：資格情報マネージャーの `CredentialBlob` は 2560 バイトを超えられない（出典：Microsoft Learn「CREDENTIALW」）
