# 0005 ペアリングは SPAKE2 で行い、通信は自己署名 TLS の公開鍵を固定する

## 背景

方針（初回にペアリングコードを入力し、端末が証明書を固定する）は 2026-11-05 に決まり、方式の細部（SPAKE2 と点演算の部品）は同日の設計レビューで決まった。

PC がサーバーとして曲を配る（0001）ので、LAN の中でも誰にでも配ってはならない。端末と PC を最初に結びつける方法と、その後の通信の保護を決める必要があった。
設計の途中で、Bouncy Castle には SPAKE2 も CPace も無く（J-PAKE は有る）、純 Java の SPAKE2 の実装は第三者の 1 件だけで保守の状況を確かめられないと分かった。

## 決定の要因

- LAN の中でも、鍵なしでは配信しない
- ペアリングコード（6 桁）を平文で送らず、盗聴 1 回でコードが割れる方式を避ける
- 接続方式（LAN・Tailscale・USB）ごとに保護の形を分けない
- 自前で書く暗号の範囲を小さくする

## 検討した選択肢

### 案 A：自己署名 TLS（証明書の公開鍵を端末が固定）と SPAKE2 によるペアリング。点演算は Bouncy Castle、手順は自前

- 良い点：LAN の盗聴を防げる。方式ごとの分岐が無い。自前なのは SPAKE2 の手順の組み立てだけで、RFC 9382 の試験ベクターで検算できる
- 悪い点：手順を自分で組むので、誤りの余地が残る

### 案 B：コードを HKDF で伸ばして使う簡易案

- 良い点：実装が小さい
- 悪い点：盗聴 1 回でコードが割れる

### 案 C：平文 TCP と署名だけ、または Tailscale のときだけ TLS を省く

- 良い点：実装が軽い（平文＋署名）。Tailscale の経路の暗号化と二重にならない（省く案）
- 悪い点：平文＋署名は内容が LAN で見える。省く案は接続方式ごとの分岐が増える

### 案 D：Bouncy Castle の J-PAKE、または第三者の SPAKE2 ライブラリ

- 良い点：部品が既にある
- 悪い点：J-PAKE は 3 往復になり、ペアリングの往復の設計を組み直す必要がある。第三者のライブラリは保守が確かめられない

## 決定

案 A。初回に PC が表示するペアリングコードを端末へ入力し、SPAKE2 で互いを確かめる。端末は PC の証明書の公開鍵情報を保存し、以後それだけを信頼する（trust on first use）。
点演算の実体は Bouncy Castle の楕円曲線（P-256）とし、手順は共有モジュールに置く。両方の画面に PC の証明書の確認コード（公開鍵のハッシュ）を出し、見比べられるようにする。

## 結果

### 良い面

- 全方式で同じ保護になり、鍵なしでは配信しない
- コードを平文で送らず、盗聴からコードが割れない
- 暗号の部品は既存のものを使い、自前の部分は試験ベクターで検算できる

### 悪い面

- PC の証明書が変わると、端末は信頼を外して再ペアリングが必要になる
- 手順の実装の正しさは、自前のテストと試験ベクターに頼る
- 端末は 1 台の PC としかペアリングしない（0012）

## 適用範囲と決めないこと

- 効く範囲：ペアリングの方式、通信の保護、証明書の固定
- 決めないこと：PC 側の鍵の保管（0006）、Android の鍵の保管の細部、ペアリングコードの有効期間の値
