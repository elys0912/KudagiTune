# 0001 PC をサーバー、端末を pull のクライアントにし、接続を 1 つのサーバーへの TCP に揃える

## 背景

決定は 2026-11-05 に確定した（USB の方式だけ、同日の設計レビューで確定）。

iTunes のプレイリストを PC から Android 端末へ同期するツール（KudagiTune）を作る。曲とプレイリストは PC にあり、運ぶ向きは PC から端末と決まっていた。
どちらが待ち受け、どちらが取りに行くか、PC と端末をどうつなぐか（同じ LAN の Wi-Fi、Tailscale、USB）を決める必要があった。

## 決定の要因

- Android は常駐に制限があり、端末が待ち受け続ける形は扱いにくい
- 接続方式ごとに実装を分けたくない
- USB 接続のために、端末の USB デバッグを常時有効にする状態は避けたい

## 検討した選択肢

### 案 A：端末が待ち受け、PC が送る（push）

- 良い点：PC 側が同期の開始を決められる
- 悪い点：端末が常駐して待ち受ける必要があり、Android の常駐の制限と合わない

### 案 B：PC がサーバー、端末が同期するときだけ接続して取りに行く（pull）。3 方式は 1 つのサーバーへの TCP に揃える

- 良い点：端末は同期するときだけつなげばよい。方式ごとの違いは「つなぐ先の決め方」だけになり、サーバーは 1 つで済む
- 悪い点：PC が起動していて、端末から届く必要がある

### 案 C：USB を adb reverse（端末の localhost から PC へ向ける）で行う

- 良い点：USB 接続で IP を意識しなくてよい
- 悪い点：adb を PC アプリに同梱する必要があり、端末の USB デバッグが常時有効になる（つないだ PC から端末を操作できる状態になる）。adb の起動と監視の実装が増える

## 決定

案 B。PC をサーバー、端末をクライアントとし、端末は同期するときだけ接続する。LAN の Wi-Fi、Tailscale、USB の 3 方式は、いずれも端末が PC のサーバーへ TCP でつなぐ形に揃える。
USB は、USB テザリング（端末が PC に IP を配る）で同じサーバーへつなぐ。adb は同梱しない（案 C は採らない。必要になれば後で足せる）。

## 結果

### 良い面

- サーバーが 1 つで、接続方式の違いが「つなぐ先の決め方」だけに収まる
- adb の同梱が無く、その配布条件の確認も要らない
- USB デバッグを常時有効にする必要が無く、端末が外から操作される状態を作らない

### 悪い面

- PC が起動していないと同期できない
- USB で使うには、利用者が端末のテザリングを有効にする必要がある（端末側の設定が 1 段増える）
- 端末側の常駐が無いので、PC から端末へ即時に知らせることはできない

## 適用範囲と決めないこと

- 効く範囲：同期の役割の分担と、接続方式の揃え方
- 決めないこと：通信の保護と認証（0005）、自動起動の条件（0008）、上の 3 方式以外の経路（Bluetooth など）
