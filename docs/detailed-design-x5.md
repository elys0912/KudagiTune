## X5 desktop

### X5 の前提

M3 は薄く保つ（N5-2）。判断（差分、署名の手順、再送防止の判定の規則、コードの生成と試行の判定の純粋な関数）は M1、plist の解釈は M2 が持つ。M3 は I/O（HTTP、mDNS、鍵の保管、ファイル、画面）と、M1 の部品に実体を渡す役を持つ。ペアリングの状態機械（H0〜H3、試行の回数、期限、表示中のコード）は M3 が持つ（X4-2。指摘 20）。値は V の番号で参照する。

### X5-1 サーバー

#### 構成

| 項目 | 内容 |
|---|---|
| 部品 | Ktor サーバー。エンジンは Netty（J19。`sslConnector` の文書がある。facts-jvm 7b） |
| 待ち受け | HTTPS の 1 ポート（V16、設定で変更可）。平文の HTTP は開かない（B4-3 の 1） |
| 証明書 | X5-2 の K2。ECDSA P-256。`sslConnector` の keyStore は、K2 の秘密鍵と証明書からメモリ上で作る（ファイルへ書かない） |
| プラグイン | 署名検証、gzip（P1 のみ）、`PartialContent`（P2 の Range。facts-jvm 7a）、エラー変換、要求の大きさの制限（V31） |
| 本文の形式 | JSON は kotlinx.serialization（X3-1 の型） |

#### ルートと処理の割り当て

| P | メソッドとパス | 署名 | M3 の処理 | 呼ぶ先 |
|---|---|---|---|---|
| P1 | `GET /v1/manifest` | 要 | 選択の集合（X5-4）と M2 の結果から、M1 にマニフェストを作らせて返す。XML が読めなければ 503（E4） | M1（X3-1）、M2（X2-3） |
| P2 | `GET /v1/tracks/{persistent_id}` | 要 | 下記「P2 の検査」 | M1（X3-3）、ファイル |
| P3 | `GET /v1/digest` | 要 | `content_digest` だけ返す | M1 |
| P4 | `POST /v1/reports` | 要 | 本文を検査し、X5-4 の端末の表の `last_sync` へ `SyncReport` の全項目をそのまま保存（項目は X3-5）。204 | 設定の保存 |
| P5 | `POST /v1/pairing/start` | 不要 | コード表示中のみ受ける。それ以外は 403（E2、`pairing_closed`） | M1（X4-2） |
| P6 | `POST /v1/pairing/confirm` | 不要 | 同上。不一致は 401（E2）。試行が V2 に達したら 403（`pairing_locked`） | M1（X4-2）、K1 の保存 |

#### 要求の検査の順（P1〜P4）

1. 本文の大きさが V31 を超えれば拒否する（413。E は付けない）
2. パスが `/v1/` の既知のルートでなければ 404（E は付けない）
3. 接続元が署名失敗の待ち（V32）にあれば 429（E2）
4. ヘッダ 4 種（`X-Psfox-Device`、`-Timestamp`、`-Nonce`、`-Signature`）の書式が誤れば 400
5. device_id から K1 を引く。無ければ、署名が合わない場合と同じ 401（E2）（区別を外に出さない）
6. M1 の検証（X4-3）を呼ぶ。入力は、メソッド、パスと問い合わせ（送られた文字列のまま）、ヘッダ、本文の SHA-256、K、現在時刻、PC の起動時刻、nonce の保持の表。出力は、成功、または `bad_signature`、`clock_skew`、`replay`
7. 失敗なら 401（E2、`detail` に出力の値。`bad_signature` は `detail` を付けない）。連続の失敗の数は X5-1 の「署名失敗の数え方」に従う
8. 成功ならルートの処理へ渡す

署名の検証は、検査 5 より前に本文を読まない。本文の SHA-256 は、検査 1 を通った本文から求める。

#### 署名失敗の数え方（B4-4 の 7、暫定）

- 数える単位は接続元の IP。署名の失敗（検査 5、7）と P5・P6 の失敗を同じ数に入れる
- しきい値は X1-4 の署名失敗の閾値（10 回）。超えたら V32 の間、検査 3 で 429 を返す
- 数はメモリにだけ置く。PC の再起動で消える
- テザリングと NAT では正規の端末も同じ IP になるが、1 台の構成（D11）では問題にならない。複数台に広げるときに見直す（指摘 30）

#### P2 の検査（B4-4 の 3）

1. `persistent_id` が 16 桁の 16 進でなければ 400
2. マニフェストに無い ID は 404（E5）
3. 問い合わせの `size`、`modified_at` が現在のマニフェストの値と違えば 409（E8）。本文を送らない
4. 実ファイルが無ければ 404（E5）。実ファイルの大きさが `size` と違えば 409（E8）
5. 保存先のパスは、M2 が解いた ID からの対応表だけで引く。要求の文字列からパスを作らない（N1-7）
6. `Range: bytes=N-` があれば、N が大きさ以上なら 416。範囲内なら 206 と `Content-Range`（`PartialContent` が受ける。GET と HEAD のみで、他のメソッドは 405。`Content-Length` が要る。facts-jvm 7a）
7. 応答のヘッダは `Content-Length`、`Accept-Ranges: bytes`、`X-Psfox-Size`、`X-Psfox-Modified-At`。本文は圧縮しない（範囲の配信中は `PartialContent` が圧縮を無効にする。facts-jvm 7a）
8. 本文はファイルから逐次に送る。全体をメモリに載せない
9. 送信中に接続が切れても、PC は何もしない（再開は端末が新しい署名で要求し直す）

- 実ファイルの更新日時を一致の判定に使うかは B2 の判断（B4-4 の 3、X3 の依頼）。この節は大きさだけを検査する

#### gzip

- P1 だけ。要求に `Accept-Encoding: gzip` があるときに圧縮する。P2、P3、P4 は圧縮しない
- 署名は本文の圧縮の前後で変わらない（署名の対象は要求の本文であり、応答ではない）

#### 応答の印と E

- 失敗の応答は `{"error":"E<番号>","detail":"…"}`（B4-4 の 8 の表）。例外は共通のエラー変換が 1 か所で変換する
- 想定外の例外は 500。本文に例外の内容を含めない。ログには出す（X5-4）
- E1、E3、E6、E7、E9 は返さない（端末側の判定）

### X5-2 鍵の保管 K1・K2

J17 により、鍵は DPAPI で暗号化したファイルに置く。

#### 保管のファイル

| 項目 | 内容 |
|---|---|
| 場所 | `%APPDATA%\playlist-sync-fox\secrets.bin` |
| 中身 | K1 の表と K2 の秘密鍵を 1 つの JSON にして、DPAPI（CurrentUser）で暗号化した 1 つのバイト列 |
| 暗号化 | JNA の `Crypt32Util`。追加のエントロピーは固定の文字列（1 か所の定数） |
| 書き込み | 一時ファイル（`secrets.bin.tmp`）へ書いて閉じ、置き換える（X5-4 の書き込みと同じ手順）。失敗したら一時ファイルを消し、前のファイルは残る |
| 証明書 | 設定の置き場の `tls-cert.pem`（B4-6）。公開してよい。`secrets.bin` に含めない |

JSON の中身（暗号化の前）

| 項目 | 型 | 意味 |
|---|---|---|
| `devices` | 連想配列 | キーは `device_id`、値は署名用の共有の鍵 K（32 バイト）の Base64。端末ごとに 1 項目（K1。J15） |
| `tls_key` | 文字列 | K2 の秘密鍵（PKCS#8）の Base64 |

- 呼び出す部品は 1 つの窓口（`SecretStore`）に包み、M3 の他の部分はこの窓口だけを使う
- 窓口の実体を差し替えられるので、試験では記憶の中の実体を使う
- 資格情報マネージャーは使わない。JNA の platform に束縛が見当たらず（facts-jvm 5a）、1 項目の上限（2560 バイト。5b）も避けられる。N1-4 の文言の直しは「基本設計の直し 2」

#### `SecretStore` の表

| 操作 | 入力 | 出力 | 副作用 |
|---|---|---|---|
| 読む | 名前（`device/<device_id>` または `tls-key`） | バイト列、または無し | なし。ファイル全体を復号して引く |
| 書く | 名前、バイト列 | なし | 全体を復号し、同名があれば置き換えて暗号化し、一時ファイル経由で置く |
| 消す | 名前 | なし | 無くても失敗にしない |

- 書く・消すは 1 つの窓口を通して直列にする（P6 と画面の操作が重なるため）
- ファイルが無いときは空として扱う。復号に失敗したとき（別の利用者の暗号化、破損）は失敗として返し、空として扱わない

#### 証明書の生成と更新

1. 起動時に `tls-key`（`SecretStore`）と `tls-cert.pem` を読む
2. 両方があり、鍵と証明書の公開鍵が一致し、期限が残り 90 日（置いた値 X5-V2）を超えれば、そのまま使う
3. 鍵があり、証明書が無い、または期限が近い、または公開鍵が一致しなければ、同じ鍵で証明書を作り直す（有効期間は V30）。SPKI は変わらない（B4-3 の 1）
4. 鍵が無ければ、ECDSA P-256 の鍵と証明書を作り、保存する。この場合の SPKI は新しい。ペアリング済みの端末があれば、X5-5 の W3 の警告に出す（端末は再ペアリングが要る）
5. 証明書の件名は固定の名前にする。人名と PC のホスト名を入れない。SAN は持たない（端末が照合しない。B4-3 の 1）
6. 作った証明書は一時ファイル経由で置き換える（X5-4 と同じ手順）

- 作成にはブラウザ向けの形式の厳密さが要らない（端末は SPKI のみ照合）。Ktor の `buildKeyStore`（`ktor-network-tls-certificates`。facts-jvm 7b）か Bouncy Castle（X4-1 で依存に入る）で作る。同じ鍵で作り直せる方を実装時に選ぶ（J21 の暫定どおり）

#### 起動時の読み込み

- K1 の一覧は、設定の端末の表（X5-4）から device_id を引き、`SecretStore` から 1 件ずつ読む。読めない device_id は、端末の表に「鍵が無い」の印を付け、そのまま署名を拒否する（401 と同じ扱い）。W3 に警告を出す
- 保管の復号に失敗した（`SecretStore` の失敗）ときは、サーバーを起動せず、トレイに「鍵の保管に失敗」を出す。平文のファイルへ逃がさない（N1-4）

### X5-3 mDNS の広告

| 項目 | 内容 |
|---|---|
| 部品 | JmDNS。インターフェースごとに 1 つのインスタンス（未確認。複数アドレスの同時の広告の挙動は実機で確かめる。N5-3。facts-jvm 6a は README に記述なし） |
| 登録の時期 | サーバーの起動が成功した後。停止の前に登録を解除する |
| サービスの型 | `_psfox._tcp`（Q1 で変わりうる。名前は 1 か所の定数） |
| インスタンス名 | `psfox-` と pc_id の先頭 8 桁（B4-1 の 1） |
| ポート | 現在のサーバーのポート |
| TXT | `v`（整数）、`pid`（pc_id の先頭 8 桁）、`pair`（0 または 1） |

#### インターフェースの選び方

1. 起動中の IPv4 のインターフェースを列挙する
2. ループバックを除く。仮想アダプタを除くかは実機で決める（B4-1 の 1。J21 の暫定どおり除かない）
3. 1 つも残らなければ、広告を行わず、W2 の警告ではなく W4 の接続先の一覧を空にする。サーバーは起動する（手入力で届くため）
4. ネットワークの変化（Wi-Fi の切り替え、テザリングの接続）を、一定間隔で列挙し直して検知する（間隔は置いた値 X5-V3。OS の通知の API を使うかは未確認）。変化があれば登録し直す

#### TXT の更新

- `pair` はコードの表示の開始と終了のたびに更新する。更新は登録の変更で行い、再起動しない
- TXT に曲名、人名、PC のホスト名を入れない（N1-6）
- 広告は認証の代わりにならない（N1-5）。PC は広告の値を自分では確かめない

### X5-4 設定とログ

#### settings.json の項目

置き場は `%APPDATA%\playlist-sync-fox\settings.json`（B4-6）。

| 項目 | 型 | 必須 | 意味 |
|---|---|---|---|
| `schema_version` | 整数 | 要 | 設定の形の版。最初は 1 |
| `xml_path` | 文字列 | 任意 | iTunes ライブラリ XML のパス（W5）。無いとき（初回）は既定の候補（`%USERPROFILE%\Music\iTunes\iTunes Music Library.xml`）を試し、読めなければ W5 で指定を促す。既定の場所は Apple の文書に無い（facts-jvm 1i） |
| `selected_playlist_ids` | 文字列の配列 | 要 | 選択した葉のプレイリストの Persistent ID（W2） |
| `stale_days` | 整数 | 要 | 古いと警告する日数。0 で警告しない（既定 V5） |
| `launch_on_login` | 真偽 | 要 | ログイン時に起動（既定は有効） |
| `port` | 整数 | 要 | サーバーのポート（既定 V16） |
| `pc_id` | 文字列 | 要 | PC の識別子（乱数 16 バイトの UUID の形。初回に作る。B4-1 の 1 の `pid` は先頭 8 桁） |
| `library_id_fallback` | 文字列 | 任意 | XML に無いときだけの代わりの乱数（B2-4） |
| `devices` | 配列 | 要 | ペアリング済みの端末の表。最初の版は 0 か 1 件（D11） |

`devices` の要素

| 項目 | 型 | 必須 | 意味 |
|---|---|---|---|
| `device_id` | 文字列 | 要 | 端末の識別子（UUID の形）。K1 の名前の一部 |
| `display_name` | 文字列 | 要 | ペアリング時に端末が申告した表示名 |
| `registered_at` | 文字列 | 要 | 登録日時（UTC、ISO 8601） |
| `last_sync` | オブジェクト | 任意 | P4 で受けた `SyncReport` の全項目をそのまま持つ（項目は X3-5） |

- 鍵、コード、署名、nonce を保存しない（N1-4、N1-6）
- 項目名は `snake_case`、kotlinx.serialization の `@SerialName` で固定（X3-1 の規則）。未知の項目は読み捨てる
- `last_seen_at` は保存しない。直近の署名つき要求の時刻は、W3 の接続中の判定（V33）のためにメモリにだけ持つ（J21 の暫定どおり）

#### 読み書きの手順

読み込み

1. ファイルが無ければ、既定値で作る（`pc_id` を生成）。初回の印を立てる（W1 が W4 を自動で開く）
2. 読めない（JSON の誤り、必須項目の欠け）ときは、`settings.json.bad` へ改名して退避し、既定で起動し、警告を出す。K1 の項目は残る
3. `schema_version` が自分より新しければ、読まず、2 と同じ扱いにする（書き戻して失う事故を防ぐため）
4. `schema_version` が古ければ、版ごとの移行の関数を順に適用して現在の版にし、保存する。移行の関数は版 n から n+1 の 1 段ずつ。最初の版は移行が無い

書き込み

1. 内容を JSON に直す
2. 同じフォルダの一時ファイル（`settings.json.tmp`）へ書き、閉じる
3. 一時ファイルを `settings.json` へ置き換える（上書きの移動。失敗したら一時ファイルを消し、前のファイルは残る）
4. 書き込みは 1 つの窓口を通し、同時の書き込みを直列にする（P4 と画面の操作が重なるため）

#### ログ

| 項目 | 内容 |
|---|---|
| 置き場 | `%LOCALAPPDATA%\playlist-sync-fox\logs\` |
| 形式 | 1 行 1 件。時刻（UTC の ISO 8601。`Z`）、レベル、モジュール、メッセージ、E の番号（あれば）を、タブで区切る |
| レベル | 情報、警告、エラーの 3 段（詳細ログは持たない） |
| 切り替え | 1 ファイルが V8 の大きさを超えたら新しいファイルへ。世代数（V8）を超えた古いものを消す |
| 出してよい | ファイルのパス、曲名（N1-6、B4-6） |
| 出さない | 鍵、コード、署名の値、証明書の秘密鍵、`secrets.bin` の中身、署名のヘッダ、nonce |

- 出さない値の遮断は、ログの窓口で行う（要求のヘッダをそのまま渡す呼び出しを作らない）。署名の失敗の記録は、device_id と `detail` だけを書く
- ログの書き込みの失敗は同期を止めない。標準エラーへ 1 行だけ出す
- 外へ送らない（F6-1）

### X5-5 画面 W1〜W5

見た目は書かない。画面の状態は、1 つの「PC の状態」の型にまとめ、画面はそれを写すだけにする。

#### PC の状態の項目

| 項目 | 型 | 意味 |
|---|---|---|
| `server` | 起動前、起動中、失敗（理由） | サーバーの状態 |
| `xml` | 正常、読めない、古い（日数）、未確認 | M2 の結果（X2-4）から |
| `playlists` | 木 | W2 の一覧 |
| `device` | 無し、あり（表示名、接続中、最後の同期） | W3 |
| `pairing` | 閉、開（コード、残り時間、失敗回数） | W4。M3 の状態機械（X4-2）の写し |
| `warnings` | 警告の一覧 | W1 の印と W2 の帯 |

#### W1 トレイ

| 状態 | 表示 | 条件 |
|---|---|---|
| ペアリング未済 | 「ペアリング未済」 | `device` が無し |
| XML が読めない | 「XML が読めない」 | `xml` が読めない |
| 同期中 | 「同期中」 | 直近の署名つき要求から V33 以内に P2 が続いている |
| 待機中 | 「待機中」 | 上のいずれでもない |

- 優先順は上の表の上から。印は `warnings` が 1 件でもあれば付ける（XML が古い、ポートの使用中、鍵が無い、選択が空）
- 同期中の判定は、P2 の送信中の数が 1 以上、または P2 の最後の要求から V33 以内のとき（P1 だけでは同期中としない。曲数を知らないため件数は出さない）

| 操作 | 処理 |
|---|---|
| 左クリック、開く | メインの窓を開く |
| ペアリングコードを表示 | W4 を開く |
| 設定 | 設定の窓を開く |
| ログの場所を開く | ログのフォルダをエクスプローラで開く |
| 終了 | 同期中なら確認を出す。X5-6 の終了の手順 |

#### W2 プレイリスト

| 状態 | 表示 | 操作と処理 |
|---|---|---|
| 一覧あり | 木。フォルダは開閉、葉にチェック、曲数、合計サイズ、スマートの印 | 葉のチェック：`selected_playlist_ids` を更新して即保存。フォルダのチェック：配下の葉を一括で更新（フォルダは保存しない） |
| 保存した ID が XML に無い | 灰色で「見つからない」 | 「外す」操作で集合から除く。自動では消さない |
| `xml` が読めない | 帯の警告。一覧は前回の内容を保たず空にする。警告の文は、iTunes の詳細設定「Share iTunes Library XML with other applications」を有効にする案内を含める（英語版の設定名。facts-jvm 1j。日本語版の名は未確認） | W5 を開く導線 |
| 選択が空 | 帯の警告 | 通知しない |

#### W3 端末

| 状態 | 表示 | 操作と処理 |
|---|---|---|
| `device` が無し | 「端末がありません」とペアリングのボタン | W4 を開く |
| あり、接続中 | 表示名、接続中、最後の同期（日時、結果、件数、E の番号と名前） | 「ペアリングを解除」 |
| あり、未接続 | 同上で未接続 | 同上 |
| 鍵が無い | 警告「この端末の鍵が見つかりません。解除して再ペアリング」 | 同上 |

- 解除：確認の後、K1 の項目を消し、`devices` から除き、保存する。端末の署名つき要求はその後に 401（E2）となる
- 証明書を作り直した（X5-2 の 4）ときの警告もここに出す

#### W4 ペアリング

| 状態 | 表示 | 操作と処理 |
|---|---|---|
| 閉 | コードを出さず「コードを表示」のボタンだけ。端末ありなら W3 での解除を案内 | ボタン：M1 の関数でコードを作り、M3 の状態機械（X4-2）を開く。`pair` を 1 にする（X5-3） |
| 開 | 6 桁のコード、残り時間（V3）、失敗回数、MagicDNS 名、接続先の一覧、指紋 | 作り直し：コードを無効にして新しいコード。閉じる：コードを無効にする |
| 失敗が上限（V2） | 帯で知らせる。コードは無効。V4 の間は作り直せない | 待ち後に「コードを表示」 |
| 期限切れ、使用済み | 閉と同じ | — |

- 窓を閉じる、アプリの終了でコードを無効にする
- コードと指紋以外の鍵の値は画面に出さない。クリップボードへの自動コピーをしない。コピーのボタンは MagicDNS 名と指紋だけ
- 接続先の一覧：X5-3 の列挙の結果から、IPv4 とポートを 1 行ずつ。テザリングのアダプターは別行
- MagicDNS 名：取得の方法は未確認。取れなければこの行を出さない（J21 の暫定どおり。方法は Tailscale の実機で確かめる）
- 指紋：X4-4 の表示形式（先頭 12 バイト、4 桁区切り）で、K2 の公開鍵の SPKI から作る

#### W5 設定

- 項目は X5-4 の settings.json の項目に 1 対 1。変更は項目ごとに検査し、即保存する（保存ボタンは置かない）

| 項目 | 検査 | 処理 |
|---|---|---|
| XML の場所（`xml_path`） | ファイルが読めるか（M2 の読み取りを試す）。未設定のときは既定の候補を試す | 読めれば保存して読み直し。読めなければ結果を横に表示し、保存しない |
| 古いと警告する日数 | 0 以上の整数 | 保存して警告を再計算 |
| ログイン時に起動 | — | X5-6 の登録を更新 |
| サーバーのポート | 1024〜65535 の整数 | 保存し、サーバーと mDNS を再起動。使用中なら起動に失敗し、元の値へ戻さず警告を出す（自動で変えない） |
| ログのフォルダ | 表示のみ | — |

### X5-6 起動と終了

#### 起動の順

1. 二重起動を防ぐ（同じユーザーの 2 つ目は、1 つ目のメインの窓を開く要求を出して終了する。方法は実装で決める。未確認）
2. ログを初期化する
3. 設定を読み込む（X5-4）
4. 鍵を読み込む（`SecretStore`。X5-2。失敗なら X5-2 の扱い）
5. XML の監視を始める（M2 の WatchService 側、X2-4）。読み取りの結果は「PC の状態」に流す
6. サーバーを起動する（X5-1）。ポートの使用中は警告を出して続行（サーバーは止まった状態）
7. mDNS の広告を登録する（X5-3）
8. トレイに入る。初回の印があれば W4 を開く

#### 終了の順

1. 同期中なら確認を出す（W1）。続行なら以下
2. コードを無効にする
3. mDNS の登録を解除する
4. サーバーを止める。送信中の接続は、猶予（置いた値 X5-V5）の後に切る
5. XML の監視を止める
6. 設定の保存が残っていれば書き切る

#### ログイン時の起動

- 登録先は現在のユーザーの Run キー（`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`）。管理者権限が要らない（B4-6 の場所の規則）
- 値の名前は `playlist-sync-fox`。値は配布物の実行ファイルのパスと `--background`（置いた値でなく定数）。パスが変わったとき（更新、移動）は、起動のたびに現在のパスで書き直す
- 無効にするときは値を消す。無ければ失敗にしない
- 登録先は Run キーで、zip 配布（J13）と合う（指摘 34。X5-J6 は解消）

### X5-7 テストの観点

M3 は薄い統合の試験（JVM。実ネットワークと実の資格情報マネージャーは使わない。B1-4）。

| 対象 | 観点 | 境界の値 |
|---|---|---|
| 要求の検査の順 | 各検査の失敗が、定めた HTTP と E になる。順が入れ替わらない（署名が無い 400 と、未登録の 401 の区別） | 本文が V31 ちょうどと 1 バイト超 |
| 署名失敗の数え方 | X1-4 の署名失敗の閾値で 429。V32 の経過後に戻る。P5・P6 の失敗も数える | 閾値ちょうどと 1 回多い |
| P2 | 400、404、409、416、206 の各経路（`PartialContent` を含む）。パスを受けない（`..` や区切りを含む ID は 400） | 16 桁と 15 桁、`N` が大きさと同じ |
| gzip | P1 だけ圧縮。ヘッダ無しは圧縮しない | — |
| 証明書の更新 | 鍵ありで期限が近い→同じ SPKI で更新。鍵が無い→新しい SPKI | 残り 90 日ちょうどと 1 日少ない |
| `SecretStore` | 書き込みは一時ファイル経由（途中で例外でも前のファイルが残る）。復号の失敗でサーバーを起動しない。平文のファイルが作られない。ファイルが無ければ空 | 0 件、2 件の端末 |
| 設定 | 一時ファイル経由（途中で例外を起こしても前のファイルが残る）。壊れた JSON は `.bad` へ退避し既定で起動。新しい版は読まず退避 | `schema_version` が現在と同じ、1 つ上、1 つ下 |
| 設定の移行 | 版 n から n+1 の関数が順に適用される | 2 段の移行 |
| ログ | 鍵、コード、署名の値が出ない。V8 を超えて切り替え、世代数を超えて消える | ちょうど V8 と 1 バイト超 |
| mDNS | 登録する TXT の値、`pair` の更新、インターフェースが 0 件でも起動する | 0 件、2 件 |
| 状態 | W1 の優先順、W3 の接続中の判定（V33） | 直近の要求から V33 ちょうどと 1 秒超 |

- 実機でしか確かめられないものは B4-8 の表（N5-3）に従う（mDNS の届き方、仮想アダプタ、DPAPI の暗号化、ログイン時起動）
- 試験の部品：記憶の中の `SecretStore`、固定の時計、一時フォルダ、固定乱数（X4-5）

### X5 の他の節への依頼

- X1：version catalog に `jna`、`jna-platform`、`bouncycastle`、Ktor（Netty、`PartialContent`）、JmDNS。X5-V2・V3・V5 を X1-4 へ。M3 のパッケージの名は X1-3 に従う（`desktop.secrets` を含む）
- X2：M3 へ渡す読み取りの結果と更新の通知の形（`xml` の状態、プレイリストの木、最終更新日時）
- X3：マニフェストを作る入力（選択の集合と M2 の結果）の型。P4 の本文の型（`SyncReport`）と検査
- X4：検証の入力・出力（X5-1 の検査の 6）、`SecretStore` を通す K1 の保存、SPKI の指紋の表示。状態機械は M3 が持つ（X4-2-1 の文を直す）
- X6：P2 の応答のヘッダ、416、409 の端末側の扱い
- X7：E2 の `detail`（`clock_skew`、`replay`、`pairing_closed`、`pairing_locked`）の文言と表示
