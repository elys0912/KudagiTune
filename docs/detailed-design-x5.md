## X5 desktop

### X5 の前提

M3 は薄く保つ（N5-2）。判断（差分、署名の手順、再送防止の判定の規則、コードの生成と試行の判定の純粋な関数）は M1、plist の解釈は M2 が持つ。M3 は I/O（HTTP、mDNS、鍵の保管、ファイル、画面）と、M1 の部品に実体を渡す役を持つ。ペアリングの状態機械（H0〜H3、試行の回数、期限、表示中のコード）は M3 が持つ（X4-2）。値は V の番号で参照する。

名前：正式名は KudagiTune（Q1。2026-11-09）。利用者に見える文字列（窓の題、トレイ、画面の文言）と文書だけを改める。識別子（パッケージ名 `playlistsyncfox`、`psfox`、サービスの型、ヘッダ名、`%APPDATA%\playlist-sync-fox` などのフォルダ名、Run キーの値の名前）は変えない。

### X5-1 サーバー

#### 構成

| 項目 | 内容 |
|---|---|
| 部品 | Ktor サーバー。エンジンは Netty（J19。`sslConnector` の文書がある。facts-jvm 7b） |
| 待ち受け | HTTPS の 1 ポート（V16、設定で変更可）。平文の HTTP は開かない（B4-3 の 1） |
| 証明書 | X5-2 の K2。ECDSA P-256。`sslConnector` の keyStore は、K2 の秘密鍵と証明書からメモリ上で作る（ファイルへ書かない） |
| プラグイン | 署名検証、gzip（P1 のみ）、`PartialContent`（P2 の Range。facts-jvm 7a）、エラー変換、要求の大きさの制限（V31） |
| 本文の形式 | JSON は kotlinx.serialization（X3-1 の型） |

#### ルートと処理の割り当て

| P | メソッドとパス | 署名 | M3 の処理 | 呼ぶ先 |
|---|---|---|---|---|
| P1 | `POST /v1/manifest` | 要 | 本文を検査し（下記「P1・P3 の本文の検査」）、本文の ID の配列と M2 の結果から、M1 にマニフェストを作らせて返す。作ったマニフェストの曲の表（persistent_id ごとの size、modified_at）を M3 が持ち、P1 のたびに置き換える（J31。メモリのみ。その要求の選択で作った表なので、選んでいない曲は P2 で配らない。X-32）。表は実ファイルのパスも持つ（X2-4 の 9）。XML が読めなければ 503（E4） | M1（X3-1、X3-1b）、M2（X2-3） |
| P2 | `GET /v1/tracks/{persistent_id}` | 要 | 下記「P2 の検査」 | 曲の表（P1 で作ったもの）、M2 の結果（X2-3）と `LibraryHolder`（X2-4）、実ファイル |
| P3 | `POST /v1/digest` | 要 | P1 と同じ本文の検査と手順で、要求の時の読み直し（X2-4 の 7、8）と実在の確認（X2-4 末尾の順）を含めてマニフェストを組み、本文は返さず `content_digest` だけ返す。XML が読めなければ 503（E4。J45）。P2 の曲の表（J31）は置き換えない（置き換えるのは P1 だけ）。要求の時の読み直しと実在の確認が入るので応答は遅れうる。端末は P3 の応答を V53 まで待つ（接続の確立は V29。J47） | M1（X3-1、X3-1b）、M2（X2-3） |
| P4 | `POST /v1/reports` | 要 | 本文を検査し（下記「P4 の本文」）、X5-4 の端末の表の `last_sync` へ `SyncReport` の全項目をそのまま保存（項目は X3-5）。保存済みの `started_at` より古い報告は上書きしない。204 | 設定の保存 |
| P5 | `POST /v1/pairing/start` | 不要 | コード表示中のみ受ける。それ以外は 403（E2、`pairing_closed`。H0 のうち V4 の待ちの間は `pairing_locked`）。devices が 1 件でもあれば 403（E2、`device_exists`）。順は X4-2-2 | M1（X4-2） |
| P6 | `POST /v1/pairing/confirm` | 不要 | 同上。不一致は 401（E2）。試行が V2 に達したら 403（`pairing_locked`）。成功のときは、応答の前に K1 の保存と settings.json の `devices` への追加（`display_name`、`registered_at`。`display_name` には P5 の本文の `device_name` を写す。X4-2-2）を済ませる（K1 と同じ時点。review-11） | M1（X4-2）、K1 の保存、設定の保存 |
| P7 | `GET /v1/playlists` | 要 | 要求の時の読み直し（X2-4 の 7、8）の後、M2 の結果のプレイリストを木（X3-1b の `PlaylistNode`）にして返す。葉は通常のプレイリスト（曲数つき）、フォルダは枝。組み込みの一覧（`Master`、`Distinguished Kind`）は出さない（B2-1）。実在の確認はしない（曲数は XML の並びの数）。XML が読めなければ 503（E4）。曲の表は置き換えない。2026-11-07（D15） | M2（X2-3）、`buildPlaylistTree`（M3） |
| P8 | `POST /v1/progress` | 要 | 本文を検査し（B4-4 の 5b。`ProgressReport`、M1）、端末の進み具合としてメモリに持つ（`ProgressBoard`。保存しない）。P4 を受けたとき、または最後の P8 から V56 の間更新が無いときに消す。204。2026-11-07（D22） | `ProgressBoard`（M3） |

- P2 の送信中の曲（ID、表示名、送ったバイト数、大きさ）を `ActivityTracker` がメモリに持つ。送ったバイト数は、ファイルから読んで応答へ渡した量で数える（送信の緩衝の分だけ先に進む）。表示名は曲の表の実ファイルのファイル名（拡張子を除く）。P2 が終われば消す（D22）

#### 要求の検査の順（P1〜P4、P7、P8）

1. 本文の大きさが V31 を超えれば拒否する（413。E は付けない）
2. パスが `/v1/` の既知のルートでなければ 404（E は付けない）
3. 接続元が署名失敗の待ち（V32）にあれば 429（E2）
4. ヘッダ 4 種（`X-Psfox-Device`、`-Timestamp`、`-Nonce`、`-Signature`）の書式が誤れば 400（ヘッダの欠け、タイムスタンプが 10 進の整数でない場合を含む。ヘッダに関する 400 はここに集める。X4-3-2 の手順 1、2 は呼び出しの前に済んでいる前提）
5. M1 の検証（X4-3）を呼ぶ。入力は、メソッド、パスと問い合わせ（送られた文字列のまま）、ヘッダ、本文の SHA-256、K1 の引き当て（device_id から K を返す関数）、現在時刻、PC の起動時刻、nonce の保持の表。順は X4-3-2 のとおり（時刻の検査、K1 の引き当て、署名、再送）。出力は、成功、または `bad_signature`（未登録を含む）、`clock_skew`、`replay`
6. 失敗なら 401（E2、`detail` に出力の値。`bad_signature` は `detail` を付けない）。連続の失敗の数は X5-1 の「署名失敗の数え方」に従う
7. 成功ならルートの処理へ渡す

#### P1・P3 の本文の検査（D15。境界の検査）

- 検査 1（本文の大きさ V31）の後、署名の検証（検査 5）を通った要求だけが、ルートの処理でこの検査を受ける。署名の検証の順は変えない（本文の SHA-256 は署名の入力に含まれ、本文は署名の対象）
- 本文を `parsePlaylistIds`（X3-1b）で検査する。JSON の形、各 ID の書式（大文字の 16 桁の 16 進）、個数（V54）の誤りは 400（E は付けない）。検査の失敗の文、ログに、本文の中身と ID を入れない
- 通った ID の配列は、重複を除いてマニフェストの組み立て（X2-4 末尾の順）に渡す。PC は選択を保存しない
- 組み立てでは、XML に無い ID と、XML にあっても種別が通常でない ID（フォルダ、`Master` など）を、同じ「見つからない」として `unresolved_playlists` に入れる（名前は XML の名前。無ければ最後に知っていた名前）。端末は消す同期でこの一覧を確認の条件に使うので、通常でない種別を選んでいると確認が出る。確認が出る側（安全側）の扱いで、意図したもの（review-15 の X5-14。今のまま）

本文の SHA-256 は、検査 1 を通った本文から求める。K1 の引き当ては M1 の検証の中で行い、M3 は別に先に引かない（未登録と時刻の誤りの区別が外に出ないよう、順を X4-3-2 の 1 か所にする。review-11）。

#### 署名失敗の数え方（B4-4 の 7、暫定）

- 数える単位は接続元の IP。署名の失敗（検査 5 の失敗の応答）と P5 の連続を同じ数に入れる（B4-4 の 7）。P5 の連続は、間に P6 を挟まない P5 の数とする。P6 は数えず、連続を途切れさせる。コードの試行は V2 の上限で別に止まる
- しきい値は V43。達したら V32 の間、検査 3 で 429 を返す
- 数はメモリにだけ置く。PC の再起動で消える
- テザリングと NAT では正規の端末も同じ IP になるが、1 台の構成（D11）では問題にならない。複数台に広げるときに見直す

#### P2 の検査（B4-4 の 3）

1. `persistent_id` が 16 桁の 16 進でなければ 400（`..`、`\` を含む値もここ）。`{persistent_id}` は `/` を含まない 1 要素で、`/` を含む場合は P2 のルートに当たらず、検査 2 のとおり 404（E は付けない）
2. 曲の表（P1 で最後に作ったマニフェストの曲の表。その P1 の要求の選択で作ったもの。J31）に無い ID は 404（E5）。起動後に P1 が無い、または同期の途中で PC が再起動して表が空のときは、404 ではなく 503（E4）で返す。同期全体の失敗で、端末の次の同期は P1 から始まる（J31）
3. 問い合わせの `size`、`modified_at` が曲の表の値と違えば 409（E8）。本文を送らない。XML が置き換わった後も、P1 で作った表と比べる（現在の XML の値は使わない）
4. 実ファイルが無ければ 404（E5）。実ファイルの大きさが `size` と違えば 409（E8）
5. 実ファイルのパスは、手順 2 の曲の表（P1 で作った表。実ファイルのパスを持つ）だけで引く。XML が置き換わった後も現在の XML は引かない。要求の文字列からパスを作らない（N1-7）
6. `Range: bytes=N-` があれば、N が大きさ以上なら 416。範囲内なら 206 と `Content-Range`（`PartialContent` が受ける。GET と HEAD のみで、他のメソッドは 405。`Content-Length` が要る。facts-jvm 7a）
7. 応答のヘッダは `Content-Length`、`Accept-Ranges: bytes`、`X-Psfox-Size`、`X-Psfox-Modified-At`。本文は圧縮しない（範囲の配信中は `PartialContent` が圧縮を無効にする。facts-jvm 7a）
8. 本文はファイルから逐次に送る。全体をメモリに載せない
9. 送信中に接続が切れても、PC は何もしない（再開は端末が新しい署名で要求し直す）

- 実ファイルの更新日時を一致の判定に使うかは B2 の判断（B4-4 の 3、X3 の依頼）。この節は大きさだけを検査する

#### P4 の本文（X3-5 の `SyncReport`）

- JSON のキーは `snake_case`（X3-1、X5-4 の規則）。項目は `SyncReport` の 8 項目で、曲名とパスを含めない（N1-6）。どの端末の `last_sync` に入れるかは、署名ヘッダの device_id で決める

| キー | 型 | 必須 | 意味 |
|---|---|---|---|
| `started_at`、`finished_at` | 日時（X3-1 の書式。UTC、ミリ秒まで、末尾 `Z`） | 必須 | 端末の時計 |
| `outcome` | 文字列（列挙） | 必須 | `success`、`partial`、`interrupted`、`failed` の 4 値（X3-5 の対応表。`not_started` は `failed` に畳んで送る） |
| `has_more` | 真偽 | 必須 | 続きあり |
| `counts` | オブジェクト | 必須 | X3-5 の `Counts` の項目を `snake_case` にしたもの：`to_add`、`to_replace`、`to_remove`、`unchanged`、`added`、`replaced`、`removed`、`failed`（8 つとも必須）。値は整数 |
| `capacity` | オブジェクト | 必須 | X3-5 の `Capacity` の項目を `snake_case` にしたもの：`diff_bytes`、`bytes_transferred`（必須）、`free_bytes_before`、`free_bytes_after`（任意。無くてよい）。値は整数 |
| `failure_counts` | オブジェクト | 必須 | キーは `E1`〜`E9`、値は件数（整数）。件数が 0 の E は省いてよい |
| `excluded_count` | 整数 | 必須 | 除外の件数 |

- `SyncResult` の `keyMismatch`（`key_mismatch`）と、入力データの `reach_failed` は P4 に載せない（X3-5）
- 検査は必須項目の有無と型まで：8 項目がそろい、型が合うこと。`outcome` が 4 値以外、日時が書式違い、`counts`・`capacity` の中身や `failure_counts` の値が整数でない、`failure_counts` のキーが `E1`〜`E9` 以外のものは 400（E は付けない。B4-4 の 8 の「書式の誤り」）。未知のキーは読み捨てる（X3-1）。通らない本文は保存しない
- 保存済みの `last_sync` の `started_at` より古い `started_at` の報告は、保存せず 204 を返す。未報告の行の再送の順が前後しても、W3 の最後の同期が古い結果にならない（端末は `started_at` の昇順で送る。X6-3）

#### gzip

- P1 だけ。要求に `Accept-Encoding: gzip` があるときに圧縮する。P2、P3、P4、P7 は圧縮しない
- 署名は本文の圧縮の前後で変わらない（署名の対象は要求の本文であり、応答ではない）

#### 応答の印と E

- 失敗の応答は `{"error":"E<番号>","detail":"…"}`（B4-4 の 8 の表）。例外は共通のエラー変換が 1 か所で変換する
- 想定外の例外は 500。本文に例外の内容を含めない。ログには出す（X5-4）
- E1、E3、E6、E7、E9 は返さない（端末側の判定）

### X5-2 鍵の保管 K1・K2

J17 により、鍵は DPAPI で暗号化したファイルに置く。

#### 保管のファイル

| 項目 | 内容 |
|---|---|
| 場所 | `%APPDATA%\playlist-sync-fox\secrets.bin` |
| 中身 | K1 の表と K2 の秘密鍵を 1 つの JSON にして、DPAPI（CurrentUser）で暗号化した 1 つのバイト列 |
| 暗号化 | JNA の `Crypt32Util`。追加のエントロピーは固定の文字列（1 か所の定数） |
| 書き込み | 一時ファイル（`secrets.bin.tmp`）へ書いて閉じ、置き換える（X5-4 の書き込みと同じ関数。一時ファイル経由の書き込みは 1 つの関数にまとめる）。失敗したら一時ファイルを消し、前のファイルは残る |
| 証明書 | 設定の置き場の `tls-cert.pem`（B4-6）。公開してよい。`secrets.bin` に含めない |

JSON の中身（暗号化の前）

| 項目 | 型 | 意味 |
|---|---|---|
| `devices` | 連想配列 | キーは `device_id`、値は署名用の共有の鍵 K（32 バイト）の Base64。端末ごとに 1 項目（K1。D11、基本設計の直し 2） |
| `tls_key` | 文字列 | K2 の秘密鍵（PKCS#8）の Base64 |

- 呼び出す部品は 1 つの窓口（`SecretStore`）に包み、M3 の他の部分はこの窓口だけを使う
- 窓口の実体を差し替えられるので、試験では記憶の中の実体を使う
- 資格情報マネージャーは使わない。JNA の platform に束縛が見当たらず（facts-jvm 5a）、1 項目の上限（2560 バイト。5b）も避けられる。N1-4 の文言の直しは「基本設計の直し 2」

#### `SecretStore` の表

| 操作 | 入力 | 出力 | 副作用 |
|---|---|---|---|
| 読む | 名前（`device/<device_id>` または `tls-key`） | バイト列、または無し | なし。ファイル全体を復号して引く |
| 書く | 名前、バイト列 | なし | 全体を復号し、同名があれば置き換えて暗号化し、一時ファイル経由で置く |
| 消す | 名前 | なし | 無くても失敗にしない |

- 書く・消すは 1 つの窓口を通して直列にする（P6 と画面の操作が重なるため）
- 名の対応：`SecretStore` の名（`device/<device_id>`、`tls-key`）と secrets.bin の JSON のキー（`devices` の下の `device_id`、`tls_key`）は同じ実体の別の綴りで、前者は窓口の名、後者は JSON のキー（`snake_case`）。secrets.bin の `devices`（鍵の連想配列）と settings.json の `devices`（端末の配列。X5-4）は別の内容
- ファイルが無いときは空として扱う。復号に失敗したとき（別の利用者の暗号化、破損）は失敗として返し、空として扱わない

#### 証明書の生成と更新

1. 起動時に `tls-key`（`SecretStore`）と `tls-cert.pem` を読む
2. 両方があり、鍵と証明書の公開鍵が一致し、期限が残り V44 を超えれば、そのまま使う
3. 鍵があり、証明書が無い、または期限が残り V44 以下、または公開鍵が一致しなければ、同じ鍵で証明書を作り直す（有効期間は V30）。SPKI は変わらない（B4-3 の 1）
4. 鍵が無ければ、ECDSA P-256 の鍵と証明書を作り、保存する。この場合の SPKI は新しい。ペアリング済みの端末があれば、X5-5 の警告の一覧に「証明書を作り直した」を出す（端末は再ペアリングが要る）。警告は、再ペアリングが完了した（P6 の成功）ときに消す。起動中ずっとは出し続けない（review-15 の X5-2）
5. 証明書の件名は固定の名前にする。人名と PC のホスト名を入れない。SAN は持たない（端末が照合しない。B4-3 の 1）
6. 作った証明書は一時ファイル経由で置き換える（X5-4 と同じ手順）

- 作成にはブラウザ向けの形式の厳密さが要らない（端末は SPKI のみ照合）。Ktor の `buildKeyStore`（`ktor-network-tls-certificates`。facts-jvm 7b）か Bouncy Castle（X4-1 で依存に入る）で作る。同じ鍵で作り直せる方を実装時に選ぶ（J21 の暫定どおり）

#### 起動時の読み込み

- K1 の一覧は、設定の端末の表（X5-4）から device_id を引き、`SecretStore` から 1 件ずつ読む。読めない device_id は、端末の表に「鍵が無い」の印を付け、そのまま署名を拒否する（401 と同じ扱い）。W3 に警告を出す
- 保管の復号に失敗した（`SecretStore` の失敗）ときは、サーバーを起動せず、トレイに「鍵の保管に失敗」を出す。平文のファイルへ逃がさない（N1-4）
- 対処：`secrets.bin` を退避すれば、ファイルが無い状態として空で起動し、新しい鍵と証明書が作られる（上の「証明書の生成と更新」の 4）。端末のペアリングは全部無効になる。解除（W3）は `SecretStore` が全体を復号して書き換えるので、復号できる状態でないと使えない。利用者への手順は説明書の「困ったとき」（J44）

### X5-3 mDNS の広告

| 項目 | 内容 |
|---|---|
| 部品 | JmDNS。インターフェースごとに 1 つのインスタンス（未確認。複数アドレスの同時の広告の挙動は実機で確かめる。N5-3。facts-jvm 6a は README に記述なし） |
| 登録の時期 | サーバーの起動が成功した後。停止の前に登録を解除する |
| サービスの型 | `_psfox._tcp`（Q1 は KudagiTune に決まったが、型は変えない。名前は 1 か所の定数） |
| インスタンス名 | `psfox-` と pc_id の先頭 8 桁（B4-1 の 1） |
| ポート | 現在のサーバーのポート |
| TXT | `v`（整数）、`pid`（pc_id の先頭 8 桁）、`pair`（0 または 1） |

#### インターフェースの選び方

1. 起動中の IPv4 のインターフェースを列挙する
2. ループバックを除く。仮想アダプタを除くかは実機で決める（B4-1 の 1。J21 の暫定どおり除かない）
3. 1 つも残らなければ、広告を行わず、W2 の警告ではなく W4 の接続先の一覧を空にする。サーバーは起動する（手入力で届くため）
4. ネットワークの変化（Wi-Fi の切り替え、テザリングの接続）を、一定間隔で列挙し直して検知する（間隔は V45。OS の通知の API を使うかは未確認）。変化があれば登録し直す

#### TXT の更新

- `pair` はコードの表示の開始と終了のたびに更新する。更新は登録の変更で行い、再起動しない
- ペアリング済み（`devices` が 1 件以上）の間は、コードを開かない（X5-5 の W1・W4）。このため `pair` は 1 にならない（P5 は常に 403 のため、受付中と知らせない。review-15 の X5-3）
- TXT に曲名、人名、PC のホスト名を入れない（N1-6）
- 広告は認証の代わりにならない（N1-5）。PC は広告の値を自分では確かめない

#### 読み書きの手順

読み込み

1. ファイルが無ければ、既定値で作る（`pc_id` を生成）。初回の印を立てる（起動の順 8 でメインの窓を自動で開く）
2. 読めない（JSON の誤り、必須項目の欠け）ときは、`settings.json.bad` へ改名して退避し、既定で起動し、警告を出す。K1 の項目は残る
3. `schema_version` が自分より新しければ、読まず、2 と同じ扱いにする（書き戻して失う事故を防ぐため）
4. `schema_version` が古ければ、版ごとの移行の関数を順に適用して現在の版にし、保存する。移行の関数は版 n から n+1 の 1 段ずつ。最初の版は移行が無い

書き込み

1. 内容を JSON に直す
2. 同じフォルダの一時ファイル（`settings.json.tmp`）へ書き、閉じる
3. 一時ファイルを `settings.json` へ置き換える（上書きの移動。失敗したら一時ファイルを消し、前のファイルは残る）
4. 書き込みは 1 つの窓口を通し、同時の書き込みを直列にする（P4 と画面の操作が重なるため）

#### ログ

| 項目 | 内容 |
|---|---|
| 置き場 | `%LOCALAPPDATA%\playlist-sync-fox\logs\` |
| 形式 | 1 行 1 件。時刻（UTC の ISO 8601。`Z`）、レベル、モジュール、メッセージ、E の番号（あれば）を、タブで区切る |
| レベル | 情報、警告、エラーの 3 段（詳細ログは持たない） |
| 切り替え | 1 ファイルが V8 の大きさを超えたら新しいファイルへ。世代数（V8）を超えた古いものを消す |
| 出してよい | ファイルのパス、曲名（N1-6、B4-6） |
| 出さない | 鍵、コード、署名の値、証明書の秘密鍵、`secrets.bin` の中身、署名のヘッダ、nonce |

- 出さない値の遮断は、ログの窓口で行う（要求のヘッダをそのまま渡す呼び出しを作らない）。署名の失敗の記録は、device_id と `detail` だけを書く
- ログの書き込みの失敗は同期を止めない。標準エラーへ 1 行だけ出す
- 外へ送らない（F6-1）
- 画面のログの欄（D21）：ファイルへ書く行と同じ行を、メモリの直近 V55 行にも入れて流す（ファイルの書き込みに失敗しても入れる）。起動の前の行はファイルから読み戻さない。欄の時刻は PC の地方時の `HH:mm:ss` で出す
- 画面の欄に流すため、次の行を情報で書く（D21）：P1 を返した（曲数）、P2 を送り終えた（表示名、大きさ）、P2 を途中で切られた（表示名）、P4 を受けた（結果）。P3・P7・P8 は数が多いので書かない
- ライブラリの読み取りの行（X2-2。review-15）：読み取りに成功するたびに、診断（読んだ曲数とプレイリスト数、落とした件数、復号不能の細目。X2-3 の `ReadDiagnostics`）を情報で 1 行書く。読み取りに失敗するたびに警告で、読み直すたびに情報で（何回目か）、V6 の回数で諦めたときはエラーで、1 行ずつ書く。書くのは件数、回数、失敗の種別だけで、曲名は書かない。パスは諦めの行にだけ `path=` で書く（PC のログにはパスを出してよい。N1-6）

### X5-6 起動と終了

#### 起動の順

1. 二重起動を防ぐ（review-15 の X5-15）。設定の置き場（`%APPDATA%\playlist-sync-fox\`）の `app.lock` を開いて排他のロックを取る。ロックを取れない 2 つ目は、同じ場所に `open-window.signal` を置いて終了する。1 つ目は 1 秒ごとに `open-window.signal` を見て、あれば消してメインの窓を開く
2. ログを初期化する
3. 設定を読み込む（X5-4）
4. 鍵を読み込む（`SecretStore`。X5-2。失敗なら X5-2 の扱い）
5. XML の監視を始める（M3 の `desktop.watch`。X2-4）。読み取りの結果は「PC の状態」に流す
6. サーバーを起動する（X5-1）。ポートの使用中と、そのほかの起動の失敗は、どちらも警告を出して続行（サーバーは止まった状態。X5-5 の W2）。ポートの範囲の検査は足さない（review-15 の X5-4）
7. mDNS の広告を登録する（X5-3）
8. トレイに入る。窓は、手動の起動（`--background` なし）では開き、`--background`（ログイン時の起動）ではトレイだけにする。ただし初回の印があれば、`--background` でも窓を開く（W4 のコードは自動では出さない）（review-15 の X5-5）

#### 終了の順

1. 同期中なら確認を出す（W1）。続行なら以下
2. コードを無効にする
3. mDNS の登録を解除する
4. サーバーを止める。送信中の接続は、猶予（V46）の後に切る
5. XML の監視を止める
6. 設定の保存が残っていれば書き切る

#### ログイン時の起動

- 登録先は現在のユーザーの Run キー（`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`）。管理者権限が要らない（B4-6 の場所の規則）
- 値の名前は `playlist-sync-fox`。値は配布物の実行ファイルのパスと `--background`（置いた値でなく定数）。パスが変わったとき（更新、移動）は、起動のたびに現在のパスで書き直す
- 無効にするときは値を消す。無ければ失敗にしない
- 登録先は Run キーで、zip 配布（J13）と合う
